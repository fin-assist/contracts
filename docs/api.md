# Клиентский API «Понятные финансы» — MVP

Версия: 2026-10-14 (0.2; уточнены деньги и заголовок `X-Read-Primary` 14.10.2026; инкременты FIN-36 — `tiles.forecast`, FIN-67 — операция без описания принимается, код `no_description` убран, FIN-68 — `INVALID_PHONE` слит в `VALIDATION_ERROR`, FIN-91 — когда клиент отправляет `timezone`, 2.2; FIN-79 — непрочитанные строки, дочитанные более поздней загрузкой, закрываются, 3.4 и 3.6; FIN-82 — расширяемость: тексты для кодов, валюта, открытые наборы, согласия списком, политика удаления; FIN-4 — экран «Аналитика» списком блоков, общий каталог блоков с помощником, 6.1 и 7.2; FIN-20 — заголовок `X-Client-Version`, коды `CLIENT_VERSION_UNSUPPORTED` и `MAINTENANCE`; FIN-196 — при смене версии реестра метрик до пересчёта отдаётся прежний снимок периода, `unavailable` — только без прежнего значения). Транспорт: HTTP/2 REST + SSE. Версионирование: URL path (`/v1/...`). Машиночитаемый контракт — `openapi.yaml` (OpenAPI 3.0.3); при расхождении смысл полей задаёт этот документ, а `openapi.yaml` правится вслед. Как считаются поля аналитики, ленты, поиска и итога импорта — `docs/calc.md` (FIN-158).

## Общие правила

### Формат
- Content-Type: `application/json` (запросы и ответы), `multipart/form-data` (загрузка файлов), `text/event-stream` (SSE).
- Моменты времени: ISO 8601 с часовым поясом (`2026-09-15T14:30:00+03:00`). В query-параметрах `+` кодируется как `%2B`.
- Диапазоны времени: пара `from` / `to` типа `datetime`, полуинтервал `[from, to)` — `from` включительно, `to` исключительно. Пример: сентябрь в Москве — `from=2026-09-01T00:00:00+03:00`, `to=2026-10-01T00:00:00+03:00`.
- Границы данных внутри периода (`data_from` / `data_to` у периода 6.1, точек графиков, сводки ленты 4.1, неполных месяцев 3.3) — по дням, покрытым периодом выписки `DTSTART..DTEND` (решение 16.10.2026), а не по операциям: `data_from` — начало (00:00) первого покрытого дня в периоде, `data_to` — время последней операции внутри периода, если она в последний покрытый день периода, иначе конец этого дня (23:59:59). Дни и время — в поясе профиля. Это моменты внутри дня, день берётся как есть: `data_from` 1 сентября и `data_to` 25 сентября — «1–25 сентября». Примеры: выписка по 25 сентября, последняя операция 25-го в 21:40 — `data_to` = `2026-09-25T21:40:00+03:00`; последняя операция 24-го в 19:10 — `data_to` = `2026-09-25T23:59:59+03:00`; в обоих случаях «по 25 сентября». Период с покрытыми днями без операций тоже их получает. Другое — `state.data_from` / `state.data_to` (4.1, 6.1): полуинтервал покрытых дней по всем загрузкам.
- Календарные единицы (месяц `YYYY-MM`, квартал `YYYY-Qn`, год `YYYY`, «сегодня») считаются в часовом поясе пользователя из профиля (`timezone`, 2.1). Границы календарного периода сервер всегда возвращает как `datetime`, клиент сам их не вычисляет. Исключение — сброс лимита помощника: всегда полночь по Москве (7.5).
- Деньги (суммы движений денег — операции, расходы, доходы, комиссии): целое число в минимальных единицах валюты — число знаков после запятой по ISO 4217 для этой валюты (RUB, USD, EUR — 2, т. е. копейки и центы; JPY — 0; KWD — 3). Клиент берёт число знаков из справочника ISO 4217 по `currency`, а не считает его равным 2. Валюта — в поле `currency` (ISO 4217); в аналитике и помощнике — всегда RUB. Уточнено 14.10.2026.
  - Величины, которым не хватает знаков валюты, — цена бумаги, курс, количество (дробные акции, паи, криптовалюта), — не деньги в этом смысле. Когда они появятся (интеграции с брокерами), это отдельный тип `decimal`: десятичное число строкой с точкой, без экспоненты, нужной точности (`"123.456789"`). Числом JSON с дробной частью ни деньги, ни `decimal` не передаются: Kotlin и JS читают его как double и теряют точность.
  - Сумма операции всегда неотрицательная, направление задаёт `kind`.
  - Суммы аналитики и ответов помощника — **со знаком**: возврат уменьшает расходы своей категории в месяце возврата, и сумма категории или всех расходов за период может уйти ниже нуля; «Доходы минус расходы» — отрицательная, если потратили больше.
- ID сущностей (пользователь, операция, загрузка, сообщение, регулярный платёж): непрозрачная строка. Клиент не парсит и не конструирует ID и не опирается на формат; сейчас это UUIDv7 в каноничной записи (`01a107db-ae80-7b07-b8a1-a8c8486e2532`), формат может смениться без breaking change. Исключение — регулярный платёж: формат его ID проверяется (UUID, `pattern` в OpenAPI, 6.3), и смена формата идёт вместе с правкой `pattern`, 6.3 и `RegularPayment.id`.
- Исключение — категории: стабильные строковые ключи справочника (`cat_supermarkets`), тоже непрозрачные.
- Секреты (токены, `verification_token`) — не ID: случайные значения, передаются только в теле или заголовках, никогда в пути и query-параметрах.
- Перечисления — строки, не числа. Три вида полей, см. «Нотация»: закрытый `enum`, открытый `code`, строка для показа.
- Все ответы — объекты (не голые массивы).

### Нотация в таблицах полей
- `string`, `int`, `bool`, `float`, `datetime`, `date`, `month`, `period_key`, `enum`, `code`, `object`, `array<T>`; после MVP — `decimal` (см. «Формат», деньги).
- `date` — календарный день `YYYY-MM-DD` (ISO 8601, в OpenAPI `string` с `format: date`) в поясе профиля, без времени и смещения: клиент показывает день как есть и не пересчитывает его в пояс устройства. Пара дней `*_from` / `*_to` — **оба дня включительно** (в отличие от полуинтервала `from` / `to` у `datetime`).
- Общие объекты: `range`, `operations_filter`, `analytics_params`, `block`, `action` — см. «Общие объекты» и «Блоки».
- `period_key` — ключ календарного периода: `YYYY-MM` (месяц), `YYYY-Qn` (квартал), `YYYY` (год). В OpenAPI `string` с `pattern: ^\d{4}(-(0[1-9]|1[0-2])|-Q[1-4])?$`. Формат расширяется вместе с `period` (неделя — ISO 8601 `YYYY-Www`); сервер возвращает ключи только в формате запрошенного `period`, поэтому старый клиент новых форматов не увидит.
- `T?` — в ответах поле может отсутствовать или быть `null`; клиент обрабатывает оба случая одинаково. В запросах `T?` — необязательное поле, которое просто не передаётся (`null` не отправляется).
- `optional<T>` — необязательное поле ответа **без `null`**: сервер либо не передаёт поле, либо передаёт значение типа `T`. В OpenAPI поле не входит в `required` и не имеет `nullable: true`. Полученный `null` — некорректное значение, его обработка задана у поля и может отличаться от отсутствия. В FIN-224 так обозначены `user_message`, `severity`, `error_user_message`, `error_severity` и REST `error.retryable`; обычная нотация `T?` и семантика прежних nullable-полей не меняются.
- `enum` — закрытый набор: в OpenAPI `enum`, новое значение — breaking change (новая версия API). Только там, где набор не может вырасти.
- `code` — открытый набор машиночитаемых значений: в OpenAPI `string` с `x-extensible-enum`, известные значения перечислены в описании. Клиент обязан обработать неизвестное значение — поведение указано у поля. Новое значение обратно совместимо.
- Если значение нужно клиенту только для показа, сервер присылает готовую строку (поле `*_name`), а не код.
- **Текст для кода.** У каждого открытого `code`, из которого клиент строит текст, есть серверный текст (`*_name`, `text`) — запасной вариант: известные коды клиент форматирует сам, для неизвестного показывает текст сервера. Иначе старый клиент не может объяснить новую блокировку, функцию или ситуацию.
- **Единица значения.** Значение, природа которого может быть разной (метрика, точка графика), несёт `value_kind` (открытый `code`: `amount`, `percent`, `count`, …); новая метрика другой природы показывается без релиза клиента. Неизвестный вид — значение не показывается, только подпись или текст блокировки.
- **Валюта.** Суммы несут валюту: у операции — своё поле `currency`, у ответа аналитики, итога импорта, события `snapshot` и сообщения помощника — `currency` на уровне ответа (суммы в блоках — в ней). Все суммы ответа (блока) — в этой одной валюте; смешанные валюты появятся новым полем, а не сменой смысла существующих.
- **Список сущностей, а не поле на каждую.** Набор однотипных сущностей, который может расти (согласия, счета, уведомления), — массив объектов с ключом (`consents[]` с `type`), а не отдельное поле на каждую: новая сущность — новый элемент, а не новое поле.
- **Имена полей в блоках.** Блоки разных типов (7.2, 6.1) не переиспользуют одно имя поля с другой формой: если у одного типа `rows` — массив, у другого `rows` не может быть объектом. Иначе ломается разбор у клиентов с плоской моделью блока.
- Почему так: кодогенерация (Kotlin, Swift) делает из OpenAPI `enum` закрытый тип, который падает на неизвестном значении, а oasdiff считает новое значение `enum` в ответе breaking change.

### Общие объекты

**`range`** — `{from: datetime, to: datetime}`, полуинтервал.

**`operations_filter`** — параметры поиска операций (4.1). Приходит из аналитики (у каждой цифры), из чипов помощника и из итога импорта. Клиент открывает Поиск с этими фильтрами: показывает их чипами, даёт править и сбросить. Поля — те же, что query-параметры 4.1 (`from`, `to`, `q`, `category_id`, `kind`, `amount_from`, `amount_to`, `transfer_mode`, `selection`), плюс одно поле только для показа:

| Поле | Тип | Описание |
|---|---|---|
| `selection_name` | string? | Подпись выборки `selection` для чипа в Поиске («Комиссии и проценты банку», «Самокат»). В запрос не передаётся |

Фильтры, у которых в Поиске нет своего чипа (`transfer_mode`, `selection`), показываются одним чипом с `selection_name` или «Как на „Аналитике“»; «Сбросить» убирает и их. `kind` здесь — открытый `code` (FIN-82): неизвестное значение клиент не отбрасывает — иначе выборка в Поиске молча расширится, — а показывает тем же чипом «Как на „Аналитике“» и передаёт в запрос 4.1 как есть. Отсутствующее поле — фильтра нет; в частности, без `transfer_mode` Поиск работает без правил аналитики (это не то же, что `with`).

**`analytics_params`** — параметры экрана «Аналитика» (6.1): `period`, `date`, `transfer_mode`, все три всегда заполнены. Сервер возвращает `period` того же типа, что запрошен (клиент запрашивает только известные ему). `transfer_mode` в любом ответе (здесь, в источнике ответа помощника): неизвестное значение клиент обрабатывает как `with`.

**`block`** и **`action`** — в «Блоки» ниже.

### Блоки (`block`)

Экран «Аналитика» (6.1) и ответ помощника (7.2) собираются из блоков одного каталога (FIN-4, решение владельца 15.10.2026). Сервер решает, какие блоки показать, в каком порядке и с какими данными; все подписи и тексты блоков — с сервера. Клиент умеет рисовать фиксированный набор примитивов: новая метрика на существующем примитиве появляется без релиза приложения, новый примитив или новое действие — с релизом.

Числа в `data` — JSON-числа, которые все клиенты (Kotlin, Swift, JS) и `google.protobuf.Struct` между сервисами читают как double: целое передаётся точно до 2^53 − 1. Суммы — целые в минимальных единицах валюты, и этого предела хватает с запасом (≈ 90 трлн ₽ в копейках); сервис, собирающий блок, не отдаёт сумму по модулю больше 2^53 − 1. Если понадобится больше, сумма придёт новым полем-строкой, а не сменой типа существующего.

Оболочка блока:
| Поле | Тип | Описание |
|---|---|---|
| `id` | string? | Стабильный идентификатор блока на экране «Аналитика» (`tiles`, `monthly_chart`, `expense_categories`, …). По нему клиент выключает блок флагом RuStore Remote Config `analytics.block.<id>` и пишет событие показа (FIN-9). В блоках помощника нет |
| `type` | code | Примитив — см. каталог ниже. Неизвестный тип клиент не рисует: показывает `alt_text`, если он есть, иначе пропускает блок |
| `v` | int | Версия схемы `data` для этого типа, начиная с 1. Неизвестная клиенту версия — как неизвестный тип |
| `status` | code? | Состояние, как у метрики: `ready` — посчитано (нет поля — `ready`); `tentative` — посчитано предварительно, данных мало; `locked` — пока не считаем, причина в `lock`; `none` — проверили, ничего нет; `unavailable` — значения нет: не удалось посчитать (сбой источника) или показатель новый и ещё не посчитан; при смене правил расчёта до пересчёта приходит прежнее значение, а не `unavailable` (FIN-196). Остальной экран показывается. Неизвестное значение — как `locked` |
| `lock` | object? | Только при `locked` |
| `lock.reason` | code | `need_full_months`, `need_months_with_data`, `too_early_in_month`, `stale_data` — для статистики и иконки. Неизвестное — блокировка без подробностей |
| `lock.text` | string | Готовый текст блокировки («Нужно 3 полных месяца, есть 1»; при нуле полных месяцев — «Нужно 3 полных месяца — пока есть только 1–25 сентября»). Клиент показывает его как есть. Если сервис текст не заполнил, приходит общий «Пока недоступно» (`grpc-api.md` 5.3); у вложенной блокировки (плитка `tile_group`) его же показывает клиент, если `text` пустой или его нет |
| `lock.required`, `lock.available` | int? | Для `need_*`: сколько месяцев нужно и сколько есть. У метрик с окном от выбранного месяца — «до выбранного включительно» (`regular_payments`, `small_frequent`) или «перед выбранным» (`notable_spending`) — `available` только такие месяцы, а текст при нуле строится по данным до конца выбранного периода («пока есть только 29–30 июня»), а не по всем загрузкам |
| `lock.available_from` | datetime? | Для `too_early_in_month`: с какого момента откроется |
| `title` | string? | Заголовок блока («Расходы по месяцам») |
| `alt_text` | string? | Текстовая версия блока: подпись для TalkBack и запасной вид для клиента, который тип не знает. Есть у всех блоков, кроме `text` и `heading` |
| `empty_text` | string? | Текст при `none` и `unavailable` («Регулярных платежей не нашли за апрель — сентябрь», «Не получилось посчитать — обновите экран позже») |
| `data` | object? | Содержимое примитива по схеме `type` и `v`; есть при `ready` и `tentative`, у `tile_group` и `insight_card` — всегда (у плиток своё состояние, закрытой карточке нужны иконка и заголовок) |
| `action` | action? | Действие по нажатию на блок целиком |

**Значения.** Число в `data` всегда идёт парой `value` + `value_kind` (открытый `code`: `amount` — сумма в минимальных единицах валюты `currency` ответа, со знаком; `percent` — доля 0–1; `count` — количество). Неизвестный `value_kind` — значение не показывается, только подписи. Форматирует значение клиент («−84 320 ₽», «46%»); `approx: true` — «≈» перед значением, `show_plus: true` — «+» у положительного.

**Действия (`action`).** Фиксированный словарь, `type` — открытый `code`; неизвестное действие — элемент не нажимается. Поля из колонки «Поля» для своего `type` обязательны (в схеме они необязательные, потому что у разных `type` разные): действие без них клиент считает неизвестным — элемент не нажимается, кнопка не показывается. Пустая строка (`label`, `payment_id`) и `filter` без единого условия считаются отсутствием: иначе кнопка без подписи или Поиск без фильтров, где выборка не совпадёт с цифрой. Условие фильтра — хотя бы одно из `from`/`to`, `q`, `category_id`, `kind`, `amount_from`/`amount_to`, `selection`; `transfer_mode` и `selection_name` не в счёт (переводы задают режим, а не выборку). `kind` — условие, если задан: в REST поле отсутствует, когда направления нет (значения «все» у него нет), в gRPC это `KIND_FILTER_UNSPECIFIED`.
| `type` | Поля | Что делает клиент |
|---|---|---|
| `open_operations` | `filter`: operations_filter | Открывает Поиск с этими фильтрами (выборка совпадает с цифрой; исключения — `docs/calc.md`, раздел 5, «Выборки») |
| `open_assistant` | — | Открывает чат помощника с режимом переводов экрана |
| `dismiss_regular_payment` | `payment_id`: string, `label`: string («Не подписка») | Кнопка у строки платежа (`items[].button` карточки): 6.3 `PUT …/dismissal`, затем перезапрос 6.1 |

**Каталог примитивов, версия 1.** Имена полей не переиспользуются с другой формой в разных типах («Нотация»).

`heading` — заголовок раздела экрана:
| Поле `data` | Тип | Описание |
|---|---|---|
| `text` | string | «Регулярные платежи и заметные траты» |

`text` — текст в узком подмножестве Markdown: абзацы (пустая строка), `**жирный**`, маркированный список (`- `); всё остальное — обычный текст:
| Поле `data` | Тип | Описание |
|---|---|---|
| `text` | string | Текст. В потоке помощника (7.2) растёт событиями `chunk` |

`rows` — строки «подпись — значение»:
| Поле `data` | Тип | Описание |
|---|---|---|
| `rows` | array | Строки по порядку |
| `rows[].label` | string | Подпись («Средний чек») |
| `rows[].sublabel` | string? | Вторая строка подписи |
| `rows[].value`, `rows[].value_kind` | number?, code? | Значение; нет — значение текстом |

### Аутентификация
- `Authorization: Bearer <access_token>` на всех эндпоинтах, кроме `/v1/auth/*` (кроме `/v1/auth/logout`).
- Access token: JWT, 15 мин. Refresh token: opaque string, ротация при каждом использовании.
- 401 → клиент пробует `/v1/auth/token`, при неудаче — на экран входа. Корректный `error.retryable: false` запрещает прямой повтор исходного запроса с прежним контекстом, но не этот восстановительный сценарий: после успешного обновления токена предусмотренная сценарием отправка исходных метода/адреса/тела выполняется с новым `Authorization`, прежним `Idempotency-Key` (если нужен) и новым `X-Request-Id`, только при сохранённых safety/TTL. Истёкший ключ не заменяется автоматически новым; без безопасного повтора используется предусмотренное восстановление/вход.

### Заголовки
- Запрос: `X-Request-Id: <uuid>` (клиент генерирует, сквозная трассировка; новый на каждую попытку).
- Запрос: `Idempotency-Key: <uuid>` — на запросах с побочными эффектами, см. «Идемпотентность».
- Запрос: `X-Read-Primary: 1` — читать с основной базы, чтобы сразу увидеть свою запись. Клиент ставит его на все запросы в течение 30 секунд после любого своего успешного пишущего запроса (`POST`, `PUT`, `PATCH`, `DELETE`), затем перестаёт; по умолчанию заголовка нет. Механически, одним перехватчиком HTTP-клиента — без учёта того, какие данные читаются (решено 14.10.2026).
- Запрос: `X-Client-Version: <платформа>/<версия>+<сборка>` (`android/0.2.5+41`) — **обязателен** на всех запросах `/v1/*`, включая `/v1/auth/*` и SSE (FIN-20, решено 15.10.2026). Платформа — открытый код (`android`, `ios`, `web`): строчные латинские буквы, цифры и `_`, начинается с буквы. Версия — `MAJOR.MINOR.PATCH`, каждая часть — неотрицательное целое без ведущих нулей (`0.10.0`, не `0.010.0`). Сборка — целое число из цифр. Всего не больше 64 символов. Значение, не подходящее под этот формат, считается неразобранным. Шаблон — у параметра `X-Client-Version` в `openapi.yaml`.
  - Сервер сравнивает версию с минимальной поддерживаемой для платформы (настройка сервера в виде `MAJOR.MINOR.PATCH`, меняется без релиза клиента). Сравниваются только `MAJOR.MINOR.PATCH` по порядку, как числа; сборка в сравнении не участвует (для логов); версия, равная минимальной, проходит. Пример: минимальная `0.2.5` — `android/0.2.5+40` проходит, `android/0.2.4+99` нет. 400 `CLIENT_VERSION_UNSUPPORTED` — если версия ниже минимальной, заголовка нет, значение не разобрано или платформа неизвестна. Приложение шлёт заголовок с первой сборки для прода, поэтому легитимного запроса без него нет; новая платформа сначала получает минимальную версию в настройке сервера.
  - Значение задаёт клиент, его можно подделать: сервер использует его только для совместимости, логов и метрик, не для авторизации и не для лимитов.
  - Служебные маршруты вне `/v1` (проверка доступности, вебхуки провайдеров) заголовка не требуют.
  - Браузерный preflight (`OPTIONS`) идёт без `Authorization` и без нестандартных заголовков. Сервер обрабатывает его до всех проверок — техработ, версии клиента, аутентификации — и не требует ни `X-Client-Version`, ни `Authorization`; `X-Client-Version`, `Authorization` и другие заголовки запросов входят в `Access-Control-Allow-Headers`. Нужно, когда появится веб-клиент (вне MVP).
- Ответ: `X-Request-Id` (эхо); свежий HTTP `Date` — во всех ответах BFF, включая ошибки; `Retry-After` (секунды) — у 429, 409 `REQUEST_IN_PROGRESS` и 503 `MAINTENANCE`. Правила таймеров — «Время ожидания и часы».

### Адрес клиента за доверенным прокси (FIN-343)

Адрес для серверных лимитов по IP (включая SSE) определяет `bank-bff`; он же передаёт его сервисам как gRPC metadata `x-client-ip`. Мобильный клиент IP не присылает: HTTP-заголовок `X-Client-IP` не используется.

- По умолчанию адрес клиента — IP TCP-пира. `X-Forwarded-For` от недоверенного пира игнорируется целиком.
- За своим nginx или ingress в `bank-bff` задаётся `TRUSTED_PROXIES`: список IPv4/IPv6 CIDR доверенных прокси через запятую, например `127.0.0.1/32,::1/128` для локального nginx. Для стенда и prod включаются только адреса/сети контролируемых HTTP-прокси, каждый из которых сам дописывает IP своего TCP-пира в `X-Forwarded-For`; это обязательное условие доверия, в том числе для промежуточных прокси. L4-балансировщики, NAT/SNAT и узлы, не дописывающие этот заголовок, в список не входят: иначе BFF пропустит их адрес и примет подставленный клиентом префикс. Если они скрывают адрес клиента, его восстанавливают на первом HTTP-прокси из доверенного инфраструктурного источника (например, PROXY protocol / `real_ip`), а не расширяют `TRUSTED_PROXIES`. Сети клиентов и `0.0.0.0/0` / `::/0` не доверяются. Пустой список означает, что заголовку не доверяют: за прокси все пользователи тогда получают его IP и общий лимит по IP. Неверный CIDR — ошибка конфигурации при старте.
- Каждый доверенный прокси дописывает в `X-Forwarded-For` IP своего TCP-пира (в nginx — `proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;`). Только если TCP-пир BFF доверенный, BFF читает все строки этого заголовка как одну цепочку справа налево: пропускает доверенные адреса и берёт первый недоверенный. Заголовок, дополненный своим доверенным прокси, — инфраструктурный источник; произвольному префиксу клиента не доверяют и левее найденного адреса не читают. Если заголовка нет, остаётся адрес TCP-пира; если все элементы доверенные — крайний левый из них. При неразбираемом элементе в просматриваемой части цепочки или достижении предела 16 просмотренных элементов без недоверенного адреса остаётся последний успешно определённый доверенный узел; левый префикс для обхода этой границы не используется.
- Пример: TCP-пир BFF `10.0.0.2`, доверены `10.0.0.0/24`, заголовок `192.0.2.66, 198.51.100.7, 10.0.0.1` — адрес клиента `198.51.100.7`; подставленный клиентом `192.0.2.66` не влияет. Тот же заголовок от недоверенного TCP-пира `203.0.113.8` игнорируется, адрес клиента — `203.0.113.8`.

### Время ожидания и часы

`datetime` остаётся абсолютным моментом RFC 3339 с часовым поясом; правила календаря и пояса профиля/Москвы не меняются. Разность `datetime − текущие часы телефона` не используется для обратного отсчёта: часы устройства могут расходиться с серверными или измениться во время ожидания.

- Для задержки запроса приоритет имеет свежий `Retry-After` в секундах, который BFF получает из актуального `RetryInfo`/deadline; для срока верификации — актуальный `expires_in`. Полученную длительность клиент уменьшает по **монотонно прошедшему времени с учётом сна устройства**. Ни смена часового пояса, ни перевод часов телефона не перезапускают таймер и не разрешают повтор.
- BFF выдаёт корректный свежий HTTP `Date` при формировании каждого ответа, включая `4xx`, `5xx` и воспроизведение результата под ключом. `Date` не берётся из сохранённого ответа. Если есть только абсолютный срок, допустима приблизительная оценка для UI: в момент получения ответа `remaining = max(0, target_datetime − Date)` **из того же свежего ответа**, затем из неё вычитается монотонно прошедшее время. Для такого сравнения часы BFF и сервиса должны быть синхронизированы; сетевые задержки и точность HTTP Date делают оценку приблизительной. Прямая длительность от сервиса предпочтительнее.
- `Date`/относительный срок из кэша или сохранённого старого ответа не становятся новой временной базой. Если свежая длительность `Retry-After`/`expires_in` получена, для её отсчёта `Date` не требуется. Если срок задан **только datetime** и корректного свежего `Date` нет, клиент обновляет состояние по существующему сценарию; до обновления показывает безопасный абсолютный текст без точного обратного отсчёта. После перезапуска устройства/потери монотонной базы обновление требуется независимо от источника прежнего срока: старую длительность заново не запускают. Если прямой повтор запрещён, само отсутствие временной базы не разрешает отправить его ради обновления — сохраняется предусмотренный восстановительный сценарий.
- Эти вычисления служат отображению и ожиданию, **не** доказывают авторизацию, действительность токена, ключа или replay-окна и не создают permission. Сервис повторно проверяет состояние при действии. Изменение состояния может снять ограничение раньше показанного срока либо продлить его; таймер не обещает успех.
- Подпись верификации «до ЧЧ:ММ» по-прежнему строится в местном поясе устройства от его часов в момент получения плюс рассчитанная оставшаяся длительность. Это подпись для пользователя; сам таймер работает по elapsed time, а не по настенным часам.

### Идемпотентность
Мобильная сеть рвёт соединение после того, как запрос дошёл до сервера, но до того, как клиент получил ответ. Повтор такого запроса не должен ничего задваивать или ломать.

- **Где обязателен `Idempotency-Key`:** на каждом `POST`, который создаёт ресурс или имеет побочный эффект — тратит лимит или деньги (звонок, LLM), меняет состояние сессии. В MVP: 1.1, 1.3, 1.4, 3.2, 7.1, 7.4. Без заголовка — 400 `VALIDATION_ERROR`. Каждый новый такой эндпоинт обязан его требовать — проверяется на ревью API.
- **Где не нужен:** `GET`; `PATCH` и `PUT`, которые присваивают значения, — повтор даёт тот же результат; `DELETE` — повтор после успеха возвращает тот же `204`; 1.5 (выход) — повтор возвращает `204`.
- **Ключ:** UUID, клиент генерирует на одно логическое действие пользователя («отправить этот вопрос», «загрузить этот файл») и хранит до получения окончательного ответа — переживает перезапуск запроса и обрыв, но не новое действие. `X-Request-Id` при этом на каждой попытке новый.
- **Область ключа:** пользователь + эндпоинт; для эндпоинтов без токена (1.1, 1.3, 1.4) — ключ + эндпоинт.
- **Повтор с тем же ключом и тем же телом** в течение срока хранения — сервер не выполняет запрос заново и возвращает сохранённый ответ (статус и тело). Сохраняются только ответы, которые зависят лишь от самого запроса: `2xx`, `400` (кроме `CLIENT_VERSION_UNSUPPORTED`, см. ниже), `413`, `422`. Не сохраняются `401`, `403`, `404`, `409`, `429`, `5xx` — состояние могло измениться (дали согласие, наступила полночь), повтор с тем же ключом выполняется заново. Исключение — 429 `RATE_LIMITED` на дубль в 1.1 (номер занят у провайдера): он сохраняется под ключом до своего `retry_at`, и повтор с тем же ключом и телом до `retry_at` получает сохранённый 429, не обращаясь к состоянию. Так можно, потому что сохраняется консервативный отказ без секретов до первоначального retry_at и он не разрешает новый внешний эффект; номер может безопасно освободиться раньше, но кэш именно этого ключа остаётся до retry_at; так нужно, потому что иначе опрос тем же ключом не упирался бы в лимит. Хранится сам `retry_at`, и при повторе `Retry-After` пересчитывается от текущего момента до него, а не берётся из первого ответа: повтор в 22:16:50 при `retry_at` 22:17:00 получает `Retry-After: 10`. С момента `retry_at` (включительно) снимок 429 снимается: пред-dispatch duplicate key выполняется заново, а исходный ключ с dispatch-marker и terminal duplicate остаётся терминальным без повторного confirm (1.1). 429 по лимиту — как остальные, не сохраняется.
- **Тот же ключ, другое тело** — 409 `IDEMPOTENCY_CONFLICT`. Тело сравнивается по хешу (для 3.2 — по хешу содержимого файла и его имени: тот же файл под другим именем — другое тело; формула — `grpc-api.md`, раздел 6). Если пользователь исправил ввод после ошибки (другой номер, новая версия согласия, другой файл) — это новое действие и новый ключ.
- **Первый запрос с этим ключом ещё выполняется** — 409 `REQUEST_IN_PROGRESS` с `Retry-After`.
- **Срок хранения:** 24 часа; для 1.4 (обновление токенов) — 60 секунд, потому что в сохранённом ответе секреты.
- **1.1, попытка без сохранённого ответа:** отсутствие кэша после 5xx не делает ключ неизвестным, если долговечная попытка уже создана. Она находится на шаге ключа до лимитов/занятости: другое тело — конфликт; работающий исполнитель — `REQUEST_IN_PROGRESS`; иначе продолжается попытка по её долговечному состоянию (первый вызов без отметки либо сверка после отметки, правила 1.1), без повторного confirm/Start, повторного списания лимита и 429 против собственной резервации. Определённо не созданная провайдером заявка закрывает попытку, для нового действия нужен новый ключ (подробности 1.1).
- **Ответы до проверки ключа** — 503 `MAINTENANCE`, 400 `CLIENT_VERSION_UNSUPPORTED`, 401 по заголовку `Authorization` и 400 / 413 проверок `bank-bff` (порядок — «Ошибки»), а у 3.2 ещё и 413 `FILE_TOO_LARGE` от сервиса: он отвечает им, не дочитав файл, а хеш тела для сверки ключа известен только в конце файла (`grpc-api.md`, раздел 6) — сервер отдаёт до обработки запроса и под ключом не сохраняет: после техработ, обновления приложения, обновления токена или исправления запроса повтор с тем же ключом выполняется как первый.

### Ошибки
Ответ с ошибкой всегда содержит ровно один объект `error`, даже если нарушений несколько:
```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Request validation failed",
    "retryable": false,
    "details": [
      {
        "field": "amount_from",
        "code": "OUT_OF_RANGE",
        "message": "must be >= 0"
      },
      {
        "field": "date",
        "code": "INVALID_FORMAT",
        "message": "must be YYYY-MM, YYYY-Qn or YYYY"
      }
    ]
  }
}
```
| Поле | Тип | Описание |
|---|---|---|
| `error.code` | code | Машиночитаемый код ошибки (реестр — раздел 8). Специальные действия — только по известному коду; неизвестный код отображается по `user_message`, а без корректного текста — безопасная общая ошибка по HTTP-статусу |
| `error.message` | string | Текст для логов и отладки, не для UI |
| `error.user_message` | `optional<string>` | Безопасный текст для пользователя из каталога `bank-bff`, 1–1000 символов Unicode, не только пробельные символы. Правила отображения и совместимости — ниже |
| `error.severity` | `optional<code>` | Оформление: `info`, `warning`, `error`. Неизвестное, отсутствующее или некорректное значение — оформление `error` с сохранением корректного `user_message` |
| `error.retryable` | `optional<bool>` | Только REST: `true` означает одновременно безопасность повторной отправки этого запроса по правилам идемпотентности метода и разрешение повторить его после этой ошибки. `false` — такого объединённого разрешения нет. Не является характеристикой всех вызовов метода; условия, время ожидания и совместимость — «Повтор REST-запроса» ниже |
| `error.details` | array? | Список нарушений; сейчас только для `VALIDATION_ERROR`. Сервер возвращает все найденные нарушения, а не первое |
| `details[].field` | string? | Путь к полю: имя query-параметра или JSON-путь в теле (`filters.category_id`). Нет, если нарушение касается запроса целиком |
| `details[].code` | code | Код нарушения: `REQUIRED`, `INVALID_FORMAT`, `OUT_OF_RANGE`. Неизвестный код — общая ошибка поля |
| `details[].message` | string | Текст для логов и отладки |
| `error.retry_at` | datetime? | У `RATE_LIMITED`: когда можно повторить («Слишком много попыток, повторите через 10 минут») |
| `error.until` | datetime? | У `MAINTENANCE`: ожидаемое окончание техработ. Нет — время окончания неизвестно; ожидание задаёт `Retry-After`; отдельное однократное возобновление известного экрана техработ, включая случай `retryable: false`, описано в «Повторе REST-запроса» ниже |
| `error.<поле>` | — | Другие дополнительные поля конкретного кода описаны у кода (например, `resets_at` у `LIMIT_EXCEEDED`) |

#### Общий механизм и адаптеры ошибок (FIN-224)

Во внутреннем API переиспользуется `google.rpc.Status` с типизированными `ErrorInfo`, `BadRequest`, `RetryInfo` и optional `common.v1.RequestRetryInfo` (grpc-api.md 5.4). Общий механизм передаёт причину, структурированные параметры, валидацию и разрешение повторить **исходный запрос**; он не содержит квот, списаний, логики модели или выбора новой прикладной операции. Разрешение сервиса на исходный RPC и безопасность всего внешнего REST-запроса — отдельные проверки. BFF соединяет их для REST `error.retryable` и формирует безопасные UI-тексты из своего каталога; он не выводит business permission из имени причины.

При отказе unary RPC Status является транспортным отказом и переводится по прежнему HTTP-реестру `error_spec`. Внутри результата, terminal event или истории Status описывает неудачный результат **успешного RPC чтения** и не превращает его в HTTP 500 или обрыв потока. В initial result profile `RequestRetryInfo` и относительный `RetryInfo` запрещены: они не дают повторить чтение, начать новую попытку или заново отсчитать старое ожидание. Возможность новой попытки и её операция задаются отдельным свойством внешнего результата; в существующем сценарии помощника это прежний `retryable` и `RetryAnswer`. Остаток, списание и состояние операции остаются вне общего Status.

Аддитивные внутренние поля — `AnswerError.status` (6), `Message.error` (14), `ImportStreamError.status` (3); прежние поля и terminal oneof сохраняют номера и типы. Они не добавляются в клиентский JSON. При отсутствии вложенного Status BFF использует прежний адаптер. Корректный присутствующий Status имеет приоритет: открытый `ErrorInfo.reason` переносится во внешние `code`/`error_code`, даже если его нет в старом enum или unary-реестре. Для неизвестной каталогу причины BFF использует общий безопасный текст и диагностику, сохраняя terminal/failed исход. Присутствующий некорректный Status даёт безопасный текст/метрику и фиксированную внешнюю проекцию: терминальный помощник — `code: INTERNAL_ERROR`, его failed-история — `error_code: INTERNAL_ERROR` (не `null`), импорт — `code: PROCESSING_FAILED`. Legacy-код при этом **не читается**, даже если он известен: malformed Status вместе с legacy `CANCELLED` не проецируется как отмена. При отсутствии Status прежний адаптер по-прежнему сохраняет `CANCELLED`. Корректное явное внешнее `retryable` помощника сохраняется от сервиса независимо от ошибки; оно не выводится из Status или несовпадающего enum. Полные правила dual-write, версий и отката — grpc-api.md 5.5.

#### Единое отображение ошибок (FIN-224)

`user_message` и `severity` — необязательные поля без `null` (`optional<T>`) в REST-объекте `error` и во всех объектах события SSE `error` (общем, импорта 3.3 и помощника 7.2). В плоском сообщении истории помощника 7.3 им соответствуют `error_user_message` и `error_severity` с тем же правилом. Отсутствующее значение сервер **не передаёт**, а не заменяет на `null`; у сообщений истории, не имеющих `status: failed`, оба новых поля `error_user_message` и `error_severity` отсутствуют. Прежний nullable `error_text` сохраняет свою нотацию `string?`. Значения формирует только `bank-bff` по машинному коду и проверенным структурированным параметрам из единого каталога. Внутренние сервисы не задают эти тексты и оформление. Каталог не копируется в клиент или сервисы. Новый обычный код с текстом требует обновления сервиса и каталога BFF, но не приложения. Новое специальное действие требует поддержки в клиенте и не включается текстом или критичностью.

Корректный пользовательский текст — строка от 1 до 1000 символов Unicode (считаются кодовые точки, не байты и не кодовые единицы UTF-16), содержащая хотя бы один символ вне Unicode `White_Space`: U+0009–U+000D, U+0020, U+0085, U+00A0, U+1680, U+2000–U+200A, U+2028, U+2029, U+202F, U+205F, U+3000. Строка показывается как обычный текст: HTML, Markdown, ссылки и команды не исполняются, не создают переходов и действий. Это ограничение не делает произвольную строку безопасной: BFF использует контролируемые шаблоны, не вставляет сырой ввод пользователя, SQL, сообщения исключений, ответы провайдеров или модели. Вставляемые параметры берутся только из разрешённых типизированных полей и форматируются BFF. Диагностические `message` и `details[].message` никогда не становятся пользовательским текстом автоматически.

Клиент разбирает оформление независимо от машинного кода, дополнительных полей и метаданных повтора; некорректное необязательное поле оформления не должно уничтожать их:

1. Корректный `user_message` (в истории `error_user_message`) показывается и для известного, и для неизвестного кода.
2. Если нового поля **нет**, из прежних серверных полей допускается только явно пользовательский текст помощника: `text` в 7.2 или `error_text` в 7.3. Для него действуют те же ограничения текста. Это совместимость со старым сервером; диагностический `message` не используется. Существующий безопасный локальный текст известного кода сохраняется по правилу 3.
3. Если новое поле присутствует, но равно `null`, имеет другой тип, пустое, пробельное или длиннее 1000 символов, клиент использует безопасный локальный текст. Прежний `text`/`error_text` в этом случае не подставляется. Если нового поля нет и нет корректного разрешённого прежнего текста, результат тот же. Для известных кодов всех сценариев сохраняются прежний безопасный локальный текст и поведение с учётом кода и контекста: например, «OFX не Т-Банка» у `WRONG_BANK`, подсказка использовать OFX у `CSV_NOT_ACCEPTED`, предложение сузить период у `TOO_MANY_RESULTS`. Это совместимость существующих сообщений, а не новый растущий каталог клиентских текстов: новый обычный код приходит с текстом BFF. Общая ошибка по HTTP-статусу — только для неизвестного REST-кода. В импорте у известного `CANCELLED` сохраняются прежнее сообщение и поведение отмены разбора пользователем; запасной текст «Не удалось разобрать файл» относится к `PROCESSING_FAILED` и неизвестному коду импорта. Для помощника остаётся прежний запасной текст «Не получилось ответить», для общего события SSE — безопасная общая ошибка сценария.
4. `info` — информационное оформление, `warning` — предупреждение, `error` — ошибка. Это открытый набор: неизвестное, отсутствующее, `null` или значение другого типа оформляется как `error`, но корректный пользовательский текст сохраняется. Оформление не меняет исход операции: даже `info` в событии `error` остаётся ошибкой.
5. Действие определяется формой ошибки, эндпоинтом и сценарием, **не одной строкой кода**. Действия раздела 8 относятся к REST-объекту `Error` и только к тем контекстам общего `ErrorEvent`, где действие явно описано. В `AnswerErrorEvent`, `StreamError` и failed-истории совпадение кода с `CONSENT_REQUIRED`, `LIMIT_EXCEEDED`, `MAINTENANCE` или иным REST-кодом не запускает вход, согласие, REST-квоту, экран техработ или повтор исходного `AskQuestion`; действуют правила соответствующего результата. Прежние сценарные `CANCELLED` импорта и permission новой попытки помощника сохраняются. В применимом контексте все существующие действия известных кодов из раздела 8 и описаний эндпоинтов сохраняются независимо от текста и оформления: в том числе вход, обновление согласия или приложения, экран техработ, открытие Поиска без недействительной `selection`, перечитывание категорий и ожидание времени повтора. Неизвестный код не создаёт новых специальных действий. Времена ожидания `retry_at`, `Retry-After`, `resets_at` и доменный `retryable` помощника сохраняют прежнюю семантику; разрешение прямого REST-повтора подчиняется приоритету `error.retryable` ниже. `severity` не разрешает повтор и не отменяет время ожидания. У неизвестного кода **общего** SSE `error` (`ErrorEvent`, прежнее имя схемы `SseError`, 1.2) сохраняется прежнее предложение повторить вручную независимо от наличия/корректности `user_message` и `severity`; это не отменяет ограничений сценария и ожидания `RATE_LIMITED` и не заменяет `retryable` события помощника.

Совпадение имени не связывает действия между контекстами: REST `Error.code: MAINTENANCE` использует описанный экран техработ, а terminal `AnswerErrorEvent.code: MAINTENANCE` — обычную ошибку результата с безопасным текстом и внешним `retryable`; он не открывает экран техработ и не возобновляет исходный AskQuestion. Общий декодер Status не запрещает совпадающие reason и не знает таблицу REST-действий. Wire-примеры этих контекстов и трёх present-invalid проекций — `fixtures/errors/presentation.json`; это примеры внешней схемы, runtime-проверки адаптера и клиента относятся к FIN-225/FIN-223.

Примеры нового обычного кода и существующего лимита (тексты — примеры каталога, не дополнительное условие лимита):

```json
{"error":{"code":"NEW_ORDINARY_ERROR","message":"Request rejected","user_message":"Сейчас выполнить действие не получилось. Попробуйте позже.","severity":"warning","retryable":false}}
```

```json
{"error":{"code":"RATE_LIMITED","message":"Rate limited","user_message":"Слишком много попыток. Попробуйте позже.","severity":"warning","retryable":false,"retry_at":"2026-10-25T20:00:00+03:00"}}
```

У второго ответа HTTP 429 и `Retry-After` по существующему правилу. `severity: "future_level"` в любом из примеров означает оформление `error`, текст сохраняется. Старый ответ `{"error":{"code":"INTERNAL_ERROR","message":"Internal error"}}` показывает общий клиентский текст, а не `message`. Ответ с `"user_message":" "` тоже показывает общий текст, даже при корректном старом тексте помощника.

Порядок совместимого внедрения:

1. После мержа владелец публикует новый неизменяемый `gen/go` тег для новых protobuf-полей и `finerr` API. Зависимые backend/library PR используют этот тег. Сначала обновляются декодеры BFF/потребителей, затем producers с dual-write прежних полей; конкретные условия — grpc-api.md 5.5. Клиент может добавить чтение внешних необязательных полей с указанными fallback, продолжая работать со старым BFF; одновременная выкладка клиента и BFF не требуется.
2. До выкладки нового BFF все экземпляры `assistant` поддерживают `retryable` FIN-159; список допустимых версий и границу отката фиксируют в FIN-225 и конфигурации выкладки (grpc-api.md 5.5). Версии до этой границы новый BFF не поддерживает: proto3 bool не отличает отсутствие от авторитетного `false`, а UI-текст больше не используется для определения возможностей сервиса. BFF начинает формировать канонические поля из своего каталога для REST, SSE и истории. Для старых клиентов он продолжает заполнять `text` события помощника и `error_text` истории **тем же безопасным текстом каталога**. Значение прежнего диагностического `message` не переопределяется. Новый BFF не использует прежние UI-строки из gRPC для этих полей.
3. Только после обновления всех экземпляров BFF и фиксации минимальной допустимой версии BFF в конфигурации выкладки и FIN-225 сервисы могут прекратить формирование прежних gRPC-строк `AnswerError.text` / `Message.error_text`. Откат BFF ниже этой версии после прекращения заполнения запрещён: иначе старый BFF снова зависел бы от уже пустых строк. Номера, имена и типы protobuf-полей остаются; в FIN-224 они не удаляются и не помечаются `deprecated`.

При неизвестном unary-коде или неполной внутренней транспортной ошибке BFF использует контролируемый общий текст и существующее преобразование транспортного статуса (для неизвестного gRPC `reason` — 500 `INTERNAL_ERROR`, grpc-api.md 5). Открытая причина корректной вложенной ошибки результата не обязана входить в этот unary-реестр и сохраняет семантику результата по правилам выше. Сырые внутренние строки наружу не копируются. Диагностическая связь сохраняется через `X-Request-Id`, логи и существующие метрики; значение неизвестного кода не становится пользовательским текстом. Для неизвестного кода терминального доменного события используется безопасный общий текст сценария, прежняя семантика завершения и авторитетный `retryable` помощника. Обрыв транспорта посреди SSE по-прежнему не превращается в доменное событие `error`.

#### Повтор REST-запроса (FIN-224)

Необязательный non-null `error.retryable` относится к повторной отправке **того же API-запроса** после полученного REST-отказа. Значение `true` даёт две гарантии вместе: повтор безопасен по правилам идемпотентности конкретного метода и при этой ошибке разрешён. Это не объявляет метод глобально идемпотентным для любого будущего вызова. Значение `false` не даёт объединённого разрешения на прямой повтор этой попытки; оно не доказывает неидемпотентность метода и не запрещает предусмотренные сценарием исправления.

- **Приоритет:** корректное `error.retryable: false` запрещает прямую повторную отправку в неизменённом контексте и автоматическое переоткрытие SSE после этого REST-отказа, даже если прежнее описание `429` или `409` предлагало повторить по таймеру. При `true` повтор возможен только с выполнением всех условий ожидания, метода и окна ключа. Лишь отсутствие или некорректный флаг сохраняет прежнее известное безопасное поведение. Успешный auth-flow и отдельный известный сценарий `MAINTENANCE` остаются восстановительными сценариями по правилам ниже; это не разрешение общего таймерного повтора. Отдельное правило ручного повтора терминального `ErrorEvent` (алиас `SseError`) не меняется.
- При прямом повторе без изменения контекста сохраняются HTTP-метод, адрес и тело исходного запроса и **тот же** `Idempotency-Key`, если метод его требует. `X-Request-Id` меняется на каждой отправке. Исправленный ввод, другой файл, новая версия согласия или новое намерение пользователя — новое логическое действие с новым ключом по прежним правилам. `retryable: false` не отменяет вход, обновление токена/согласия/приложения, исправление `selection`, перечитывание категорий и другие корректирующие действия из раздела 8 и описаний методов.
- `true` разрешает повтор, но не требует автоматической отправки, не обещает успех и не разрешает бесконечный цикл. Ограничения сценария, `Retry-After` и `retry_at` продолжают действовать. `resets_at` сообщает о суточной квоте, а не разрешает повтор. Критичность, текст, HTTP-статус или их сочетание не заменяют флаг и не создают новую возможность повтора. Для известного `MAINTENANCE` сохраняется отдельный прежний сценарий экрана техработ: после указанного `Retry-After` допустимо одно контролируемое возобновление исходной операции с прежними методом/адресом/телом и тем же ключом, только при проверенных safety/TTL. Это узкое восстановление известного сценария, а не прямой retry по произвольному таймеру или permission неизвестного кода; при новом отказе автоматический цикл не запускается. Ввод пользователя сохраняется.
- **В момент фактической повторной отправки** клиент снова проверяет ограничения метода и действительность исходного ключа/окна повтора. Флаг не продлевает хранение результата и не восстанавливает истёкшую или удалённую запись: общий срок ключа — 24 часа, у обновления токенов 1.4 — 60 секунд. Блокировка OFF_TOPIC может длиться до 7 суток, поэтому ожидание `retry_at` может выйти за окно ключа. Даже ранее полученное `true` не разрешает отправку за пределами этого окна. Клиент не создаёт свежий ключ автоматически вместо истёкшего ради повтора: новое логическое действие требует отдельного намерения пользователя. В частности, повтор использованного refresh-токена после 60 секунд может отозвать цепочку сессии по правилам 1.4; нужен предусмотренный восстановительный сценарий, а не слепая отправка.
- Сервис/usecase задаёт permission повторить исходный RPC в optional typed detail `common.v1.RequestRetryInfo`; общий helper не выбирает его по business-коду. BFF соединяет применимое service-owned permission с доказанной безопасностью **всего** REST-запроса по его контракту, включая уже выполненные действия других RPC. Отсутствующая, некорректная или дублированная распознанная деталь, непроверенная связь с исходным запросом или недоказанная safety дают `false` у нового BFF; отсутствие внешнего поля служит совместимости со старым сервером. Собственные транспортные отказы BFF получают permission из соответствующего обработчика, а не из каталога UI. BFF не принимает бизнес-решение о повторе переключателем по имени причины. Наличие UUID в `Idempotency-Key` не доказывает возраст или действительность записи. Для POST, безопасность которого зависит от ключа, BFF не выдаёт `true`, если срок допустимого повтора выходит за установленное окно или достоверного подтверждения безопасности нет. Ни любой `429`, ни любой `5xx`, ни голый gRPC `UNAVAILABLE`/`DEADLINE_EXCEEDED` не означают `true`: отказ транспорта может прийти уже после эффекта. Для `REQUEST_IN_PROGRESS` повтор с тем же активным ключом по `Retry-After` допустим только при сохранённых условиях метода и подтверждённом окне; сам код не снимает эти условия.
- Если флага нет либо пришли `null` или значение не boolean, **нового разрешения нет**; сохраняется прежнее известное безопасное поведение метода, кода и сценария. Поле разбирается независимо: ошибка в нём не уничтожает `code`, пользовательский текст, `retry_at` и другие корректные данные. Неизвестный код с безопасным текстом отображается по общим правилам, но текст и `severity` не дают права повторить запрос. При сетевом сбое тело ошибки может вообще не прийти: клиент обязан знать правила повтора и идемпотентности вызываемого метода и не ждать от флага универсального разрешения на сетевые повторы.

Пример разрешённого безопасного повтора: существующий `GET /v1/auth/phone/events` получил HTTP 429 **до начала SSE**. Повторное чтение безопасно; при установленном разрешении после ограничения BFF может вернуть такой ответ и `Retry-After`:

```json
{"error":{"code":"RATE_LIMITED","message":"Rate limited","user_message":"Слишком много попыток. Попробуйте позже.","severity":"warning","retryable":true,"retry_at":"2026-10-25T20:00:00+03:00"}}
```

Повтор выполняется не раньше указанного времени и с соблюдением остальных условий 1.2. Это иллюстрация решения для конкретного чтения при service-owned permission (либо permission собственного транспортного обработчика BFF), не правило «все 429 можно повторять».

Пример разделения гарантий: `GET` с неверным параметром запроса получает `VALIDATION_ERROR`. Повторное чтение само по себе безопасно, но тот же неверный запрос нужно исправить, а не повторять напрямую:

```json
{"error":{"code":"VALIDATION_ERROR","message":"Request validation failed","user_message":"Проверьте параметры запроса.","severity":"warning","retryable":false,"details":[{"field":"date","code":"INVALID_FORMAT","message":"Invalid date"}]}}
```

Аналогично, `WRONG_BANK` при загрузке требует другой файл; это исправленное тело и новое действие с новым `Idempotency-Key`, а не разрешённый повтор исходной загрузки. Сохранённый `400`/`413`/`422` с прежними ключом и телом может снова воспроизвести ту же ошибку — идемпотентность не делает такой повтор полезным или разрешённым.

**Прежний `retryable` помощника — другой объект и действие.** В терминальном SSE `error` 7.2 и сообщении истории `failed` 7.3 он по-прежнему разрешает `RetryAnswer` (7.4): новую генерацию с новым логическим POST и новым ключом. Он не обещает безопасность повторной отправки исходного `AskQuestion`. Новый `error.retryable` относится только к общему REST-объекту `Error`; одноимённые SSE/история сохраняют FIN-159. Общий SSE и импорт не получают новый флаг в FIN-224, прежнее предложение ручного повтора `ErrorEvent` (алиас `SseError`) остаётся отдельным правилом.

Это контракт планируемого внедрения; реализация BFF — FIN-225, клиента и fake — FIN-223. Политика OFF_TOPIC (FIN-222/FIN-161), HTTP/gRPC-статусы и реестр `error_spec` не меняются.

### Размер JSON-запроса (FIN-339)

Транспортный бюджет относится только к шести операциям: `POST /v1/auth/phone` (1.1), `POST /v1/auth/register` (1.3), `POST /v1/auth/token` (1.4), `POST /v1/auth/logout` (1.5), `PUT /v1/profile/assistant-consent` (2.3), `POST /v1/assistant/messages` (7.1). BFF принимает тело размером **до 65 536 байт включительно**; развёртывание может установить больший предел, но не меньший. Считаются байты UTF-8 переданного JSON целиком, включая пробелы и escape-последовательности, а не число символов полей. Лимиты полей по схеме действуют независимо. В OpenAPI `x-min-request-body-bytes: 65536` отмечает минимально поддерживаемый транспортный бюджет, а не максимальную длину строки или фактический предел развёртывания.

Тело сверх фактического предела — HTTP 413 `REQUEST_TOO_LARGE`, с обычным `ErrorResponse` и `retryable: false`: неизменённый запрос повторять бессмысленно. Код генерирует только BFF; он не входит в gRPC `ErrorReason` и не меняет файловый `FILE_TOO_LARGE`. Клиент показывает безопасный `user_message` по общим правилам, без нового специального действия или локального каталога. Исправление тела — новое логическое действие, а не автоматический повтор; у операций с `Idempotency-Key` ему соответствует новый ключ.

У этих шести операций `Content-Encoding` отсутствует либо содержит единственный токен `identity` (без учёта регистра). Любое другое значение, включая сжатие `gzip`/`br`, список или несколько заголовков `Content-Encoding`, — HTTP 400 `VALIDATION_ERROR` после приоритетных проверок техработ/версии/авторизации, но до чтения тела/проверки его размера, распаковки и вызова сервиса. Пробельное оформление HTTP-заголовка (OWS) нормализует HTTP-парсер; пустое значение не равно отсутствию. BFF не распаковывает запрос, и инфраструктура перед ним не должна скрыто распаковывать его: считаемые wire-байты совпадают с байтами JSON. Нового 415 или кода ошибки нет.

После более приоритетных проверок техработ, версии и заголовка авторизации BFF проверяет размер по `Content-Length`, если он известен, и ограничивает фактическое чтение потока независимо от заголовка. При превышении прекращает чтение и отвечает 413 **до вызова сервиса и проверки/резервирования ключа идемпотентности**; этот отказ под ключом не сохраняется. Отсутствие `Content-Length` не обходит ограничение.

Остальные восемь операций текущего HTTP-набора FIN-268 не принимают тело: `GET /v1/auth/phone/events`, `GET /v1/consents/{type}`, `GET /v1/profile`, `DELETE /v1/profile/assistant-consent`, `GET /v1/assistant/messages`, `GET /v1/assistant/messages/{answer_id}/events`, `POST /v1/assistant/messages/{answer_id}/retry`, `GET /v1/assistant/limit`. У них принимается фактическое тело длиной **0 байт**: в том числе `Content-Length: 0`, пустой chunked-поток, `Content-Type: application/json` без байтов или отсутствие этого заголовка. Заголовки сами по себе не доказывают наличие тела. Любое тело длиной **от 1 байта**, включая `{}` и пробельный символ, — HTTP 400 `VALIDATION_ERROR`, без нового 413. Для обнаружения достаточно ограниченного чтения одного байта; весь поток в память не читают. Это явное правило BFF, а не обещание kin-openapi отклонить тело без `requestBody`.

У всех прочих операций с телом сохраняются прежние проверки `Content-Length` и ограниченное чтение до валидации/вызова сервиса, включая существующий 413 при превышении транспортного предела. Для остальных JSON-операций конкретный код и байтовый бюджет такого отказа контракт пока не определяет; их последующее согласование относится к FIN-225 и не расширяет реализацию FIN-268. FIN-339 не распространяет на них `REQUEST_TOO_LARGE`/минимум 65 536 байт; отдельно описанный файловый лимит и код 3.2 сохраняются. Зависимая реализация этих уточнений — FIN-268; Android FIN-223 уже обрабатывает неизвестный код по общему fallback, отдельное новое действие клиента не требуется.

Ошибки разных классов не смешиваются: сервер проверяет их по порядку и возвращает первую — `503` (`MAINTENANCE`) → `400` `CLIENT_VERSION_UNSUPPORTED` → `401` (заголовок `Authorization`) → `400` / `413` проверки `bank-bff` (нет `Idempotency-Key`, тело не по схеме, `Content-Length` больше лимита и ограниченное чтение тела; у шести JSON-операций — по «Размеру JSON-запроса») → ключ идемпотентности (сохранённый ответ, `409` или возобновление долговечной попытки 1.1) → `429` → `401` (токены запроса, которые проверяет сервис) → `400` (проверки сервиса) → `404` → `403` (согласие, лимит) → `413` / `422`. У 3.2 `413` `FILE_TOO_LARGE` сервиса — до ключа идемпотентности: сервис отвечает им, не дочитав файл, и под ключом его не сохраняет; остальные ответы 3.2 сверяют ключ в конце потока, по хешу содержимого и имени файла («Идемпотентность»). Техработы и версия клиента проверяются первыми: устаревший клиент с просроченным токеном получает требование обновиться, а не экран входа. Первый шаг `401` — только проверка заголовка `Authorization` (её делает `bank-bff`); у эндпоинтов без него этого шага нет. Второй шаг `401` — токены запроса, которые проверяет сервис: `registration_token` (1.3) и `refresh_token` (1.4) в теле, `X-Verification-Token` (1.2) в заголовке. Он идёт после ключа идемпотентности — иначе повтор после обрыва получил бы `401` вместо сохранённого ответа (его отдаёт шаг ключа), а в 1.4 ещё и отозвал бы цепочку сессии, — и после `429`: иначе запрос с неверным токеном никогда не упирался бы в лимит, и подбор токенов ничем не ограничивался бы. У 1.2 ключа идемпотентности нет, поэтому для него этот шаг идёт сразу после проверок `bank-bff` и лимитов. Цена: клиент, попавший в лимит с отозванным или просроченным токеном, сначала получит `429` и только после паузы — `401`. Пример: новый запрос 1.3 с просроченным `registration_token` и `pd_consent_accepted: false` получает 401 `TOKEN_EXPIRED`, а не `CONSENT_REQUIRED`, — клиент начинает вход заново, а не остаётся на экране согласия. Проверки `bank-bff` идут до ключа, потому что ключ хранит сервис («Идемпотентность»); повтор это не ломает: тело, не прошедшее схему, не может совпасть с сохранённым. Повтор с известным ключом и тем же телом получает сохранённый ответ (в 1.1 без окончательного ответа — продолжает существующую попытку по её состоянию до лимитов/занятости), тот же ключ с другим телом — 409 `IDEMPOTENCY_CONFLICT`, ещё выполняющийся — 409 `REQUEST_IN_PROGRESS`, без проверки лимитов; лимиты (`429`) и проверки состояния — только для неизвестного ключа.

Коды HTTP:
| Код | Когда |
|-----|-------|
| 400 | Невалидный запрос; версия клиента ниже минимальной (`CLIENT_VERSION_UNSUPPORTED`) |
| 401 | Нет/невалидный/просроченный токен |
| 403 | Нет согласия, лимит исчерпан |
| 404 | Ресурс не найден |
| 409 | Конфликт по `Idempotency-Key`: другое тело или первый запрос ещё выполняется |
| 413 | Превышен транспортный предел тела; у шести JSON-операций FIN-339 — `REQUEST_TOO_LARGE`, у остальных JSON-операций код/бюджет пока не определены (последующее согласование FIN-225); файл > 10 МБ в 3.2 — `FILE_TOO_LARGE` |
| 422 | Запрос понят, но выполнить нельзя (не тот формат или банк, категорию нельзя назначить, повтор недоступен) |
| 429 | Rate limit |
| 500 | Внутренняя ошибка |
| 503 | Техработы (`MAINTENANCE`) |

### SSE

Для REST-отказов до начала потока и при его переоткрытии действует приоритет `error.retryable` из «Повтора REST-запроса»: корректный `false` останавливает прямой повтор/автоматическое переоткрытие в неизменённом контексте, `true` сохраняет все условия времени и сценария; отсутствие или некорректное значение сохраняет прежний безопасный алгоритм ниже. Отдельное восстановление после успешного auth-flow или в известном сценарии `MAINTENANCE` подчиняется правилам того же раздела. Это не меняет обработку обрыва без тела ошибки и не относится к доменному `retryable` терминального события помощника.
- При подключении сервер первым событием отдаёт текущее состояние ресурса — целиком. Переподключение (обрыв сети, возврат приложения из фона) не теряет события: клиент просто открывает поток заново.
- После терминального события (успех или ошибка) сервер закрывает поток. Подключение к уже завершённому ресурсу отдаёт состояние и терминальное событие сразу. Поток, закрытый без терминального события, — обрыв: клиент переоткрывает его, как после обрыва сети. Переоткрытие после обрыва — с паузой: базовая пауза d — 1 с, затем удвоение до 30 с; фактическая пауза — случайная в [0,5·d; d] (джиттер, чтобы клиенты после общего сбоя не переподключались одновременно); базовая пауза сбрасывается до 1 с, когда поток проработал без обрыва 30 с или пришло терминальное событие (одного `snapshot` мало: сбой сервера после снимка иначе дал бы цикл переподключений без пауз у всех клиентов сразу). Ответ 429 `RATE_LIMITED` на переоткрытие — пауза до `error.retry_at` (`Retry-After`) плюс случайная добавка в [0; 0,5·d] (d — текущая базовая пауза), чтобы клиенты с одним `retry_at` не переподключились одновременно; d при этом удваивается, как после обрыва.
- Сервер шлёт комментарий-heartbeat (`: ping`) каждые 15 с, чтобы прокси и мобильные сети не рвали простаивающее соединение.
- Ошибки до начала потока (400, 401, 404, 429, 503) — обычный HTTP-ответ с JSON-телом; после начала — терминальное событие `error` с полями `code`, `message` (как в `error` выше), и только для доменного исхода (разбор файла не удался 3.3, ответ помощника не получился 7.2). Сбой сервера или транспорта посреди потока — не событие `error`, а закрытие потока без терминального события (обрыв, правило выше): клиент переоткрывает поток и первым событием получает текущее состояние ресурса. Открытый поток при начале техработ обрывается; переподключение получает 503 `MAINTENANCE`.
- Неизвестный тип события клиент игнорирует.
- Все SSE-эндпоинты требуют заголовков (`Authorization`, `X-Verification-Token`), поэтому браузерный `EventSource` не подходит: веб-клиент читает поток через `fetch` (Android — OkHttp SSE, iOS — `URLSession` bytes).

### Расширяемость
Наборы метрик, характеристик и других данных растут вместе с сервисом; это не должно засорять контракт устаревшими методами и полями (решение 13.10.2026, Confluence «Архитектура» → «Расширяемость API»).

- Новые необязательные поля в ответах — обратно совместимы; клиент игнорирует неизвестные.
- Новые значения `code` — обратно совместимы; клиент обрабатывает неизвестные по правилу поля. Новые значения `enum` — breaking change.
- Новые необязательные параметры запроса — обратно совместимы.
- Удаление полей, переименование, смена типов, новое обязательное поле запроса — breaking change, новая версия API.
- Клиент терпим к неизвестному: неизвестные поля игнорирует, неизвестные коды обрабатывает по правилу поля, битый элемент списка пропускает, а не роняет весь ответ.
- Контроль breaking changes: oasdiff в CI.

**Удаление устаревшего.** `deprecated` — исключение, а не способ развития контракта: сначала — добавление (новое необязательное поле, новый код, новый элемент списка).
- Устаревшее поле или метод помечается `deprecated` вместе с выпуском замены: в OpenAPI `deprecated: true`, в proto `[deprecated = true]`. Каждый `deprecated` ссылается на задачу FIN с условием удаления.
- Удаляется, когда минимальная поддерживаемая версия клиента (`CLIENT_VERSION_UNSUPPORTED`, FIN-20) выше версии, где появилась замена, и метрики по `X-Client-Version` показывают ноль обращений к устаревшему .
- Версия `/v1` при этом не меняется; `/v2` — только для изменения, которое так провести нельзя.
- Пока продукт в альфе (не для широкого круга пользователей), несовместимые изменения допустимы без `deprecated`; принимает их владелец меткой PR `breaking-accepted` (oasdiff в CI тогда не падает).

## 1. Аутентификация `/v1/auth`

Сценарий: отдельное подтверждение 14+ → номер телефона и отдельное согласие на обработку ПДн → пользователь сам звонит на выданный номер подтверждения → для нового номера завершение регистрации → код-пароль на устройстве. Обе отметки по умолчанию сняты; возраст подтверждается до ввода/отправки телефона, согласие со ссылкой на полный актуальный документ — до отправки номера. Дата рождения и сведения о родителях не запрашиваются. До подтверждения номера API не сообщает, зарегистрирован ли номер: иначе перебором номеров можно узнать, кто пользуется приложением.

### 1.1 Начать верификацию телефона
```
POST /v1/auth/phone
Idempotency-Key: 7c1e4b2a-9f3d-4a8e-b6c5-1d0e2f3a4b5c
```
После успешного старта повтор с тем же ключом возвращает ту же заявку и не расходует лимит верификаций на номер — в том числе после `expires_at` (ответ хранится 24 часа, «Идемпотентность»). В сохранённом ответе хранится `expires_at`, а `expires_in` сервер пересчитывает в момент отправки повтора (после `expires_at` — `0`). Поэтому новая заявка после `expired` или после `expires_at` — новое действие и новый ключ.

На номер одновременно действует не больше одной заявки: провайдер не принимает повторную заявку на тот же номер, пока не истёк срок предыдущей (дубль), даже если по ней уже вошли.

- **Действующая заявка** — заявка, которая ещё не закрыта: `pending` до `expires_at` или `verified` с неиспользованным результатом до 15 минут с момента подтверждения звонком (решение 17.10.2026; срок результата отсчитывается от `verified`, а не от `expires_at`). Заявка, закрытая первым `/v1/auth/token` с выданным refresh или `/v1/auth/register` (1.2), действующей не считается: её результат больше не доставляется.
- **Известная локальная занятость номера** держится до сохранённого `known_busy_until` последней заявки (для Zvonok declared provider expiry + ε), отдельно от более раннего публичного `expires_at` и закрытия доставки результата. Пока номер занят, новая заявка на него не создаётся: и при чужой действующей заявке, и после успешного входа — тот, кто вышел и сразу входит снова, ждёт до сохранённого срока занятости; для Zvonok он учитывает фиксированный TTL 5 минут и допуск ε.
- **Результат прежней заявки:** новая заявка на номер (после его освобождения) неиспользованный результат `verified` прежней не отменяет — он доступен до своего срока (15 минут с подтверждения): новую заявку может создать не владелец номера, и иначе она отняла бы у владельца уже подтверждённый вход.
- **Порядок проверок:** сначала поиск по `Idempotency-Key`, включая долговечную попытку без окончательного ответа, — повтор с тем же ключом и тем же телом получает ту же заявку или продолжает попытку по её долговечному состоянию и правилам ниже; тот же ключ с другим телом — 409 `IDEMPOTENCY_CONFLICT`, а не `429` («Ошибки», порядок). Пока её обрабатывает другой исполнитель — 409 `REQUEST_IN_PROGRESS` с `Retry-After`. Известная попытка не проходит лимиты и проверку занятости заново, не списывает попытку повторно и не получает 429 против собственной резервации. Для неизвестного ключа — сначала лимиты верификаций на номер и на адрес, затем занятость номера. При превышенном лимите отказ — по лимиту: `retry_at` — срок лимита, занятость номера не проверяется и через `retry_at` не раскрывается.
- **Дубль известной заявки или локальной unknown-резервации**: запрос с новым ключом на занятый номер получает 429 `RATE_LIMITED`; сервер определяет занятость по своей БД и к провайдеру не обращается. `verification_token` чужой заявки не возвращается — его получил только тот, кто создал заявку, а отдать его по одному номеру телефона значило бы отдать токены входа любому, кто знает номер. Этот 429 сохраняется под ключом до своего `retry_at` («Идемпотентность»): повтор с тем же ключом до `retry_at` получает тот же ответ (тот же `retry_at`, `Retry-After` — от текущего момента) и занятость номера заново не проверяет — точный момент освобождения номера опросом тем же ключом не узнать. После `retry_at` новый пред-dispatch ключ выполняется заново; исходный dispatched ключ с terminal duplicate следует отдельному правилу ниже.
- **`retry_at` при дубле** — `known_busy_until` последней известной заявки на номер либо сохранённый unknown deadline для локальной резервации, округлённый вверх до целой минуты (секунды и доли — в ноль, плюс минута, если они не нулевые): `expires_at` 22:16:20 → `retry_at` 22:17:00, `expires_at` 22:17:00 → `retry_at` 22:17:00. Точный срок чужой заявки не раскрывается: по нему можно было бы узнать, когда владелец номера входит, и создать свою заявку ровно в момент истечения его заявки.
- **Отказ провайдера по дублю** (номер свободен по нашей БД, а провайдер заявку не принял) — не штатный путь, а рассогласование с провайдером: сервер пишет его в лог и метрику `finassist_phone_verification_provider_duplicate_total` и отвечает так же 429 `RATE_LIMITED` с `retry_at` = время запроса плюс срок заявки у провайдера (5 минут), округлённое вверх до целой минуты.
  Эта существующая метрика фиксирует внешнее рассогласование (bare provider duplicate/проверенный старый или чужой ID), без phone/IP/ID-меток; обычный DB-429 до обращения к провайдеру её не увеличивает.
- **Учёт в лимитах:** ответ 429 на дубль (известная заявка/unknown-резервация по БД или отказ провайдера) засчитывается как попытка в лимитах верификаций на номер и на `x-client-ip` — опрос номера сам упирается в лимит. Попытку списывает выполнение запроса, а не воспроизведение сохранённого ответа: до `retry_at` повтор с тем же ключом получает сохранённый 429 и ничего не списывает, после `retry_at` пред-dispatch ключ выполняется заново и учитывается как новая попытка; terminal dispatched ключ — исключение ниже без повторного эффекта — один ключ учитывается не больше одного раза на каждое окно до `retry_at`. 429 по лимиту не сохраняется и попытку не списывает: сетевой повтор после него лимит не расходует.
- **Полученный 429 и ключ клиента:** клиент ждёт retry_at по общим правилам времени. Для новой осознанной попытки Start после ожидания он генерирует новый Idempotency-Key; транспортный повтор при потерянном ответе до окончательного исхода сохраняет прежние ключ/тело. Не нужно угадывать, был ли отказ до или после dispatch: terminal C429 несёт явный service-owned RequestRetryInfo{retryable: false}, и RetryInfo/retry_at у него задаёт время нового действия, не разрешение авто-reconfirm старым ключом. Совместимость сервера позволяет pre-dispatch B/D исполнить прежний ключ после retry_at; это не меняет правило нового клиента для нового intent.
- **Срок на устройстве** (решение 17.10.2026; «Время ожидания и часы»): клиент получает длительность `expires_in` ответа 1.1 и уменьшает её по монотонно прошедшему времени с учётом сна. Подпись «до ЧЧ:ММ» остаётся местной: часы устройства в момент получения + оставшаяся длительность, в поясе устройства. `expires_at` — абсолютный срок сервера, не разность с часами телефона. Если `expires_in` нет, приблизительный UI-fallback — `expires_at − Date` из того же свежего ответа с последующим вычитанием elapsed time. Нет корректного свежего Date/монотонной базы — обновить состояние по существующему сценарию, до него без точного отсчёта; старую длительность не перезапускать. В событиях 1.2 срока нет: он берётся из ответа 1.1. Ниже «срок своей заявки» — этот срок на устройстве.
- **Клиент, новая заявка:** пока своя заявка действующая (`pending`, срок своей заявки не прошёл, или `verified` с неиспользованным результатом, не прошло 15 минут с получения `verified` по часам устройства), новую заявку на тот же номер клиент не создаёт: при `pending` ждёт звонка, при `verified` продолжает вход или регистрацию (1.3) по имеющемуся результату.
- **Клиент, номер подтверждения:** показывается, только пока своя заявка `pending` и срок своей заявки не прошёл, вместе со временем ожидания. Клиент убирает номер с экрана и не предлагает позвонить на него при `expired` (1.2), при наступлении срока своей заявки по таймеру устройства (поток в этот момент может быть закрыт — клиент переоткрывает 1.2, чтобы подтвердить статус: и событие `expired`, и 401 `INVALID_TOKEN` до начала потока означают конец заявки — клиент предлагает начать заново с новым ключом; если поток ответил `pending`, потому что часы клиента спешат, клиент возвращает номер на экран и ждёт по потоку) и при 429, полученном без своей действующей заявки: звонок на номер без своей действующей заявки может засчитаться чужой заявке на тот же номер.

Запрос:
```json
{
  "phone": "+79001234567",
  "pd_consent_accepted": true,
  "pd_consent_version": "2026-09-28",
  "age_confirmed": true
}
```
| Поле | Тип | Описание |
|---|---|---|
| `phone` | string | Номер в формате E.164, только российские номера (`+7` и 10 цифр). Неверный формат — `VALIDATION_ERROR` с `details: [{field: "phone", code: "INVALID_FORMAT"}]` (FIN-68) |
| `pd_consent_accepted` | bool | Отдельное согласие на обработку ПДн до передачи телефона провайдеру; `false` → 403 `CONSENT_REQUIRED` |
| `pd_consent_version` | string | Версия документа `personal_data` из 1.6: от 1 до 64 Unicode-символов, без `null`. Должна равняться текущей версии при первом принятии заявки; иначе 422 `CONSENT_OUTDATED` |
| `age_confirmed` | bool | Отдельное подтверждение «Мне исполнилось 14 лет»; `false` → 400 `VALIDATION_ERROR`, `details: [{field: "age_confirmed", code: "REQUIRED"}]` |

Все четыре поля обязательны. Отсутствие, `null`, неверный тип или выход за структурные границы — 400 `VALIDATION_ERROR` до ключа на BFF. Прямой gRPC-вызов также проверяется сервисом: пустая/слишком длинная версия и `age_confirmed: false` — 400 на шаге проверок сервиса, `pd_consent_accepted: false` — 403, несовпадение непустой версии — 422. Проверки одинаковы для новых и существующих номеров и реального/фейкового провайдера.

#### Доказательство до внешней передачи (FIN-363)

После ключа сервис проверяет лимиты и занятость номера (429), затем формат/возраст (400), согласие (403), актуальность версии (422). При нескольких нарушениях действует общий порядок ошибок. Ни проверка состояния кнопки, ни заголовок версии клиента, ни прежнее согласие аккаунта не заменяют эти проверки. До их успеха номер не передаётся провайдеру.

До первого внешнего вызова в БД `user` надёжно фиксируются внутренний ID попытки, номер, ключ и хеш полного запроса, тип и точная версия документа, `pd_consent_accepted: true`, `age_confirmed: true`, серверные UTC-моменты получения обоих подтверждений и проверенный `x-client-ip` от BFF (по общим правилам доверенных прокси). Клиентские часы и произвольный HTTP `X-Client-IP` доказательством не служат. Эти моменты — время первого успешного приёма подтверждений сервером, не время звонка и не время Register. Сохраняется доступ к неизменяемому тексту именно этой версии документа. Запись и резервирование попытки выполняются атомарно; провайдер вызывается после commit, вне транзакции. Ошибка записи/commit запрещает внешний вызов. До звонка это утверждения неустановленного заявителя, связанного с попыткой; они не доказывают владение номером и не записываются в аккаунт, найденный только по `phone`.

Долговечная попытка без окончательного ответа находится на шаге ключа, а не считается неизвестным ключом после 5xx. Локальный timeout неизвестного исхода задаётся серверным `PHONE_VERIFICATION_UNKNOWN_TIMEOUT` (целевое внедрение в FIN-364): default `5m`, проверяемый при старте диапазон `1s..5m`. Это duration Go, без hot reload и новых REST-полей; некорректная конфигурация запрещает запуск. При первоначальном успешном приёме сервер один раз сохраняет абсолютный deadline = время приёма + тогдашний timeout. Перезапуск с другим env, отметка, повтор, смена исполнителя или сверка этот deadline не пересчитывают и не продлевают. Это отдельная настройка неизвестного исхода: фиксированный внешний TTL провайдера 5 минут, `expires_at` известной заявки и 15 минут результата не становятся произвольными env-значениями. До первого внешнего вызова единственный исполнитель атомарно записывает долговечную отметку «внешний вызов мог начаться» неизменный `first_dispatch_at` в этой же транзакции и абсолютный `dispatch_not_after`, не позже этого локального срока. Только исполнитель, впервые записавший отметку, вправе сделать один первый вызов строго до этой границы, с дедлайном не позже неё. После границы отправлять не вправе и он. Повторные confirm/Start у провайдера, включая retry-middleware, запрещены навсегда; при существующей отметке разрешена только читающая сверка, даже при сбое между commit и фактической отправкой.

До сохранённого локального deadline неизвестный исход удерживает номер от других ключей в карантине. Новый ключ получает существующий 429 `RATE_LIMITED`-дубль без confirm: `retry_at` = сохранённый unknown deadline, округлённый вверх до целой минуты. Его кэширование до `retry_at`, пересчёт `Retry-After` и учёт phone/IP-попыток полностью следуют общим правилам дубля выше: до `retry_at` replay не списывает повторно, после него ключ выполняется заново; лимитный 429 проверяется до состояния и не списывает попытку. Известная попытка не списывает лимит повторно и не получает 429 против собственной резервации. При внутренней ошибке её продолжения до локального срока сервис может явно поставить `RequestRetryInfo{retryable: true}` только если доступен проверенный читающий путь сверки; без него — явно `false`. BFF соединяет permission с доказанной safety всего запроса. Разрешение относится к тому же запросу/ключу: без отметки возможен один первый вызов до границы отправки, после отметки — только сверка, без нового confirm/списания/продления TTL. «Не найдено» при существующей отметке не означает определённого отказа: запрос мог ещё не дойти или не появиться в чтении. Определённый отказ — проверенный окончательный ответ самого первого вызова, гарантирующий отсутствие созданной заявки (кроме provider duplicate); он закрывает попытку и освобождает номер раньше срока, а тот же ключ получает `INTERNAL_ERROR` с явным `false`.

Если к моменту локального срока внешний исход так и не установлен, рабочая попытка атомарно закрывается как неудачная, карантин/phone-fence освобождаются и разрешается новая независимая заявка. Владелец выбрал освобождение по сохранённому локальному deadline (default 5 минут с первоначального приёма), принимая риск позднего принятия прежнего запроса, ещё действующей внешней заявки и дубля (решение 28.10.2026). Это осознанное исключение из ожидания доказанного внешнего исхода: HTTP timeout не доказывает отсутствие позднего принятия, а закрытие у нас не отменяет заявку у провайдера. Глобального provider-off и требования гарантии верхней границы Zvonok до обычного создания нет. Если исход уже авторитетно установлен и сохранён, применяются обычные срок известной заявки и 15 минут доступности результата `verified`; неизвестная попытка не используется, чтобы отнять подтверждённый результат.

Закрытие по unknown deadline не удаляет защиту старого ключа. Закрытое состояние, хеш полного запроса и связь с исходным доказательством сохраняются отдельно от активной заявки как минимум до окончания обычного 24-часового окна ключа, в пределах срока хранения доказательства ниже. Тот же ключ/тело получает `INTERNAL_ERROR` с `RequestRetryInfo{retryable: false}`/REST `error.retryable: false`, другое тело — `IDEMPOTENCY_CONFLICT`; никакого нового confirm, восстановления pending, новых времён согласия или повторного списания нет. Это долговечный терминальный учёт исходной unknown-попытки, не кэш 5xx-ответа. Отказавшийся новому ключу 429-дубль отдельно следует своему правилу хранения до retry_at и последующего выполнения заново. В обычном окне старого ключа новое действие требует нового ключа и создаёт независимую попытку со всеми проверками и собственным доказательством. Для исходной unknown-попытки replay/конфликт/учёт действуют только 24 часа с первого приёма ключа, не до unknown deadline + 24 часа. Архив может физически жить до удаления доказательства, но не продлевает lookup/replay-окно. После истечения обычного окна тот же UUID по общему правилу трактуется как fresh-запрос со всеми проверками и новой попыткой; это не восстановление архивной заявки и не разрешение клиенту повторять истёкшее действие автоматически.

Поздний webhook, сверка или завершение прежнего исполнителя не открывают закрытую попытку, не восстанавливают старые verification/registration token, не выдают пару токенов и не переносят старое подтверждение новой заявке. Персональное восстановительное задание этой рабочей попытки прекращается при закрытии; сохранённый архив не даёт права возобновлять внешний эффект. Операционную строку можно физически удалить лишь сохранив необходимое отдельное доказательство и терминальный учёт ключа; активный phone-fence после локального срока не удерживается. Другой действующий аккаунт/независимая заявка не удаляются, очистка сериализуется с их созданием и с привязкой доказательства к подтверждённому аккаунту. Уже списанные попытки не компенсируются, общие rate-limit окна живут по своим правилам и срокам.

Zvonok confirm может вернуть прежний ID незавершённого вызова. Доверенные поля — `created`, `call_id`, `phone`, `call_status`/legacy `status`, `completed` и пул из аутентифицированного ответа. Идентичность `(provider, настроенная campaign, call_id)` атомарно уникальна между рабочими заявками и сохраняемыми архивами. Campaign определяется доверенным запросом к настроенной кампании/проверенным binding, не клиентом или отсутствующим полем ответа. ID другого binding не перепривязывается; дальнейшая обработка различает доказанно активный вызов, terminal и недоверенный ответ по правилам ниже.

Для ещё не связанного ID новой попытки C проверяются same phone/campaign и `provider.created` в интервале `[C.first_dispatch_at.Truncate(1ms) − ε, получение первого authenticated confirm-ответа + ε]`. Для Zvonok `ε = ClockSkewTolerance = 1s` — конечная константа адаптера FIN-364, не новый env; 1 ms — точность timestamp, а не обещание нулевого расхождения часов. При читающей сверке после потери ответа верхняя граница — получение этого authenticated чтения + ε, пока C ещё открыта и её unknown deadline не наступил. За пределами допуска нет произвольного расширения/подстановки локального времени. До первого binding требуются pending `new`/`wait`/`in_process`, `completed` null/zero, не `pincode_ok`/terminal и валидный пул 1–1000 distinct E.164. Наличие closed unknown архива само по себе не создаёт C ошибку или новый карантин; неразличимый late A внутри расширенного интервала остаётся принятым поздним риском без наследования terminal-результата.

Сроки фиксируются один раз вместе с авторитетным `provider.created`: `declared_provider_expiry = created + 5 минут` (внешний TTL), наш публичный/проверочный `expires_at = declared_provider_expiry − ε` и внутренний `known_busy_until = declared_provider_expiry + ε`. Публичный deadline консервативен при расхождении часов в пределах ε; он не выдаёт provider TTL за время от C/sent/recovery. Подтверждение нашей заявки ограничено публичным deadline, занятость известной внешней — отдельным latest-known-busy deadline. Повтор ID/replay/перезапуск не пересчитывают эти сроки. На commit строго `public_deadline − now > 0` как Duration, без неназванного минимального порога; `expires_in = floor(max(0, public_deadline − now))` может быть 0 при положительном остатке меньше секунды. Локальный/fake адаптер без внешнего clock skew может использовать ε=0 при тех же бизнес-проверках/инвариантах; сценарий получает проверенные сроки через интерфейс, без ветвления по имени провайдера.

При принятии результата атомарно повторно проверяются все условия, уникальный ID/binding, C open, `now < unknown_deadline` и положительный публичный остаток; одного ожидания cleanup job недостаточно. `created` до нижней границы означает старый вызов, после верхней/противоречивые поля/непроверяемое время — безопасную внутреннюю ошибку без binding/proof. Для уже связанного с C ID не наследуется новый `created`/TTL; дальнейшее подтверждение — только authenticated проверка текущего binding. Наблюдаются расстояния `created` за локальным интервалом dispatch/recv и RTT, а не вычисленный из latency «точный clock offset»: ограниченные метрики и агрегированная диагностика без phone/IP/user/call/campaign ID, raw payload и персональных меток.

Если единственный confirm исходной C с dispatch-marker вернул проверенный старый/чужой либо уже непригодный по публичному остатку ID, отдельно проверяется реальная занятость: только валидированный same-phone/campaign NONTERMINAL вызов и `known_busy_until > now` создают/обновляют локальный known-busy факт номера до этого срока. Это не ownership/binding чужого ID и не его подтверждение. C закрывается терминально; `retry_at = ceilMinute(known_busy_until)` строго в будущем, C получает 429 `RATE_LIMITED` с явным `RequestRetryInfo{retryable: false}`/REST `error.retryable: false` до него, сохранённый 429 сохраняет этот false и повторяется со свежим `Retry-After`. RetryInfo/retry_at указывает время новой независимой попытки, не успех старого ключа. После `retry_at` и до конца обычного 24-часового окна исходный ключ C получает terminal `INTERNAL_ERROR` с `retryable: false`, без нового confirm/доказательства/списания. Новые B/D до known-busy срока получают DB-429 без HTTP; их пред-dispatch 429 по обычному правилу допускает выполнение заново после `retry_at`. Это исключение для исходного dispatched C из общего правила повторного исполнения дубля после `retry_at`.

Проверенный terminal/`pincode_ok` либо вызов с `known_busy_until <= now` не создаёт fake busy только из `created + 5 минут`: C закрывается с terminal `INTERNAL_ERROR`/`retryable: false`, без 429 с прошедшим сроком и без такого fence. Недоверенный/malformed ответ не создаёт срок занятости из payload и следует обычному unknown recovery/deadline пути. Bare provider duplicate без валидного `created` использует прежний конечный fallback по правилу отказа провайдера, но 429 выдаётся только при строго будущем retry_at; иначе terminal false без fake fence; исходный dispatched ключ при этом также терминален и не выполняет confirm заново после кэша 429. Нынешний Recover повторяет confirm и заменяется в FIN-364 действительно читающим путём.

Поздний первоначальный исполнитель A с сохранённым причинным контекстом может записать только наблюдение ID/created/declared expiry и проверенных границ public/busy в ещё существующий архив A, без открытия заявки, авторизации и продления retention. Проверка уникальности атомарна: ID, уже связанный с C, не отнимается и не перепривязывается. Static webhook содержит ID вызова, но не ID нашей попытки: по одному телефону/наличию архива запрещено угадывать A. Webhook обновляет архив только после authenticated `call_by_id` и при уже существующей однозначной связи; иначе обрабатывается как неизвестный вызов/игнорируется, без создания связи. Архивирование наблюдения не является условием нового входа, не создаёт активный phone-fence/новый карантин и после удаления архива не воссоздаёт персональную запись.

Доказательство и времена первоначального приёма переживают ошибку провайдера, истечение/закрытие рабочей заявки и TTL её временных ресурсов. Для брошенной регистрации без созданного аккаунта и без связи с подтверждённым существующим аккаунтом доказательство хранится отдельно 24 часа после окончания срока заявки (решение владельца 28.10.2026). Если внешний срок так и не установлен, опора — первоначально закреплённый unknown deadline (приём + тогдашний PHONE_VERIFICATION_UNKNOWN_TIMEOUT), затем ещё 24 часа; ни сверки, ни закрытие/освобождение номера эту опору не продлевают. До конца этого срока допустимы отдельные архивные evidence/терминальные key records без активного phone-fence и восстановления рабочих запросов. Для доказательства, связанного с подтверждённым аккаунтом, прежний срок по п. 3.3 Политики сохраняется: 3 года после удаления аккаунта/отзыва, отдельно от данных аккаунта и с отдельными правами доступа.

По окончании срока хранения брошенного доказательства удаляются относящиеся к нему персональные записи и производные: phone/IP, evidence и связь с попыткой, request_hash/key/resource binding, token hashes/result ciphertext, персональные параметры фоновых заданий и связи отказов других ключей с этим карантином. Ресурсы 429 новых ключей очищаются по их короткому правилу до retry_at и не продлевают retention старого доказательства; если такой ключ позже создал независимую заявку, её новые ресурсы не удаляются при очистке прежнего архива. Каскад удаления рабочей заявки по unknown deadline не должен удалить архив, а архив не должен продлевать активную блокировку. Очистка не удаляет данные другого live account/attempt, сериализуется с привязкой доказательства к аккаунту и не возвращает квоту. Удаление архивов не разрешает восстановить старые результаты или подтвердить старую заявку. Контракт задаёт требования к FIN-364, а не подтверждает их наличие в текущем коде.

Версия документа закреплена при первом принятии попытки: последующее обновление текущего документа не меняет доказательство и не прерывает эту заявку, доступность её результата (15 минут с `verified`) или Register. Новый ключ — новая попытка, которая проверяет текущую версию; исправление версии/подтверждений — новое действие с новым ключом. При `CONSENT_OUTDATED` в 1.1 клиент перечитывает 1.6, показывает новый документ и сбрасывает отметку согласия. Возврат назад не ставит отметки автоматически; отказ от новой попытки не отменяет уже полученное доказательство старой.

После подтверждения звонком существующий аккаунт получает связь с доказательством этой заявки до выдачи пары токенов; первоначальные согласия и их времена сохраняются отдельно, а повторная доставка `verified` не создаёт новых событий согласия. Новый аккаунт получает связь с тем же доказательством атомарно с созданием в Register; `registration_token` однозначно связан с заявкой. Ответ 1.1 и ошибки не раскрывают наличие аккаунта. Каждый отдельный принятый Start получает собственное доказательство с IP, даже при повторном входе и той же версии документа: это фиксация получения каждого согласия по п. 3.3 Политики, с фактическим временем перед отдельной передачей телефона. Для подтверждённого аккаунта сохраняется весь установленный срок; замена таких доказательств одной записью на версию или сокращённый срок для повторных входов не согласованы. Состав ограничен указанными выше данными согласия/возраста и связи с запросом; IP и события последующих Watch, RefreshTokens и иных обращений в доказательство не добавляются.

При внедрении задаётся серверный момент переключения. Заявки и результаты без обоих доказательств после него не могут вновь выдавать/доставлять токены или завершать регистрацию: Watch/Register отвечают 401 `INVALID_TOKEN`, клиент начинает вход заново. Старый сохранённый ответ 1.1 не становится обходом: его verification_token также недействителен. Для этой миграции установленная сессия — пара access/refresh, которую сервер выпустил и надёжно сохранил до переключения, независимо от первого RefreshTokens и закрытия заявки. Такой refresh не отзывается только из-за отсутствия нового доказательства у старой заявки; первый RefreshTokens работает по прежним правилам и закрывает результат. Если до переключения Watch уже доставил пару, но клиент ушёл в фон до RefreshTokens, эта пара сохраняется. Если пару сохранили, но не доставили, повторный Watch старой заявки её уже не отдаёт; само наличие такой пары не разрешает новую выдачу из старого результата. Старые registration_token без доказательства не создают аккаунт; успешно завершённый до переключения Register с сохранённой парой — установленная сессия. Старый клиент, не передающий новые обязательные поля 1.1, получает 400 (или общий `CLIENT_VERSION_UNSUPPORTED`, если ниже серверного минимума); сервер не подставляет подтверждения автоматически.

Ответ `200`:
```json
{
  "verification_token": "vt_9mQ2x7LpR4aZ8cN1kT6wY3eB5uH0jV2sD4fG7hK9lP1",
  "callback_number": "+74951234567",
  "expires_at": "2026-10-04T22:17:00+03:00",
  "expires_in": 300
}
```
В примере provider.created = 22:12:01, declared provider expiry = 22:17:01, ε=1s и публичный expires_at=22:17:00; ответ отправлен в 22:12:00 по часам сервера с остатком 300 секунд. Если часы устройства в момент получения ответа показывают 22:13:40, клиент показывает «до 22:18»; исходная местная оценка окончания — 22:18:40. Обратный отсчёт этих 300 секунд идёт по монотонному времени с учётом сна, поэтому последующий перевод часов телефона его не меняет.

| Поле | Тип | Описание |
|---|---|---|
| `verification_token` | string | Секрет заявки: 256 случайных бит, base64url. Клиент хранит его в памяти до окончания входа и передаёт только в заголовке `X-Verification-Token` (1.2) |
| `callback_number` | string | Номер подтверждения, на который пользователь звонит со своего телефона (E.164); клиент показывает его и передаёт в `ACTION_DIAL`. Звонок не бесплатный — оплачивается по тарифу абонента, поэтому клиент не обещает бесплатность. Номер может быть общим для многих пользователей и заявок: звонок засчитывается только с номера из заявки (`phone`) и только пока заявка действует. Не зашит в приложение: провайдер может выдавать номер под заявку, а при смене провайдера или переключении на запасного номер меняется без релиза |
| `expires_at` | datetime | Наш консервативный deadline подтверждения по часам сервера: для Zvonok provider.created + фиксированный TTL 5 минут − ClockSkewTolerance 1s. Это не внутренний latest-known-busy deadline (+ε); сроки хранятся отдельно. Клиент считает остаток по свежему expires_in, длительность не зашивает. После него — новая заявка с новым `Idempotency-Key` |
| `expires_in` | int? | Оставшийся срок заявки в секундах на момент отправки ответа (`expires_at` минус время сервера, округлено вниз, не меньше `0`). Сервер вычисляет его при каждой отправке, в том числе при повторе сохранённого ответа по `Idempotency-Key`. Клиент отсчитывает длительность монотонно, местная подпись — по «Сроку на устройстве». Нет — старый сервер, приблизительный fallback только через свежий `Date` того же ответа по разделу «Время ожидания и часы» |

Ошибки: `VALIDATION_ERROR` (400, структура запроса, формат номера или неподтверждённые 14+), `CONSENT_REQUIRED` (403), `CONSENT_OUTDATED` (422), `RATE_LIMITED` (429, с `error.retry_at`: превышен лимит верификаций на номер или адрес — `retry_at` по лимиту; либо известная заявка/локальная unknown-резервация занимает номер — `retry_at` по правилу дубля выше).

### 1.2 Статус верификации (SSE)
```
GET /v1/auth/phone/events
Accept: text/event-stream
X-Verification-Token: vt_9mQ2x7LpR4aZ8cN1kT6wY3eB5uH0jV2sD4fG7hK9lP1
```
Клиент открывает поток после `ACTION_DIAL` и переоткрывает при возврате приложения из фона. Первое событие — текущий статус.

Ожидание:
```
event: status
data: {"status": "pending"}
```

Подтверждён, существующий пользователь (терминальное):
```
event: status
data: {"status": "verified", "is_new_user": false, "access_token": "eyJ...", "refresh_token": "rt_..."}
```

Подтверждён, новый пользователь (терминальное):
```
event: status
data: {"status": "verified", "is_new_user": true, "registration_token": "reg_..."}
```

Истёк (терминальное):
```
event: status
data: {"status": "expired"}
```

Событие `status`:
| Поле | Тип | Описание |
|---|---|---|
| `status` | code | `pending` — звонка ещё не было; `verified` — номер подтверждён; `expired` — срок заявки истёк: клиент убирает номер подтверждения с экрана (1.1) и предлагает начать заново. Неизвестный статус — заявка не удалась, предложить начать заново |
| `is_new_user` | bool? | Только при `verified`: `true` — номера нет в системе, клиент завершает регистрацию вызовом 1.3; повторная отметка согласия не требуется |
| `access_token` | string? | Только при `verified` и `is_new_user: false` |
| `refresh_token` | string? | Только при `verified` и `is_new_user: false` |
| `registration_token` | string? | Только при `verified` и `is_new_user: true`; одноразовый, живёт 15 минут с момента подтверждения звонком (`verified`), а не до `expires_at` заявки. Таймер завершения регистрации клиент не показывает: срок с запасом |

Лимит: у эндпоинта серверный лимит запросов (попыток подключения) за окно на `x-client-ip`, как у 1.3 и 1.4 (значение задаёт сервер; в контракте не фиксируется). Считаются все попытки, включая отклонённые с 401: подбор токена открытых потоков не создаёт, поэтому ограничение одновременных потоков от него не защищает. Отдельный потолок одновременных потоков с адреса — на усмотрение сервера, к защите токена не относится. Сверх лимита — 429 `RATE_LIMITED` с `error.retry_at` до начала потока («SSE»), до проверки `X-Verification-Token` («Ошибки», порядок): подбор токена упирается в лимит. Корректный REST `error.retryable: false` останавливает автоматическое переоткрытие после этого отказа. При `true` клиент ждёт до `retry_at` и проверяет условия заявки; при отсутствующем или некорректном флаге сохраняется прежнее безопасное поведение. Своя заявка при ожидании не теряется, пока не прошёл её `expires_at`.

Эндпоинт открыт без `Authorization`, и при `verified` отдаёт токены: `verification_token` — единственное, что его защищает. Поэтому токен не попадает в URL (а значит, и в логи ingress) и сравнивается на сервере по хешу за постоянное время.

Повторная доставка: успешная запись в сокет не гарантирует, что клиент получил событие. Поэтому результат `verified` остаётся доступным 15 минут с момента подтверждения звонком (не до `expires_at` заявки), и переподключение с тем же `verification_token` отдаёт те же токены (или тот же `registration_token`). Заявка закрывается, как только клиент воспользовался результатом — первый `/v1/auth/token` с выданным refresh или `/v1/auth/register`; после этого, после 15 минут с подтверждения и для `pending` — после `expires_at` подключение возвращает 401 `INVALID_TOKEN`.

Сервер: обработчик находит заявку по хешу токена, читает статус из БД `user`, затем ждёт `LISTEN/NOTIFY` по внутреннему ID заявки — вебхук провайдера может прийти на любой под.

### 1.3 Регистрация (только новый пользователь)
```
POST /v1/auth/register
Idempotency-Key: 2b8d6f1e-3c4a-4e9b-8a7d-5f6e1c2b3a4d
```
Вызывается после подтверждения номера с исходными значениями согласия из 1.1, без повторного получения согласия. `registration_token` одноразовый: без ключа повтор после обрыва получил бы `INVALID_TOKEN`, и пользователю пришлось бы звонить заново. С ключом повтор возвращает тот же ответ `201`.

Запрос:
```json
{
  "registration_token": "reg_...",
  "pd_consent_accepted": true,
  "pd_consent_version": "2026-09-28",
  "timezone": "Europe/Moscow"
}
```
| Поле | Тип | Описание |
|---|---|---|
| `registration_token` | string | Из события `verified` (1.2) |
| `pd_consent_accepted` | bool | Подтверждает согласие, уже полученное в 1.1; `false` → `CONSENT_REQUIRED`. `true` не заменяет доказательство заявки и не меняет его время |
| `pd_consent_version` | string | Исходная версия из 1.1, от 1 до 64 Unicode-символов. Должна совпадать с доказательством заявки: несовпадение → `CONSENT_OUTDATED`. С текущей версией документа повторно не сравнивается; новая отметка и время не создаются |
| `timezone` | string? | Часовой пояс устройства (IANA); без поля — `Europe/Moscow`. При регистрации клиент отправляет пояс устройства сразу, без правила 72 часов из 2.2 |

Ответ `201`:
```json
{
  "access_token": "eyJ...",
  "refresh_token": "rt_...",
  "user_id": "01a107db-ae80-7b07-b8a1-a8c8486e2532"
}
```
| Поле | Тип | Описание |
|---|---|---|
| `access_token` | string | JWT, 15 мин |
| `refresh_token` | string | Для обновления токенов (1.4) |
| `user_id` | string | ID созданного пользователя |

Лимит: серверный лимит запросов на `x-client-ip` (значение задаёт сервер, в контракте не фиксируется) — проверяется до `registration_token` («Ошибки», порядок), подбор токена упирается в лимит.

Ошибки: `INVALID_TOKEN`, `TOKEN_EXPIRED` (401 — прошло больше 15 минут с подтверждения звонком; клиент начинает вход заново), `CONSENT_REQUIRED` (403), `CONSENT_OUTDATED` (422), `RATE_LIMITED` (429, с `error.retry_at`). `registration_token` расходуется только успешным ответом `201`: после ошибки 4xx его можно отправить снова (с новым ключом, если тело изменилось). При `CONSENT_OUTDATED` в 1.3 клиент восстанавливает исходную версию своей заявки, а не подставляет новый документ; если локальное состояние заявки потеряно, начинает 1.1 заново. Отсутствующее доказательство заявки нельзя заменить полями этого запроса: 401 `INVALID_TOKEN` до проверок согласия. Создание аккаунта, связь с исходным доказательством и расходование токена — одна транзакция.

Код-пароль и биометрия настраиваются на устройстве после получения токенов. Сервер про них не знает.

Лимит: серверный лимит запросов на `x-client-ip` (значение задаёт сервер, в контракте не фиксируется) — проверяется до `refresh_token` («Ошибки», порядок), подбор токена упирается в лимит.

## 2. Профиль `/v1/profile`

### 2.1 Получить профиль
```
GET /v1/profile
```
Ответ `200`:
```json
{
  "user_id": "01a107db-ae80-7b07-b8a1-a8c8486e2532",
  "phone": "+79161234567",
  "theme": "system",
  "timezone": "Europe/Moscow",
  "consents": [
    {"type": "assistant", "granted": false, "current_version": "2026-09-28"}
  ],
  "created_at": "2026-10-04T20:00:00+03:00"
}
```
| Поле | Тип | Описание |
|---|---|---|
| `user_id` | string | ID пользователя |
| `phone` | string | Номер полностью, E.164 — это логин пользователя, в профиле показывается целиком (решение a11y-14); форматирует клиент |
| `theme` | code | Тема: `system`, `light`, `dark`. Неизвестное значение — как `system` (новая тема не ломает разбор профиля у старого клиента) |
| `timezone` | string | Часовой пояс (IANA), в котором считаются месяцы и «сегодня» |
| `consents` | array | Согласия пользователя, по одному на тип; новый тип согласия — новый элемент, а не новое поле. Согласие на ПДн (1.3) сюда не входит: без него аккаунта нет |
| `consents[].type` | code | `assistant` — передача данных помощнику (Alice AI). Элемент с неизвестным типом клиент пропускает |
| `consents[].granted` | bool | Действует ли согласие |
| `consents[].version` | string? | Версия документа (1.6), на которую дано согласие |
| `consents[].current_version` | string | Текущая версия документа; если `version` старше — согласие нужно дать заново |

Нет элемента нужного типа — согласия нет (как `granted: false`); версию документа клиент берёт из 1.6.
| `created_at` | datetime | Дата регистрации |

### 2.2 Обновить настройки
```
PATCH /v1/profile
```
Запрос (любое подмножество полей):
```json
{
  "theme": "dark"
}
```
| Поле | Тип | Описание |
|---|---|---|
| `theme` | enum? | Новая тема: `system`, `light`, `dark` — закрытый набор в запросе; неизвестное сервер отклоняет 400. В ответе (2.1) `theme` — открытый код |
| `timezone` | string? | Новый часовой пояс (IANA). Клиент отправляет, когда новый пояс устройства держится 72 часа, — см. ниже |

Ответ `200`: обновлённый профиль (как в 2.1).

Смена `timezone` запускает фоновый пересчёт помесячной аналитики; пока он идёт, `/v1/analytics` отдаёт `state.recalculating: true`.

**Когда клиент отправляет `timezone`** (решение владельца 14.10.2026, FIN-91). Пояс телефона определяется автоматически и меняется в каждой поездке, а смена пояса профиля сдвигает границы месяцев и запускает пересчёт. Поэтому пояс профиля меняется, только если новый пояс устройства держится не меньше 72 часов: пересадки и поездки на выходные аналитику не трогают, переезд подхватывается через трое суток.
- Клиент запоминает пояс устройства, отличный от `profile.timezone`, и момент, когда впервые его увидел. Проверяет при старте приложения, возврате из фона, смене пояса в системе и входе.
- Тот же пояс держится 72 часа и больше — `PATCH /v1/profile {timezone}`. Устройство вернулось в пояс профиля раньше — запись сбрасывается; пояс снова сменился — отсчёт начинается заново.
- Если в профиле уже нужный пояс, запрос не отправляется. Ошибка запроса пользователю не показывается — повтор при следующей проверке.
- Порог — константа клиента. Сервер правило не проверяет и принимает `timezone` как есть.
- При регистрации (1.3) пояс устройства уходит сразу.

### 2.3 Дать согласие помощнику
```
PUT /v1/profile/assistant-consent
```
Только с экрана согласия после галочки (решение edit ux-1). Идемпотентно: повтор с той же версией ничего не меняет.

Запрос:
```json
{
  "version": "2026-09-28"
}
```
| Поле | Тип | Описание |
|---|---|---|
| `version` | string | Версия документа (1.6, `type=assistant`), который видел пользователь. Устаревшая → `CONSENT_OUTDATED` (422) |

Ответ `200`: профиль (как в 2.1), в `consents` — элемент `assistant` с `granted: true`. Сервер фиксирует версию и время.

### 2.4 Отозвать согласие помощнику
```
DELETE /v1/profile/assistant-consent
```
Переключатель «Передавать данные помощнику» в профиле, без диалога. Ответ: `204 No Content`; повтор — тоже `204`. История ответов остаётся.

### 2.5 Удалить аккаунт
```

```
Клиент подтверждает код-паролем/биометрией локально, затем вызывает.

Ответ: `204 No Content`. Сервер удаляет все данные во всех сервисах, включая файлы выписок. Повтор после успешного удаления (access-токен ещё жив) — тоже `204`.

## 3. Выписки `/v1/statements`

Файл выписки сохраняется в Yandex Object Storage — отдельный бакет без Object Lock (не бакет бэкапов), шифрование на стороне сервера, доступ только у роли поддержки. Нужен только поддержке — разобраться с непрочитанными строками по письму «Сообщить нам» (3.6); клиенту файл не отдаётся. Файл удаляется вместе с загрузкой (3.5) и аккаунтом (2.5); при неудачном или прерванном разборе — сразу. Содержимое непрочитанных строк в БД не хранится — только номер строки, дата, причина и, если прочитались, счёт (внутренний ID, не номер) и `FITID` — по ним строку закрывает более поздняя загрузка (3.6, «Закрытие строк»). В файле полные номера счетов и имена получателей переводов — это отражается в политике ПДн и модели угроз.

### 3.1 Конфигурация импорта

| `notices[].text` | string | Готовый текст ситуации. Известный `code` клиент оформляет сам (заголовок, иконка), неизвестный — показывает `text` |

Событие `error` (терминальное): `code`, `message`, необязательные `user_message` и `severity` — как в общем формате ошибок («Единое отображение ошибок», FIN-224). `message` — диагностический и не показывается. Импорт атомарный: при ошибке ни одна операция не сохранена, файл удаляется.
- `PROCESSING_FAILED` — не удалось разобрать файл, в том числе разбор не завершился за 3 минуты с начала (таймаут; так же завершается разбор, прерванный сбоем сервера — решение владельца 17.10.2026, FIN-159);
- `CANCELLED` — разбор прерван пользователем (3.5).

Неизвестный код показывается по корректному `user_message`; без него — как `PROCESSING_FAILED` («Не удалось разобрать файл»). У известного `CANCELLED` при отсутствующем или некорректном `user_message` сохраняются прежнее безопасное сообщение и поведение отмены пользователем, а не ошибка разбора. Например: `{"code":"PROCESSING_FAILED","message":"Import failed","user_message":"Не удалось разобрать файл","severity":"error"}`.

После ошибки (и после таймаута) итог загрузки сохраняется: переподключение к потоку 3.3 первым событием сразу отдаёт это `error` («SSE» — подключение к завершённому ресурсу), а в 3.4 загрузка не показывается. BFF формирует пользовательский текст и оформление заново по сохранённому коду и параметрам; отдельного объекта ошибки в истории загрузок нет.

### 3.5 Удалить загрузку или прервать разбор
```
DELETE /v1/statements/{upload_id}
```
- Загрузка в статусе `done`: удаляет операции, которых нет в других загрузках, и файл. Ручные правки категорий у оставшихся операций сохраняются. Пересчёт аналитики — асинхронно.
- Загрузка в статусе `processing` (диалог «Прервать разбор?»): разбор прерывается, ничего не сохраняется, поток 3.3 завершается событием `error` с кодом `CANCELLED`.

Ответ: `204 No Content`. Повтор для уже удалённой загрузки — тоже `204`; `404` — только если такой загрузки у пользователя никогда не было.

### 3.6 Непрочитанные строки
```
GET /v1/statements/unread-lines?upload_id=01a10812-9d00-77d9-8c3d-b350e0119cd5
GET /v1/statements/unread-lines?from=2026-09-01T00:00:00%2B03:00&to=2026-10-01T00:00:00%2B03:00
```
Шторка «Непрочитанные строки» — из итога импорта (по загрузке) и с «Аналитики» («5 строк за сентябрь не прочитали», по периоду).

Непрочитанной строку делает только то, без чего операцию нельзя учесть: сумма, дата, целостность строки. Отсутствие описания операцию не блокирует (FIN-67): она принимается с пустым `title`, клиент показывает категорию банка или «Без описания»; в правиле возврата такая операция по описанию не сопоставляется.

Возвращаются только незакрытые строки — и по загрузке, и по периоду; закрытые строки дочитаны более поздней загрузкой или заменены её записью (см. «Закрытие строк» ниже). То же правило у счётчиков: `uploads[].unread_count` (3.4), `unread_lines_count` (6.1).

Параметры (нужен `upload_id` или пара `from`/`to`):
| Параметр | Тип | Описание |
|----------|-----|----------|
| `upload_id` | string? | Строки одной загрузки |
| `from`, `to` | datetime? | Строки, разобранная дата которых попадает в период; строки без даты сюда не попадают |

Ответ `200`:
```json
{
  "lines": [
    {
      "upload_id": "01a10812-9d00-77d9-8c3d-b350e0119cd5",
      "file_name": "operations_2026.ofx",
      "line_number": 412,
      "date": "2026-09-03T00:00:00+03:00",
      "reason": "bad_amount",
      "reason_name": "не распознали сумму"
    }
  ]
}
```
| Поле | Тип | Описание |
|---|---|---|
| `lines` | array | Непрочитанные строки по порядку в файле |
| `lines[].upload_id`, `lines[].file_name` | string | Загрузка и файл |
| `lines[].line_number` | int | Номер строки в файле |
| `lines[].date` | datetime? | Дата операции, если её удалось прочитать |
| `lines[].reason` | code | Причина: `bad_amount` — не распознали сумму, `bad_date` — дата не разбирается, `no_date` — даты нет, `truncated` — строка обрезана. Для статистики; показывается `reason_name` |
| `lines[].reason_name` | string | Причина для показа |

Содержимого строк (сумма, описание) в ответе нет — оно не хранится. Сервер хранит у строки номер, дату, причину и, если прочитались, счёт (внутренний ID счёта, не номер) и `FITID`; счёт известен из блока выписки счёта даже при битой сумме или дате. Счёт и `FITID` в ответ не попадают — они нужны только для закрытия.

**Закрытие строк (FIN-79).** Пользователь загружает исправленный файл или тот же файл после исправления разбора — строки, которые раньше не читались, проходят штатно. Старые непрочитанные строки при этом закрываются, иначе «Не прочитали N строк» висели бы и в истории, и на «Аналитике», хотя данные уже полные. Закрытие — в транзакции успешного импорта новой загрузки; строка не удаляется (поддержке видна история), а получает ссылку на закрывшую загрузку и исход: **дочитана** или **заменена**. Новая загрузка закрывает строку, если её выписка по тому же счёту покрывает строку:
1. **По `FITID`.** У строки есть счёт и `FITID`. В новой загрузке есть операция с этой парой — новая или повтор уже сохранённой — строка дочитана; операция, пришедшая с другой загрузкой, строку не закрывает; у новой загрузки строка с той же парой снова не читается — строка заменена.
2. **По дате, если `FITID` не дошёл** (как правило, `truncated`). Период выписки по тому же счёту (`DTSTART`–`DTEND` из OFX, а не первая и последняя операция) покрывает день строки — сравниваются дни в поясе профиля, `DTEND` без времени покрывает свой день целиком. У новой загрузки нет непрочитанных строк по этому счёту за эту дату — строка дочитана; есть — заменена.
3. **Без даты и без `FITID`.** Новая выписка по тому же счёту покрывает весь период старой загрузки по этому счёту. Нет непрочитанных строк в этом периоде (включая строки без даты) — дочитана; есть — заменена.

Заменённая строка снова не прочиталась в новой выписке: актуальной остаётся запись новой загрузки, старая скрывается. Поэтому повторная загрузка того же битого файла не увеличивает счётчики. В `resolved_unread_count` (3.4) входят только дочитанные строки.

Правила сравнивают загрузки по `uploaded_at`: строку закрывает только более поздняя загрузка. Загрузки одного пользователя могут разбираться параллельно и завершаться не по порядку, поэтому при фиксации каждой загрузки закрытие проверяется в обе стороны: строки более ранних завершённых загрузок — против неё, её собственные строки — против уже завершённых более поздних. Из нескольких подходящих строку закрывает самая ранняя из более поздних загрузок; при равных `uploaded_at` более поздней считается загрузка с бо́льшим `upload_id`. Шаг закрытия при фиксации загрузки и при удалении сериализуется по пользователю (блокировка пользователя, например `SELECT … FOR UPDATE` или advisory-lock, до конца транзакции). Блокировку берут первым действием транзакции, до любых чтений, или выполняют шаг закрытия в `READ COMMITTED`: при `REPEATABLE READ` и выше снимок фиксируется первым запросом, и дождавшаяся блокировки транзакция не увидела бы коммит соседней. Иначе две одновременно фиксируемые загрузки не увидят друг друга и строка останется открытой. Так результат не зависит от порядка завершения и удалений. День строки и периода сравнивается в поясе профиля на момент проверки; смена пояса (2.2) закрытия сама не пересматривает — они проверяются заново при следующем импорте или удалении, уже в новом поясе.

Удаление загрузки (3.5) удаляет её строки, закрытые и незакрытые. Строки других загрузок, которые она закрыла, проверяются заново по тем же правилам среди оставшихся загрузок (в той же транзакции): не закрыла ни одна — строка снова открыта. Иначе удалённая выписка оставила бы закрытой строку, операции которой больше нет. Поэтому после удаления у других, более ранних загрузок могут вырасти `unread_count` и упасть `resolved_unread_count`: клиент перезапрашивает список истории (3.4), а не только убирает удалённую запись.

Ошибки: `VALIDATION_ERROR` (400) — нет ни `upload_id`, ни пары `from`/`to`, или переданы оба; `NOT_FOUND` (404) — загрузки нет.

**«Сообщить нам»** — эндпоинта нет. Клиент открывает письмо в почтовом приложении пользователя (`mailto:` на адрес поддержки, как «Написать в поддержку» в профиле) с заполненными темой и телом: `user_id` (2.1), `upload_id`, `file_name`, номера строк и `reason` из этого ответа. Письмо уходит с почты пользователя — поддержка отвечает ему обычным письмом. По `upload_id` поддержка находит файл в хранилище.

Правила для поддержки: перед тем как открыть файл, сверить, что `upload_id` принадлежит `user_id` из письма; содержимое файла в ответах не пересылать — только исправить разбор и попросить загрузить выписку повторно (повторы пропускаются, недостающие операции добавятся). Если почтового приложения на телефоне нет, клиент показывает адрес поддержки и кнопку «Скопировать данные».

## 4. Операции `/v1/operations`

### Перевод между своими счетами
Пара найденных переводов между своими счетами (списание с одного счёта и зачисление на другой) показывается **одной записью** вида `own_transfer` с двумя счетами — как в макете «Перевод между счетами · 20 000 ₽». В аналитику пара не входит. Перевод, для которого пары не нашлось, — обычная операция с категорией «Между своими счетами» (пользователь отнёс её туда сам или вторая сторона в другом банке).

### 4.1 Список и поиск операций
```
GET /v1/operations
GET /v1/operations?before=2026-07-01T00:00:00%2B03:00
GET /v1/operations?q=самокат&from=2026-04-01T00:00:00%2B03:00&to=2026-10-01T00:00:00%2B03:00
```
Два режима:
- **Лента** («Операции») — без фильтров. Порции по 3 календарных месяца, новые первыми: первый запрос без параметров — три месяца, заканчивая месяцем самой новой операции (даже если выписка давно устарела; `docs/calc.md`, раздел 6); следующий — с `before` из `next_before` предыдущего ответа. Клиент календарь не вычисляет.
- **Поиск** — передан хотя бы один фильтр. Вся выборка одним ответом, без подгрузки (решение ux-17); клиент показывает её виртуализированным списком. Если период не задан, сервер ищет за последние 12 месяцев: старые совпадения обычно не нужны и засоряют результаты, а более старые данные читаются только по явному действию пользователя. Совпадения за пределами периода сервер не ищет и не считает. Если у пользователя вообще есть операции раньше периода (`has_older_data`, известно из сводки загрузок без поиска), клиент показывает под результатами ссылку «Искать за всё время» → тот же запрос с `all_time=true`. Чип периода в Поиске тоже предлагает «За всё время». Если выборка больше 10 000 операций — 422 `TOO_MANY_RESULTS`, клиент просит сузить период. Когда появятся данные других банков и история за годы, поиск перейдёт на подгрузку при прокрутке — новым необязательным параметром.

Параметры-фильтры (все необязательные; любой из них включает режим поиска):

| `all_time` | bool? | Искать за всё время, без периода по умолчанию. Вместе с `from`/`to` не передаётся (400) |

| `amount_from`, `amount_to` | int? | Сумма операции не меньше / не больше, копейки |

### 4.2 Детали операции
```
GET /v1/operations/{id}?occurred_at=2026-09-25T19:11:00%2B03:00
```
Параметры:
| Параметр | Тип | Описание |
|----------|-----|----------|
| `occurred_at` | datetime | Обязательный (FIN-202). Время совершения записи — значение `occurred_at` её записи из 4.1 как есть (у пары — время списания). Сервер ищет запись по точному совпадению момента `occurred_at` и `id` (это поиск среди операций одного года), сравнивается момент, а не строка: `2026-09-25T16:11:00Z` = `2026-09-25T19:11:00+03:00`. Сервер отдаёт `occurred_at` в 4.1–4.3 с той точностью, с какой хранит (доли секунды — только если они не нулевые), поэтому значение из 4.1, переданное как есть, совпадает; клиент его не округляет и не переформатирует |

- Параметра нет или он не в формате `datetime` — 400 `VALIDATION_ERROR`, нарушение у поля `occurred_at` (`REQUIRED` / `INVALID_FORMAT`).

- Записи с этим `id` у пользователя нет ни за какое время (загрузка удалена, пара разделена или собрана, чужой ID) — 404 `NOT_FOUND`.

| `source_name` | string | Название источника для отображения («Выписка Т-Банка») |

Необязательные поля приходят, только если источник их поставляет; клиент показывает строку на экране по наличию поля.

### 4.3 Сменить категорию
```
PATCH /v1/operations/{id}
```
Запрос:
```json
{
  "category_id": "cat_restaurants",
  "occurred_at": "2026-09-25T19:11:00+03:00"
}
```
| Поле | Тип | Описание |
|---|---|---|
| `category_id` | string | Новая категория из 5.1, допустимая для этой записи: `assignable`, и `kind` записи входит в `kinds` категории (для пары `own_transfer` — любая категория с `assignable`, см. правила ниже) |
| `occurred_at` | datetime | Обязательное (FIN-202). Время совершения записи — значение `occurred_at` её записи из 4.1 или 4.2 как есть (у пары — время списания). Запись ищется так же, как в 4.2: нет поля или не тот формат — 400 `VALIDATION_ERROR` у поля `occurred_at`; время не совпадает — не ошибка, сервер ищет запись по `id` за всё время; записи с этим `id` нет — 404 `NOT_FOUND` |

Ответ `200`:
```json
{
  "items": [
    {"id": "01a10812-a0e8-765b-89e4-a4314a43656f", "kind": "expense", "category_id": "cat_restaurants", "is_category_manual": true}
  ],
  "replaced_id": null
}
```
| Поле | Тип | Описание |
|---|---|---|
| `items` | array | Изменённые записи целиком, как в 4.2 (в примере сокращено) |
| `replaced_id` | string? | Есть, если запись с этим ID перестала существовать — клиент заменяет её на `items` |

Правила:
- Обычная операция: меняется её категория, `items` — одна запись.
- Пара `own_transfer`: смена на любую категорию, кроме «Между своими счетами», разделяет пару на две операции — пользователь сказал, что это не перевод себе. Выбранная категория назначается стороне, к которой она подходит (расходная — списанию, доходная — зачислению, подходящая к обеим — списанию); другая сторона получает категорию банка. `items` — две операции, `replaced_id` — ID пары.
- Операция с категорией «Между своими счетами», у которой нашлась вторая сторона, становится парой: `items` — пара, `replaced_id` — ID операции.

Ручная правка не перетирается при повторном импорте. Пересчёт аналитики за затронутый месяц — асинхронно.

Ошибки: `VALIDATION_ERROR` (400) и `NOT_FOUND` (404) — по `occurred_at` и `id`, как выше; `CATEGORY_NOT_ASSIGNABLE` (422) — категория не подходит к записи. Клиент перечитывает 5.1 и перестраивает выбор категории: справочник мог измениться на сервере (новая категория, смена `kinds`).

| `is_system` | bool | Системная категория («Между своими счетами», «Возврат», «Без категории») — группа «Системные» сверху в выборе категории |
| `kinds` | array<code> | К каким записям применима: `expense`, `income`; неизвестные значения клиент пропускает. Системные категории: «Между своими счетами» (`cat_own_transfer`, оба направления), «Возврат» (`cat_refund`, только доход), «Без категории» (`cat_uncategorized`, оба направления). «Без категории» получает операция, у которой в выписке категория банка пустая или буквально «Без категории» — это одна категория справочника, отдельной несистемной нет; в неё же идут возвраты, для которых не нашлась расходная категория (как цель возврата). Выбрать такому возврату цель вручную нельзя (решение 16.10.2026): в 4.3 зачислению доступны только категории с `income` в `kinds`, а ручная доходная категория делает его обычным доходом — он перестаёт уменьшать расходы. Исключение — ручной «Возврат» (`cat_refund`): запись остаётся возвратом, цель ищется по той же цепочке (`docs/calc.md`, 3.3) и снова оказывается «Без категории». Поэтому «разобрать» такой возврат — это либо оставить его в «Без категории», либо перевести в доход. Выбрать её вручную нельзя (`assignable: false`) — из неё категорию только убирают.

Направления категорий банка (`kinds`; от них зависят выбор категории и правило возврата: зачисление в расходной категории — возврат), FIN-126, подробно — [«Расчёт метрик и правила учёта»](https://finassist.atlassian.net/wiki/spaces/PF/pages/13991937), 3.1:
| Направление | Категории банка |
|---|---|
| только доход (`income`) | «Зарплата», «Пополнения», «Вклады», «Проценты», «Бонусы», «Дивиденды и купоны», «Другое» |
| оба (`expense`, `income`) | «Переводы», «Финансы», «Наличные», «Без категории» и любая новая категория банка, пока её не внесли в список известных |
| расходная (`expense`) | остальные известные («Супермаркеты», «Фастфуд», «Услуги банка» …) |

- Возврат: зачисление без ручной категории и вне пары — возврат, если его категория банка расходная, **или** раньше было списание с тем же непустым описанием, у которого категория банка — не «Переводы» (исключение относится к списанию: перевод от человека, которому раньше переводили, — не возврат; категория банка самого зачисления не важна), **или** в описании есть «возврат». Два последних признака действуют для любой категории, в том числе «оба» и «Без категории»: такое зачисление уменьшает итоговую категорию последнего более раннего списания с этим описанием и категорией банка не «Переводы» (по времени; дальше — цепочка выбора цели из `docs/calc.md`, 3.3), а в «Без категории» попадает, только если расходная категория не нашлась.
- Направление описывает выбор категории и правило возврата, а не то, какие операции бывают: списание в категории «только доход» («Другое», «Проценты») остаётся в ней и считается расходом этой категории.
- Список известных категорий банка и их направлений — `fixtures/calc/categories.json` (51 категория из выписки владельца, FIN-107; полного списка категорий Т-Банка нет — FIN-200; `docs/calc.md`, 3.1). Его знает сервер, клиент не знает и берёт `kinds` из 5.1. Когда категорию вносят в список (правка файла и выпуск сервиса; меняется её `kinds`), правила применяются заново ко всем операциям, как после импорта. В отличие от пересчёта после импорта, `state.recalculating` (6.1) при этом не ставится — это пересчёт после выпуска нового списка, снимки заменяются молча, по месяцам (FIN-196); клиент видит новый `kinds` после очередного перечитывания справочника. Число новых категорий банка не ограничено; название берётся из выписки и обрезается до 64 символов (решение 16.10.2026) — это и `name` в 5.1, и `bank_category` в 4.2. Категория определяется по обрезанному названию: две строки выписки с одинаковыми первыми 64 символами — одна категория справочника.

#### Блоки экрана

Что сервер собирает сейчас (MVP). Состав, порядок, подписи и тексты меняются на сервере без релиза клиента — таблица описывает текущую композицию, а не ограничение контракта.

| `id` | Тип | Содержимое и правила расчёта |
|---|---|---|
| `tiles` | `tile_group` | Четыре плитки. `balance` — «Доходы минус расходы», сумма со знаком, подпись — доля дохода («46% дохода · по выписке», «−12% · потратили больше, чем получили»; при нулевом доходе — «Доходов за период нет»). ### 6.2 Периоды с данными
```

```
Для шторки выбора периода (нажатие на название периода на «Аналитике»): все периоды, где есть хоть один день, покрытый выпиской (периодом `DTSTART..DTEND` хотя бы одной загрузки), — даже если операций в нём нет. ### 6.3 «Не подписка»
```
PUT /v1/analytics/regular-payments/{id}/dismissal
DELETE /v1/analytics/regular-payments/{id}/dismissal
```
`PUT` — пользователь отметил платёж как «Не подписка»: он исчезает из карточки, итог пересчитывается. `DELETE` — вернуть (в MVP в интерфейсе нет, нужен для поддержки и будущей отмены). Оба идемпотентны.

Ответ: `204 No Content`. Отметка привязана к платежу (его ключу — описанию операции из выписки), а не к периоду: при следующих загрузках платёж тоже не показывается. `id` платежа стабилен между пересчётами; это ID по общему правилу («Формат»: сейчас UUIDv7, соответствие ключа и `id` хранит сервер), а не само описание и не его кодирование: описание операции — персональные данные и в URL и логи не попадает. После отметки 6.1 отдаёт `state.recalculating: true`, пока итог карточки не пересчитан.

`{id}` — UUID в каноничной записи (строчные буквы); другой формат сервер отклоняет 400 `VALIDATION_ERROR`, не ища платёж: так в адрес не попадёт описание операции.

Ошибки: `VALIDATION_ERROR` (400) — `id` не UUID; `NOT_FOUND` (404).

## 7. Помощник `/v1/assistant`

Один непрерывный диалог. Вопрос создаётся `POST` (7.1), ответ генерируется на сервере независимо от соединения клиента и читается потоком (7.2). История — 7.3.

**Лимит:** 5 вопросов в сутки, сброс в 00:00 по Москве (решение edit ux-13; местное время клиент показывает в скобках). Попытка списывается при создании вопроса и возвращается, если ответа не получилось — любая ошибка ответа (событие `error` в 7.2, статус `failed` в 7.3; сейчас `MODEL_ERROR`, `CANNOT_ANSWER`, `OFF_TOPIC` — вопрос не по теме, решение 17.10.2026, FIN-159) — или если помощник ответил тем, что есть, и назвал, чего не хватает (решение states gpt-7) — тогда `charged: false`.

Возврат за неполный ответ решает **сервер по результатам функций, а не модель на словах**: попытка возвращается, если хотя бы одна функция, нужная для ответа, вернула блокировку («нужно 1 полный месяц, есть 0») или пустой охват за запрошенный период. Иначе вопрос можно сформулировать так, чтобы модель сама сослалась на нехватку данных, и получить ответ бесплатно.

**Отдельный лимит OFF_TOPIC** (решение владельца 23.10.2026, FIN-222): по умолчанию 5 терминальных исходов `OFF_TOPIC` за скользящие 7×24 часа после последнего сброса. Порог и длительность окна задаются конфигурацией `assistant`; ниже примеры для 5 и 7 суток. Это отдельная защита от злоупотреблений, а не расход суточных вопросов или отдельная платная классификация темы.

- Случай учитывается один раз при сохранении терминального `OFF_TOPIC`, с серверного момента завершения ответа. Повторная доставка события, чтение истории и переподключение к потоку счётчик не меняют. В момент `t` учитываются случаи после последнего сброса, у которых `completed_at ≤ t < completed_at + 7 суток`: ровно через 7 суток случай уже не учитывается, независимо от пояса и календарной недели.
- После пятого учитываемого случая новые 7.1 и 7.4 отвечают `RATE_LIMITED` (429) без создания вопроса/ответа, запуска модели и списания попытки. Уже принятые генерации продолжаются, поэтому одновременные завершения могут увеличить число случаев сверх 5. История 7.3, поток существующего ответа 7.2 и суточный остаток 7.5 доступны; значение `remaining` в 7.5 не отражает эту блокировку.
- Полный сброс всех накопленных случаев — только после успешного финансового ответа `complete` с `charged: true`. Это действует и до пятого случая, и для уже запущенного ответа во время блокировки. `MODEL_ERROR`, `CANNOT_ANSWER`, `OFF_TOPIC` и `complete` с `charged: false` ничего не сбрасывают. Одновременные завершения сервер упорядочивает по пользователю: исходы до сброса удаляются из счётчика, после него учитываются заново.
- У отказа `RATE_LIMITED` поле `error.retry_at` — момент, когда число уже сохранённых учитываемых случаев станет меньше порога за счёт их истечения; `Retry-After` — положительная задержка до него по общему правилу. При 5 случаях это самое раннее истечение, при 7 — третье. В общем случае из `n ≥ limit` случаев, упорядоченных по `completed_at` от старых к новым, берётся случай с индексом `n − limit` (с нуля), `retry_at = completed_at + window`. Успешный уже запущенный финансовый ответ может сбросить счётчик раньше `retry_at`, а новые `OFF_TOPIC` от ранее принятых генераций — сдвинуть срок позже; указанное время не резервирует блокировку. Клиент показывает отказ по общему правилу `RATE_LIMITED`, не выводит недельный остаток из суточного и не повторяет запрос автоматически в цикле.
- Успешный результат, уже сохранённый под тем же `Idempotency-Key`, воспроизводится **до** проверки этого лимита: тот же `201`, без новой модели и списания. Отказ по лимиту не сохраняется под ключом: после освобождения окна или сброса повтор с тем же ключом может пройти. Это не отменяет остальные проверки, в том числе согласие и суточный лимит.

Примеры (моменты в UTC):

| События | Результат |
|---|---|
| Пять `OFF_TOPIC` завершились 1–5 октября в 12:00; сброса нет | После пятого новые вопросы и повторы блокируются; ближайший `retry_at` — 8 октября 12:00 |
| Запрос 8 октября ровно в 12:00 | Случай 1 октября уже истёк, осталось 4; недельная защита пропускает запрос |
| Семь ранее принятых ответов завершились `OFF_TOPIC` 1 октября в 12:00:01–12:00:07, по одному в секунду; сброса нет | `retry_at` — 8 октября 12:00:03: после третьего истечения останется 4 случая |
| После двух `OFF_TOPIC` финансовый ответ завершился `complete`, `charged: true` | Счётчик 0; следующий `OFF_TOPIC` будет первым |
| Во время блокировки ранее принятый ответ завершился `complete`, `charged: false` | Счётчик прежний; такой же ответ с `charged: true` снял бы блокировку |
| После блокировки повторён ключ уже созданного вопроса | Тот же сохранённый `201`; лимит не мешает получить результат принятого запроса |

### 7.1 Задать вопрос
```

```
`Idempotency-Key` обязателен (см. «Идемпотентность»): повтор того же вопроса после обрыва не создаёт второй вопрос и не списывает попытку. Отказы `CONSENT_REQUIRED`, `LIMIT_EXCEEDED` и `RATE_LIMITED` не сохраняются: после согласия, обновления суточного лимита или снятия блокировки OFF_TOPIC повтор с тем же ключом проверяется заново.

| Поле | Тип | Описание |
|---|---|---|
| `question` | object | Сохранённый вопрос, как сообщение в 7.3 |
| `answer_id` | string | ID ответа помощника; по нему — поток ответа (7.2) |
| `remaining_limit` | int | Осталось вопросов на сегодня — попытка списана в момент создания вопроса; окончательное значение — в `done` (7.2) |

Ошибки (обычный HTTP-ответ, до начала генерации):
- `VALIDATION_ERROR` (400) — пустой или слишком длинный текст, нет `Idempotency-Key`;
- `CONSENT_REQUIRED` (403) — нет действующего согласия на передачу данных помощнику, показать экран согласия. Попытка не списывается;
- `LIMIT_EXCEEDED` (403) — суточный лимит исчерпан; `error.resets_at` — когда обновится;
- `RATE_LIMITED` (429) — в том числе блокировка по OFF_TOPIC (правило раздела 7); `error.retry_at` и `Retry-After`.

### 7.2 Поток ответа (SSE)
```
GET /v1/assistant/messages/{answer_id}/events
Accept: text/event-stream
```
Клиент открывает поток сразу после 7.1 и переоткрывает после обрыва или возврата приложения из фона. Работает и для готового ответа: тогда приходят `snapshot` и терминальное событие сразу.

#### Содержимое ответа — блоки
Ответ — упорядоченный список блоков из общего каталога («Общие правила» → «Блоки»; сейчас помощник использует `text`, `chart`, `rows`): текст, график, строки «подпись — значение» (как в макете `Chat`: текст, под ним карточка с графиком «Самокат по месяцам» и строками «Операций», «Средний чек»). Чипы и строка источника — не блоки, они показываются под ответом.

#### События

`snapshot` (первое) — всё состояние ответа к моменту подключения:
| Поле | Тип | Описание |
|---|---|---|
| `status` | code | `generating`, `complete`, `failed` — как в 7.3. Неизвестное значение — как `failed` |
| `blocks` | array<block> | Блоки на момент подключения; может быть пустым. Клиент заменяет ими показанное |
| `chips` | array | Уже собранные чипы (поля — как у события `chip`) |
| `source` | object? | Строка источника, если уже есть (поля — как у события `source`) |
| `currency` | string | Валюта всех сумм в блоках ответа (ISO 4217); сейчас всегда `RUB` |

`chunk`:
| Поле | Тип | Описание |
|---|---|---|
| `index` | int | Номер текстового блока. Равен числу уже полученных блоков — начинается новый текстовый блок; меньше — дописать в существующий |
| `text` | string | Фрагмент текста; клиент дописывает его в конец `data.text` блока |

`block`:
| Поле | Тип | Описание |
|---|---|---|
| `index` | int | Номер блока; всегда следующий по порядку |
| `block` | block | Готовый нетекстовый блок — приходит целиком |

`source` — строка под ответом «По вашим операциям, апрель — сентябрь 2026 · посчитано 25 сентября в 19:11»:
| Поле | Тип | Описание |
|---|---|---|
| `calculated_at` | datetime | Время расчёта данных, на которых построен ответ |
| `data_range` | range? | Период данных, по которым ответил помощник |
| `transfer_mode` | code | Режим переводов, в котором дан ответ |
| `changed_since` | array<code> | Отличия от исходных данных ответа: `categories` — менялись категории или учётные правила; `uploads` — загружали или удаляли выписки; `time_zone` — обновились настройки часового пояса. `unverified` — актуальность источника нельзя подтвердить, например у прежнего ответа без сохранённых ревизий; это не утверждение о фактической правке. Пустой список означает подтверждённое совпадение ревизий всех использованных источников. Для неизвестного кода клиент показывает `changed_since_text` |
| `changed_since_text` | string? | Готовый текст о тех же отличиях или неопределённости; например «Актуальность данных этого ответа не подтверждена» для `unverified`. Нет — актуальность подтверждена. Клиент для известных кодов собирает текст сам, при неизвестном коде показывает этот |

Решение владельца 27.10.2026 ([FIN-367](https://finassist.youtrack.cloud/issue/FIN-367), реализация [FIN-358](https://finassist.youtrack.cloud/issue/FIN-358), [FIN-368](https://finassist.youtrack.cloud/issue/FIN-368), [FIN-369](https://finassist.youtrack.cloud/issue/FIN-369)): помощник сохраняет ревизии именно тех данных, на которых построен ответ, и при чтении истории сравнивает их с текущими ревизиями primary-хранилища. Время `calculated_at` остаётся временем расчёта для показа. По нему нельзя определять изменения: транзакция правки может начаться раньше ответа, а зафиксироваться позже. Ревизии — внутренние данные сервисов, в REST не передаются.

Если ответ использовал несколько снимков разных ревизий одного вида, совпадения с одним более новым снимком недостаточно: актуальность подтверждается только при совпадении всех использованных ревизий с текущей. У старого ответа или снимка без ревизий нет доказуемой исходной версии; сервер возвращает `unverified`, а не восстанавливает её из текущего состояния или часов. При фактически установленном отличии известного вида сервер также возвращает соответствующий код. Пример: `changed_since: ["unverified"]`, `changed_since_text: "Актуальность данных этого ответа не подтверждена"`; прежний клиент с обработкой неизвестных кодов показывает готовый текст.

Проверка выполняется один раз на запрос истории, а в потоке — перед начальным `snapshot` с источником и при последующих обновлениях ответа перед событием `source`. Неизменившийся сохранённый источник также проверяется заново. Это не подписка на будущие правки операций: без обновления ответа отдельное событие не гарантируется. У ответа без источника не создаётся фиктивная строка с временем расчёта.

При временной транспортной недоступности проверки версии сохранённый ответ доступен с `unverified`, исходные ревизии не изменяются. Исключение узкое: только голый внутренний `UNAVAILABLE`/`DEADLINE_EXCEEDED` без details при живом контексте чтения. Ошибки доступа, неверный ответ сервиса версии, отсутствие настройки клиента и отмена/истечение всего запроса остаются ошибками чтения по прежним правилам; они не превращаются в успешный ответ с пометкой.

`chip` (может прийти несколько):
| Поле | Тип | Описание |
|---|---|---|
| `label` | string | Текст чипа |
| `screen` | code | Экран перехода: `operations` — Поиск, `analytics`. Неизвестный экран — чип не показывать |
| `filters` | operations_filter? | Для `operations`: фильтры Поиска, всегда с `transfer_mode` ответа |
| `params` | analytics_params? | Для `analytics`: параметры экрана |

`done` (терминальное) — ответ готов и сохранён:
| Поле | Тип | Описание |
|---|---|---|
| `charged` | bool | Списана ли попытка. `false` — данных для полного ответа не хватило (по результатам функций), помощник ответил тем, что есть |
| `remaining_limit` | int | Осталось вопросов на сегодня |

`error` (терминальное):
```
event: error
data: {"code": "MODEL_ERROR", "user_message": "Не получилось ответить. Вопрос не потрачен", "severity": "error", "text": "Не получилось ответить. Вопрос не потрачен", "retryable": true, "message": "...", "remaining_limit": 5}
```
| Поле | Тип | Описание |
|---|---|---|
| `code` | code | Почему ответа нет: `MODEL_ERROR` — сбой или таймаут Alice AI; `CANNOT_ANSWER` — вопрос непонятен или на него нельзя ответить по данным; `OFF_TOPIC` — вопрос не о данных пользователя и не о личных финансах (модель вызвала инструмент `off_topic`, FIN-159); `INTERNAL_ERROR` — безопасная причина при присутствующем некорректном Status (legacy-код не читается), а также прежний fallback при отсутствии канонического Status/известного legacy-кода. Корректный открытый reason сохраняется даже при отсутствии текста в каталоге. Текст и оформление задаёт каталог BFF, `retryable` — сервис помощника. Сбой самого потока — не `error`, а обрыв («SSE»). Клиент по коду не строит текст и не решает о повторе; код — для аналитики, логов и запасного правила, когда `retryable` нет. Неизвестный код — по общим правилам `user_message` и `retryable`, как известный |
| `user_message` | `optional<string>` | Канонический безопасный текст из каталога BFF, по общим правилам ошибок (FIN-224); имеет приоритет над `text` |
| `severity` | `optional<code>` | `info`, `warning`, `error`; неизвестное, отсутствующее или некорректное — оформление `error` без изменения текста и разрешения повтора |
| `text` | string? | Прежний безопасный текст FIN-159 для старых клиентов. Новый BFF заполняет его тем же текстом каталога, что `user_message`. Новый клиент использует его только при отсутствии `user_message` и только если строка корректна по общим правилам. Иначе — общий текст «Не получилось ответить». Сейчас: `MODEL_ERROR` — «Не получилось ответить. Вопрос не потрачен»; `CANNOT_ANSWER` — полный прежний текст макета `Chat` (FIN-159, без сокращения); `OFF_TOPIC` — «Вопрос не по теме — помощник отвечает только на вопросы о ваших финансах. С другими вопросами помогут универсальные ассистенты: Алиса AI, GigaChat, ChatGPT, Claude, DeepSeek» |
| `retryable` | bool? | Доступен ли повтор (7.4); сервер присылает его всегда, начиная с FIN-159. `true` — клиент показывает «Повторить», `false` — не показывает. Сейчас `true` только у `MODEL_ERROR`. Разрешён `RetryAnswer` — новая генерация и новый логический POST с новым ключом, не повтор исходного `AskQuestion` и не REST `error.retryable`. Поля нет (старая версия сервера) — «Повторить» только при `code` = `MODEL_ERROR`, как до FIN-159 |
| `message` | string | Для логов и отладки, не для показа |
| `remaining_limit` | int | Остаток после возврата попытки |

Пример вопроса не по теме:
```
event: error
data: {"code": "OFF_TOPIC", "text": "Вопрос не по теме — помощник отвечает только на вопросы о ваших финансах. С другими вопросами помогут универсальные ассистенты: Алиса AI, GigaChat, ChatGPT, Claude, DeepSeek", "retryable": false, "message": "off_topic tool called", "remaining_limit": 5}
```

При ошибке попытка возвращается, ответ в истории получает статус `failed`, уже показанные блоки клиент убирает. Генерация, которая не закончилась за 3 минуты (в том числе прерванная сбоем сервера), завершается с `MODEL_ERROR`. Для уже неудачного ответа первое событие `snapshot` имеет `status: failed`, после него сразу приходит терминальное `error` с теми же правилами отображения; отдельные поля ошибки в `snapshot` не добавляются.

Сбой сервера посреди потока — не событие `error`: сервер закрывает поток без терминального события, клиент переоткрывает его («SSE») и по снимку видит, что ответ ещё генерируется, готов или `failed`.

Чужой или несуществующий `answer_id` — 404 `NOT_FOUND` до начала потока.

#### Блоки (`block`)

Блоки ответа — из общего каталога («Общие правила» → «Блоки»): `text`, `chart`, `rows`; поля `id` и `status` у них нет (ответ целиком либо готов, либо `failed`). Суммы в блоках — в валюте `currency` события `snapshot` и сообщения (7.3). Неизвестный тип клиент показывает текстом из `alt_text`.

|---|---|---|
| `messages` | array | Сообщения в хронологическом порядке (старые первыми); с разделителями по дням клиент разбирается сам по `created_at` |
| `messages[].id` | string | ID сообщения |
| `messages[].role` | code | `user` — вопрос, `assistant` — ответ. Сообщение с неизвестной ролью клиент не показывает |
| `messages[].text` | string? | Только у `user`: текст вопроса |
| `messages[].status` | code? | Только у `assistant`: `complete` — готов; `generating` — ещё генерируется, клиент открывает поток 7.2; `failed` — не получилось ответить, попытка возвращена. Неизвестный статус — как `failed` |
| `messages[].error_code` | code? | Только у `failed`: коды события `error` (7.2) — `MODEL_ERROR`, `CANNOT_ANSWER`, `OFF_TOPIC`, `INTERNAL_ERROR`. Клиент по коду не строит текст и не решает о повторе; неизвестный — по общим правилам `error_user_message` и `retryable`, как известный. При present-invalid вложенном Status — `INTERNAL_ERROR`, не `null`, без чтения legacy-кода. Совпадение с REST-кодом не запускает действия раздела 8; явное `retryable` остаётся независимым свойством сервиса |
| `messages[].error_user_message` | `optional<string>` | Только у `failed`: канонический безопасный текст из каталога BFF, как `user_message` события `error` (7.2). Приоритет и fallback — общие правила ошибок (FIN-224) |
| `messages[].error_severity` | `optional<code>` | Только у `failed`: оформление по общим правилам `severity` — `info`, `warning`, `error`; неизвестное, отсутствующее или некорректное — `error` без изменения корректного текста |
| `messages[].error_text` | string? | Прежний безопасный текст FIN-159 для старых клиентов; новый BFF заполняет его тем же текстом каталога, что `error_user_message`. Новый клиент использует его только при отсутствии `error_user_message` и корректной строке по общим правилам. Иначе — общий текст «Не получилось ответить»; это же правило действует при неизвестном `status`, показанном как `failed` |
| `messages[].retryable` | bool? | Только у `failed`; сервер присылает всегда, начиная с FIN-159: доступен ли повтор (7.4), как в событии `error` (7.2): `RetryAnswer` создаёт новую генерацию с новым логическим POST и новым ключом, а не повторяет исходный `AskQuestion` (это не REST `error.retryable`). `true` — «Повторить»; `false` — без «Повторить». Поля нет — «Повторить» только при `error_code` = `MODEL_ERROR`, как до FIN-159 (у сообщения с неизвестным `status` кода нет — без «Повторить») |
| `messages[].charged` | bool? | Только у `complete`: списана ли попытка |
| `messages[].blocks` | array<block>? | Только у `assistant`: блоки ответа — текст, графики, строки, — те же, что в потоке 7.2. У `generating` — на момент запроса, у `failed` — пустой массив |
| `messages[].currency` | string | Валюта сумм в `blocks` (ISO 4217), есть у каждого сообщения; сейчас всегда `RUB`. У вопроса сумм нет, но поле тоже обязательное: так схема гарантирует валюту ответа без разделения `Message` по ролям (осознанный компромисс). Поля валюты в профиле пока нет, поэтому у вопросов и у сообщений, сохранённых до появления поля, — `RUB` |
| `messages[].chips` | array? | Только у `complete`: чипы, как в событии `chip` (7.2) |
| `messages[].source` | object? | Только у `complete`: как в событии `source` (7.2); `changed_since` пересчитывается на момент запроса |
| `messages[].created_at` | datetime | Время сообщения |
| `has_older` | bool | Есть более старые сообщения |

Ответ, заменённый повтором (7.4), в истории не возвращается; его поток 7.2 отвечает 404 `NOT_FOUND`.

### 7.4 Повторить ответ
```
POST /v1/assistant/messages/{answer_id}/retry
Idempotency-Key: 6b2e9d1c-4f7a-4a3b-8c5d-2e9f1a7b3c6d
```
Кнопка «Повторить» у неудачного ответа с `retryable: true` (7.2, 7.3; сейчас — только `MODEL_ERROR`): тот же вопрос, новый ответ. Неудачный ответ заменяется новым — в истории вопрос не дублируется. Попытка списывается заново (неудачная уже возвращена).

Проверка отдельного лимита OFF_TOPIC и порядок воспроизведения `Idempotency-Key` — как в 7.1; блокировка распространяется на повтор любого ответа, даже если у него `retryable: true`. Отказ не сохраняется под ключом.

Тела запроса нет. Ответ `201`:
```json
{
  "answer_id": "01a10853-0c11-7d2e-9a4b-6f1e3c8d2a95",
  "remaining_limit": 4
}
```
Дальше — поток 7.2 по новому `answer_id`.

У ответов, сохранённых до FIN-159 (признак повтора не записан), сервер решает о повторе по коду, как раньше: `MODEL_ERROR` — повтор разрешён, остальные — нет.

Ошибки: `NOT_FOUND` (404); `RETRY_NOT_ALLOWED` (422) — ответ не в статусе `failed` с `retryable: true` или уже заменён; `CONSENT_REQUIRED`, `LIMIT_EXCEEDED` (403); `RATE_LIMITED` (429) — в том числе блокировка по OFF_TOPIC, `error.retry_at` и `Retry-After`.

### 7.5 Остаток лимита
```
GET /v1/assistant/limit
```
Ответ `200`:
```json
{
  "remaining": 4,
  "daily_max": 5,
  "resets_at": "2026-10-05T00:00:00+03:00"
}
```
| Поле | Тип | Описание |
|---|---|---|
| `remaining` | int | Осталось вопросов на сегодня («осталось 3 из 5»; при `remaining = daily_max` — «5 вопросов в день») |
| `daily_max` | int | Суточный лимит |
| `resets_at` | datetime | Когда лимит обновится — полночь по Москве, с поясом `+03:00` («Новые — в 00:00 по Москве»; при другом поясе телефона клиент добавляет местное время в скобках) |

## Решения по расширяемости

1. **Новые банки.** `source_name`, `account.type_name`, `account.mask` уже в контракте; новый источник отображается без обновления клиента. Новые категории появятся в 5.1. Новые необязательные поля в операциях (кэшбэк, комиссия, контрагент) — обратно совместимы; поиск `q` подхватит их без изменения API.
2. **Новые платформы (iOS, веб).** API идентичен; различаются только выбор файла и `ACTION_DIAL` (клиентская логика). Календарь, пороги и тексты блокировок — на сервере, поэтому клиенты показывают одно и то же.
3. **Вклады и кредиты (после MVP).** Новые эндпоинты `/v1/deposits`, `/v1/credits`; на «Аналитике» — новое необязательное поле.
4. **Платные тарифы.** Поле `plan` в профиле, `daily_max` в 7.5 меняется по тарифу.
5. **Новые функции аналитики.** Новые блоки и метрики на существующих примитивах — без релиза клиента (FIN-4); новый примитив или действие — новый тип в каталоге «Блоки» и `supports`; новые `feature` в итоге импорта, новые `lock.reason` — клиент показывает тексты сервера.
6. **Автоматическое подключение банков.** Новые эндпоинты `/v1/connections`; «История загрузок» станет историей синхронизаций новыми полями.
7. **Часовой пояс.** Диапазоны — `datetime` с поясом, календарные единицы — в поясе профиля; пользователи в других поясах не требуют изменений API.
8. **Подгрузка в поиске.** Когда выборки вырастут, поиск получит необязательный курсор — без изменения ответа для старых клиентов.
9. **Тексты, единицы, валюта, списки** (FIN-82, 13.10.2026). У открытых кодов, из которых клиент строит текст, — серверный текст для неизвестных значений (`feature_name`, `notices[].text`, `changed_since_text`, тексты блокировок в 6.1); у значений — `value_kind`; у ответов с суммами — `currency`; согласия — списком `consents[]`; `theme` и `operations_filter.kind` в ответах — открытые коды. Устаревшее удаляется по правилу «Удаление устаревшего» («Расширяемость»).
10. **Экран «Аналитика» — список блоков** (FIN-4, 15.10.2026). Вместо фиксированного дерева `tiles` / `insights` — блоки общего каталога с помощником; состав, порядок и тексты — на сервере, клиент рисует примитивы и сообщает `supports`; эксперименты над составом — `exp` из Remote Config; выключатель блока — флаг `analytics.block.<id>`.
11. **Ошибка ответа помощника — текст и повтор с сервера** (FIN-159, 17.10.2026). Событие `error` (7.2) несёт `text` и `retryable`, сообщение `failed` (7.3) — `error_text` и `retryable`: клиент не строит текст из `code` и не решает о «Повторить» сам, поэтому новый код ошибки (как `OFF_TOPIC`) показывается без обновления клиента.
12. **Единое отображение серверных ошибок** (FIN-224, решение 23.10.2026). REST и терминальные SSE добавляют необязательные `user_message` и `severity`; история помощника — `error_user_message` и `error_severity`. Каталог безопасных текстов и оформления принадлежит BFF, внутренние сервисы возвращают код и структурированные параметры. Прежние `text`/`error_text` помощника сохраняются для совместимости по правилам «Единого отображения ошибок» и больше не определяют владельца каталога; прежний result.`retryable` помощника остаётся доменным разрешением новой попытки. Общий `google.rpc.Status` переиспользуется между сценариями; `RequestRetryInfo` и REST `Error.retryable` относятся только к исходному запросу по правилам «Повтора REST-запроса» и grpc-api.md 5.4.
