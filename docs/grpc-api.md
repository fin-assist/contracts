## 2. Кто кого вызывает

```
bank-bff ──(токен пользователя)──► user · bank-statement-data · analytics · assistant

assistant ──(системный)──► user.UserInternalService.GetAssistantConsentStatus
          ──(системный)──► statementdata.AssistantToolsService       (инструменты LLM)
          ──(системный)──► analytics.AnalyticsService               (инструменты LLM)

bank-statement-data ──(системный, outbox)──► analytics.MetricsIngestService.UpsertUserMetrics

user ──(системный, outbox)──► usersettings.SetUserTimezone на bank-statement-data, assistant
     ──(системный, outbox)──► userdeletion.PurgeUserData на bank-statement-data, analytics, assistant

все сервисы ──► user.UserInternalService.GetSigningKeys  (JWKS, кэш)
```

Циклов нет: `analytics` никого не вызывает, `bank-statement-data` вызывает только `analytics`. Синхронных вызовов «сервис → сервис» на пути запроса клиента два: проверка согласия в `assistant` и инструменты LLM (последние — в фоне генерации).

Системные вызовы (`assistant → user`, `user → bank-statement-data / analytics / assistant`) нанесены на схему «Services v3» фиолетовым пунктиром 12.10.2026; `* → user` (JWKS) — стикером, а не стрелками.

## 3. Две модели вызова

### 3.1 От имени пользователя

Путь `bank-bff → сервис`. `bank-bff` проверяет JWT сам (JWKS, локально) и **пробрасывает исходный токен** в `authorization`. Сервис проверяет его повторно (Ed25519, микросекунды) и берёт `user_id` только из `sub`. В сообщениях запросов `user_id` нет.

### 3.2 Системный

Фоновые вызовы, у которых нет живого токена пользователя: outbox, удаление аккаунта, синхронизация пояса, **инструменты помощника**. `user_id` — явным полем запроса; вызывающий подтверждает себя сервисным токеном.

Почему инструменты помощника системные, а не «с токеном пользователя», как было записано в `architecture.md` («Внутренние вызовы несут токен пользователя»): генерация идёт на сервере до 3 минут независимо от соединения клиента, а access-токен живёт 15 минут и мог быть выдан 14 минут назад — вызов инструмента посреди ответа получил бы `UNAUTHENTICATED`. `assistant` запоминает `user_id` из проверенного токена при создании вопроса и передаёт его явно. `architecture.md` исправлен 12.10.2026: «токен пользователя — только на синхронном пути `bank-bff → сервис`».

Методы со смешанной моделью (`GetAnalytics`, `ListPeriods`, `GetAssistantConsentStatus`) имеют `optional string user_id`: с токеном пользователя поле пустое (или равно `sub`), с системным вызовом — обязательно.

### 3.3 Идентичность сервиса

Решено 12.10.2026: **projected ServiceAccount token** Kubernetes.

- У каждого сервиса свой ServiceAccount (`bank-bff`, `user`, `bank-statement-data`, `analytics`, `assistant`) в namespace `finassist`.
- В Deployment — projected volume `serviceAccountToken` с `audience: finassist-internal`, `expirationSeconds: 3600`; kubelet сам обновляет файл токена при ~80 % срока, перезапуск пода не нужен. Один общий audience для всех получателей — иначе клиенту пришлось бы монтировать токен на каждого адресата; разделение по получателю даёт таблица разрешений ниже.
- Клиент читает файл (кэш по mtime) и передаёт `x-service-authorization: Bearer <token>`.
- Сервер проверяет локально по JWKS API-сервера k3s (`https://kubernetes.default.svc/openid/v1/jwks`, кэш 1 ч, обновление при неизвестном `kid`): подпись, `exp`, `iss`, `aud`. Имя вызывающего — `kubernetes.io.serviceaccount.name` (дублируется в `sub`). TokenReview на каждый вызов не используем.
- k3s: зафиксировать `--kube-apiserver-arg=service-account-issuer=https://kubernetes.default.svc.cluster.local` на всех трёх серверах; при недоступности discovery анонимно — ClusterRoleBinding сервисов на `system:service-account-issuer-discovery`.
- Токен — bearer; шифрование и защита от перехвата — WireGuard между узлами (см. 9). mTLS отклонён как дублирующий; статический секрет на сервис отклонён (ротация и хранение наши, утечка даёт права навсегда).

Интерцептор на сервере держит таблицу «метод → разрешённые вызывающие → модель»:

## 4. Metadata

| Ключ | Кто ставит | Смысл |
| --- | --- | --- |
| `authorization` | `bank-bff` | `Bearer <access JWT>` пользователя, как пришёл от клиента |
| `x-service-authorization` | каждый клиент | токен ServiceAccount вызывающего |
| `x-request-id` | `bank-bff` (из заголовка клиента или новый) | сквозной ID в логах всех сервисов; дальше пробрасывается без изменений |
| `idempotency-key` | `bank-bff` | из `Idempotency-Key`; проверку наличия делает `bank-bff` (400 до вызова), хранение — сервис-владелец |
| `x-client-ip` | `bank-bff` | IP TCP-пира; за явно доверенным прокси — первый справа недоверенный адрес из `X-Forwarded-For` по правилу ниже. HTTP `X-Client-IP` и произвольные заголовки клиента не копируются; сервис верит metadata только от `bank-bff` |
| `x-client-version` | `bank-bff` | `android/0.2.5+41` из заголовка клиента `X-Client-Version` (FIN-20), для логов и метрик. Запрос без заголовка или с неразобранным значением `bank-bff` отклоняет сам (400 `CLIENT_VERSION_UNSUPPORTED`), поэтому в вызовах от имени пользователя ключ доходит до сервиса всегда. В системных вызовах (outbox, инструменты помощника) его нет, и сервис его не требует. Подделывается клиентом: не для авторизации и не для лимитов |
| `x-read-primary` | `bank-bff` (из заголовка клиента `X-Read-Primary`) | `1` — читать с primary. Клиент ставит заголовок на все запросы в течение 30 с после любого своего успешного пишущего запроса (`POST`, `PUT`, `PATCH`, `DELETE`); по умолчанию — нет (решено 14.10.2026, см. 7.3) |

**Доверенные прокси для `x-client-ip` (FIN-343).** В `bank-bff` настройка `TRUSTED_PROXIES` содержит IPv4/IPv6 CIDR своих nginx/ingress и промежуточных доверенных HTTP-прокси через запятую (для локального nginx, например, `127.0.0.1/32,::1/128`). Неверный CIDR — ошибка старта; пусто — всегда IP TCP-пира, поэтому за прокси лимиты по IP становятся общими. Обязательное условие включения адреса/сети в список — это контролируемый HTTP-прокси, который сам дописывает IP своего TCP-пира в `X-Forwarded-For`. L4-балансировщики, NAT/SNAT и узлы, не дописывающие заголовок, не включаются: их пропуск при разборе цепочки позволил бы принять подставленный клиентом префикс. Если они скрывают IP клиента, его восстанавливают на первом HTTP-прокси из доверенного инфраструктурного источника (например, PROXY protocol / `real_ip`), а не расширяют список. Сети клиентов и все адреса не доверяются. Только от доверенного TCP-пира BFF читает все строки заголовка справа налево до первого адреса вне доверенных сетей и использует его как `x-client-ip`; левый клиентский префикс не читает. От недоверенного пира заголовок игнорируется. Если заголовка нет, остаётся TCP-пир; если все элементы доверенные — крайний левый из них. Неразбираемый элемент просматриваемой части цепочки или предел 16 просмотренных элементов без недоверенного адреса оставляет последний успешно определённый доверенный узел. Заголовок, дополненный своим доверенным прокси, — инфраструктурный источник, а не произвольный клиентский ввод. Один и тот же вычисленный IP используется в лимитах SSE BFF и передаётся сервисам; примеры и настройка nginx — `api.md`, «Адрес клиента за доверенным прокси».

`verification_token` передаётся полем запроса (`WatchPhoneVerificationRequest`), а не metadata: тело gRPC не попадает в логи ingress, а поле проще не потерять при логировании metadata интерцептором. Интерцептор логирования обязан маскировать `authorization`, `x-service-authorization`, `idempotency-key` и поля с именами `*token*` (маскирование ПДн вообще — после MVP, но токены — сразу).

## 5. Ошибки

Ошибка, которую клиент должен получить осмысленно, несёт `google.rpc.ErrorInfo{domain: "finassist", reason: <ErrorReason>, metadata}`, а при необходимости ещё `google.rpc.BadRequest` или `google.rpc.RetryInfo`. Реестр — `common/v1/errors.proto`. У каждого кода есть опция `error_spec` (`common/v1/error_options.proto`): код gRPC, HTTP-статус, обязательные ключи `metadata`, прикладываемые детали. Таблица ниже повторяет реестр для чтения; источник правды — опции.

`bank-bff` переводит **по `reason`**, а не по коду gRPC:

| `reason` | gRPC | REST | Доп. поля |
| --- | --- | --- | --- |
| `VALIDATION_ERROR` | `INVALID_ARGUMENT` | 400 | `details[]` из `BadRequest` (в том числе неверный формат телефона, FIN-68) |
| `INVALID_TOKEN`, `TOKEN_EXPIRED`, `TOKEN_REVOKED` | `UNAUTHENTICATED` | 401 |  |
| `CONSENT_REQUIRED` | `PERMISSION_DENIED` | 403 |  |
| `LIMIT_EXCEEDED` | `RESOURCE_EXHAUSTED` | 403 | `resets_at` |
| `NOT_FOUND` | `NOT_FOUND` | 404 |  |
| `IDEMPOTENCY_CONFLICT` | `ALREADY_EXISTS` | 409 |  |
| `REQUEST_IN_PROGRESS` | `ABORTED` | 409 | `Retry-After` из `RetryInfo` |
| `FILE_TOO_LARGE` | `OUT_OF_RANGE` | 413 |  |
| `WRONG_FORMAT`, `CSV_NOT_ACCEPTED`, `WRONG_BANK`, `CONSENT_OUTDATED`, `TOO_MANY_RESULTS`, `SELECTION_NOT_FOUND`, `CATEGORY_NOT_ASSIGNABLE`, `RETRY_NOT_ALLOWED` | `FAILED_PRECONDITION` | 422 |  |
| `RATE_LIMITED` | `RESOURCE_EXHAUSTED` | 429 | `retry_at`, `Retry-After` |
| нет `ErrorInfo`, неизвестный `reason`, `INTERNAL_ERROR`, голые `INTERNAL` / `UNAVAILABLE` / `DEADLINE_EXCEEDED` / `PERMISSION_DENIED` |  | 500 `INTERNAL_ERROR` |  |

Коды `MAINTENANCE`, `CLIENT_VERSION_UNSUPPORTED` (FIN-20) и `REQUEST_TOO_LARGE` (FIN-339) в межсервисный реестр не входят: их генерирует сам `bank-bff` до вызова сервиса (`MAINTENANCE` — 503 с `until` и `Retry-After`; `CLIENT_VERSION_UNSUPPORTED` — 400, решено 15.10.2026), сервисы их не возвращают. `REQUEST_TOO_LARGE` — HTTP 413 для шести JSON-операций и транспортного бюджета из `api.md`, «Размер JSON-запроса»: проверяется по заголовку и ограниченному чтению потока до сервиса/ключа, не сохраняется под ключом, `retryable: false`. Это BFF-only исключение из правил 2 и 4 ниже: новый protobuf reason, `error_spec`, Go API или тег для него не нужны; `FILE_TOO_LARGE` остаётся только файловым. Минимальная версия по платформам и режим техработ — конфигурация `bank-bff`, меняются без релиза. Проверку версии `bank-bff` делает до валидации kin-openapi — иначе отсутствие обязательного заголовка стало бы `VALIDATION_ERROR`.

### 5.1 Правила реестра

Цель — чтобы кодов были десятки, а не сотни, и без дублей (решение 12.10.2026).

1. **Новый код — только при новой реакции клиента**: другой текст или действие, ретрай, выход из аккаунта. Подробности (какое поле, какой ресурс, какой лимит) идут в `metadata` или `BadRequest`, а не в новый код. Неверный формат любого поля — `VALIDATION_ERROR` с нарушением у поля, а не `FIELD_X_INVALID`; «нет операции / загрузки / платежа» — один `NOT_FOUND`. По этому правилу `INVALID_PHONE` слит в `VALIDATION_ERROR` (FIN-68).
2. **Реестр один на все сервисы.** Своих enum ошибок у сервисов нет: сервис берёт общий код или предлагает новый по правилу 1.
3. **В реестре только то, что доходит до клиента.** Внутренние отказы между сервисами — голый код gRPC без `ErrorInfo`: ретраи и метрики работают по коду. Поэтому `CALLER_NOT_ALLOWED` удалён — чужой вызывающий получает голый `PERMISSION_DENIED`, `bank-bff` отдаёт 500 и поднимает алерт.
4. **Реестр меняется только вместе с разделом 8 `api.md`**, через задачу FIN. Удалённые номера и имена — в `reserved`.
5. **`error_spec` существующего кода не меняется.** `buf breaking` опций не сравнивает (это проверяет `scripts/check_error_spec_stable.py` против базы PR; изменение принимает владелец меткой `breaking-accepted`), а новый ключ `metadata`, деталь или статус меняют сигнатуру конструктора `finerr` и при разъезде версий модуля превращают ошибку в 500 у `bank-bff`. Нужна другая реакция клиента — новый код по правилу 1; если без изменения не обойтись (решение владельца), последней выкатывается сторона, которая начинает требовать больше: добавление ключа или детали — сначала все сервисы, потом `bank-bff`; удаление — сначала `bank-bff`, потом сервисы; смена `http_status`/`grpc_code` порядка не требует.

**`BadRequest` → REST `details[]`:** `field` → `field`, `reason` → `code` (`REQUIRED`, `INVALID_FORMAT`, `OUT_OF_RANGE`, …), `description` → `message` (для логов, в интерфейсе не показывается); `localized_message` не используется. `VALIDATION_ERROR` без единого нарушения или с нарушением без `reason`, `REQUEST_IN_PROGRESS`/`RATE_LIMITED` без `RetryInfo` с положительной задержкой, пустое значение обязательного ключа `metadata` и ключ с суффиксом `_at`, который не является моментом RFC 3339 (смещение в пределах ±14:59) или равен нулевому времени (конструктор принимает для него `time.Time`; смещение в строке — `Location` переданного времени, поэтому если REST фиксирует пояс, как `resets_at` с `+03:00` в api.md 7.5, сервис передаёт время в этом поясе), — неполная ошибка: `bank-bff` отвечает 500 и считает `finassist_unmapped_error_total` (`finerr.ToREST`).

### 5.2 Контроль

Правила выше рассчитаны на дисциплину. Чтобы их соблюдали и люди, а не только агенты, правильный путь должен быть самым коротким, а неправильный — не проходить CI.

| Механизм | Что не даёт сделать | Где |
| --- | --- | --- |
| Опция `error_spec` у каждого кода | завести код без кода gRPC, HTTP-статуса или с ключами `metadata` не в snake_case | `.proto` + проверка CI |
| Генерация из опций: конструкторы ошибок для сервисов (`finerr.NotFound()`, `finerr.LimitExceeded(resetsAt)`) и таблица перевода для `bank-bff` (`finerr.ToREST`) | вручную собрать `ErrorInfo` с опечаткой в `reason`, забыть обязательный ключ `metadata` (это параметр конструктора), разойтись с маппингом `bank-bff` (его не пишут руками) | `tools/protoc-gen-finerr` в `fin-assist/contracts`, результат — пакет `finerr` модуля `gen/go` (раздел 10) |
| Линтер (`golangci-lint`, правило `forbidigo`): `status.Error`, `status.New`, `errdetails.ErrorInfo` запрещены вне пакета `finerr` | обойти конструкторы | CI сервисов |
| `scripts/check_error_registry.py` | разойтись с разделом 8 `api.md` (коды и HTTP-статусы), завести `error_spec` в другом enum (свой реестр сервиса), превысить лимит в 30 кодов | CI `proto/` |
| `buf breaking` | переиспользовать удалённый номер или имя | CI `proto/` |
| CODEOWNERS на `errors.proto`, `error_options.proto`, `scripts/check_error_registry.py` и `api.md` + обязательное ревью владельца в защите ветки | добавить код или поднять лимит без ревью владельца | GitHub |
| Метрика `bank-bff` `finassist_unmapped_error_total{reason, grpc_code}` и алерт на любое ненулевое значение | незаметно отдавать клиенту 500 вместо осмысленной ошибки | рантайм |

Лимит в 30 кодов — не оценка, а точка обязательного обсуждения: сейчас кодов 20. Поднять лимит можно только правкой скрипта, а она проходит через CODEOWNERS.

- `status.message` наружу не передаётся никогда — только в лог `bank-bff` с `x-request-id`.
- Порядок проверки из `api.md` (`401 (Authorization) → 400/413 проверки bank-bff → ключ идемпотентности (сохранённый ответ / 409) → 429 → 401 (токены запроса, которые проверяет сервис) → 400 → 404 → 403 → 413/422`; исключение — `FILE_TOO_LARGE` в `UploadStatement`: до ключа, под ключом не сохраняется, остальные исходы `UploadStatement` сверяют ключ в конце потока — раздел 6) после проверок `bank-bff` соблюдает **сервис**: `bank-bff` сам отвечает 401 по заголовку `Authorization` (свой разбор JWT — первый шаг `401`), 400 при отсутствии `Idempotency-Key` и невалидной схеме (kin-openapi) и 413 по `Content-Length`/ограниченному чтению до валидации и вызова сервиса. FIN-339 уточняет код `REQUEST_TOO_LARGE` и минимум 65 536 байт только у шести JSON-операций (`api.md`, «Размер JSON-запроса»); ограниченное чтение и отказ 413 остальных операций с телом сохраняются. Для остальных JSON-операций конкретный код и байтовый бюджет такого отказа контракт пока не определяет — последующее согласование FIN-225, без расширения реализации FIN-268; отдельно описанный файловый лимит и код сохраняются. Восемь операций без тела принимают фактические 0 байт независимо от заголовков, а от 1 байта (включая `{}`/пробел) дают 400 при ограниченном чтении. У шести JSON-операций разрешён только отсутствующий `Content-Encoding` или `identity`; другие значения — 400 без распаковки. Токены запроса, которые проверяет сервис (`registration_token` в `Register`, `refresh_token` в `RefreshTokens`, `verification_token` в `WatchPhoneVerification` из REST-заголовка `X-Verification-Token`), — второй шаг `401`: после ключа идемпотентности (повтор получает сохранённый ответ) и после `429` (подбор токенов упирается в лимит); у `WatchPhoneVerification` ключа нет — шаг идёт сразу после проверок `bank-bff` и лимитов.
- Ошибки внутри потоков (`PROCESSING_FAILED`, `CANCELLED`, `MODEL_ERROR`, `CANNOT_ANSWER`, `OFF_TOPIC`) — не статус gRPC, а терминальное сообщение потока (`ImportStreamError`, `AnswerError`), после которого сервис закрывает поток со статусом OK. Статус не-OK в середине потока (обрыв, падение пода) во всех трёх потоках — `WatchPhoneVerification` (REST 1.2), `WatchUpload` (3.3), `WatchAnswer` (7.2) — `bank-bff` не превращает в событие `error`, а закрывает SSE **без** терминального события (FIN-159): терминальный `error` в REST — только доменный исход (разбор не удался, ответ не получился), и клиент не должен принимать сбой транспорта за него. Клиент считает такое закрытие обрывом и переоткрывает поток по общему правилу (`api.md` «SSE»); первым событием он получает текущее состояние ресурса (статус заявки 1.2, прогресс или итог разбора 3.3, снимок ответа 7.2) — состояние хранится в сервисе, а не в потоке. У помощника генерация от потока не зависит и сохраняется в БД `assistant`, поэтому снимок есть всегда: ответ ещё генерируется, уже готов или `failed` с текстом. Для `WatchUpload` исход разбора, прерванного падением пода, — `PROCESSING_FAILED` по 3-минутному таймауту разбора (7.2; решение владельца 17.10.2026). Если генерацию прервало падение пода `assistant`, ответ завершается `MODEL_ERROR` по 3-минутному таймауту генерации (`api.md` 7.2), и клиент получает его при следующем подключении.

### 5.3 Тексты для кодов и формы ответа (FIN-82, FIN-224)

Сервисы отдают коды и числа; исключение — блоки экрана «Аналитика» (FIN-4): их состав, порядок и тексты, включая `lock.text`, собирает `analytics` (FIN-5, `GetAnalyticsResponse.blocks`), а `bank-bff` переводит блоки в REST один к одному (`data` — `google.protobuf.Struct` → JSON-объект). Блоки помощника `bank-bff` переводит из типизированных `assistant.v1.Block` в тот же общий формат REST. Остальные тексты для показа, которые клиент берёт как запасной вариант для неизвестного кода (`feature_name` и `text` у `coverage.features`, `notices[].text` итога импорта, `changed_since_text` источника ответа помощника), собирает `bank-bff` при переводе ответа в REST. Он обновляется вместе с сервисами и знает все их коды; новый код без текста в `bank-bff` — `finassist_untranslated_code_total{field, code}`, алерт на ненулевое значение. Так же `bank-bff` собирает `profile.consents[]` из полей согласий `user.Profile`. Для этих полей proto не меняется.

Остальные поля, которые отдают сами сервисы, `bank-bff` переносит как есть:

| Поле | Кто заполняет | Почему сервис |
|---|---|---|
| `BlockLock.text` (и устаревший `MetricLock.text`) | `analytics` | текст зависит от данных пользователя («Нужно 3 полных месяца — пока есть только 1–25 сентября»), их знает только сервис |
| `AnswerError.retryable`, `Message.retryable` (FIN-159) | `assistant` | возможность повтора — доменное правило помощника, которое проверяет и `RetryAnswer`. Для поддерживаемой версии `assistant` значение `AnswerError.retryable` авторитетно, включая `false`: наличие или содержимое текста не влияет на него. У `Message.retryable` есть presence; если поле отсутствует, сохраняется прежнее правило `MODEL_ERROR` → повтор разрешён, остальные → нет. Старые сохранённые записи сервис дополняет по тому же правилу. Прежние `AnswerError.text` и `Message.error_text` остаются только для совместимости wire-формата; новый BFF их не переносит и не использует для определения возможностей сервиса (5.4) |
| `currency`: `GetAnalyticsResponse`, `Message`, `AnswerSnapshot` | `analytics`, `assistant` | валюта — свойство посчитанных сумм; сейчас всегда `RUB`. Поля валюты в профиле пока нет: у вопросов — `RUB`; сообщения, сохранённые до появления поля, `assistant` дозаполняет `RUB` миграцией (FIN-98) |

В proto это `string` без `optional`: поле обязательное (`GetAnalyticsResponse.currency` — только при `has_data`, при `has_data = false` оно пустое и в REST не передаётся), пустая строка — ошибка сервиса. Вместо пустого значения `bank-bff` подставляет:

- `currency` — `RUB`. Подстановка временная, пока не все версии сервисов заполняют поле; снимает её FIN-98, обязательно до включения второй валюты (иначе сумма в ней молча покажется рублями). Условие снятия — шаги; порядок обязателен для 1 → 2 → 3, шаг 4 можно вести параллельно с ними, шаг 5 — после 1–4:
  1. все экземпляры `assistant` и `analytics` в проде заполняют поле при записи и в ответах;
  2. после этого миграция `assistant` дозаполняет `RUB` у всех сохранённых сообщений обеих ролей — вопросов и ответов;
  3. проверка нуля (ниже) по полям `currency` с окном `[14d]`, целиком после отметки шага 2 в FIN-98;
  4. `api.md` (7.2, 7.4, раздел 8) описывает ошибку при пустой валюте после снятия, и правки смержены в `main` репозитория `contracts`;
  5. непосредственно перед снятием — повторная проверка, что в базе `assistant` нет сообщений с пустой `currency`.

  Вопросы к FIN-98 для шага 4: ответ REST-запроса; событие потока помощника, которое клиент отличит от обрыва (5.2); состояние ответа и возврат попытки; падает ли вся история из-за одной записи или запись пропускается.

  Запрет на откат действует для `assistant` и `analytics` по отдельности: от выкладки версии сервиса, заполняющей поле, и бессрочно. Версии без поля не выкатываются и не используются для отката: после снятия подстановки такой откат дал бы ошибку пользователям. Минимальную допустимую версию каждого сервиса владелец FIN-98 записывает в задаче и в конфигурацию выкладки сервиса — пайплайн не выкатывает версию старше неё.

  Если сервис нужно срочно откатить по другой причине (дефект в самой выкладке), чинят вперёд: исправление поверх версии с полем. Откат на версию без поля возможен только по явной отметке владельца FIN-98 в задаче, по шагам:
  1. владелец FIN-98 отмечает откат в задаче и ставит тишину только на `field` откатываемого сервиса (`analytics` — `GetAnalyticsResponse.currency`; `assistant` — `Message.currency`, `AnswerSnapshot.currency`) со ссылкой на отметку и сроком 24 часа; продлевают её только новой отметкой в задаче. Через 72 часа отката владелец решает в задаче: возвращать вперёд или продлевать явно;
  2. только если `bank-bff` без подстановки уже выложен — `bank-bff` откатывают на версию с подстановкой (критерий ниже); откатывали ли его, владелец отмечает в задаче;
  3. владелец снижает минимальную версию только откатываемого сервиса и только до конкретной версии, на которую откатывают, и сервис откатывают.

  Возврат вперёд: сервис выкатывают на версию с полем, и после того как обновлены все его экземпляры, владелец возвращает минимальную версию. Если откатывали `assistant` — затем заново миграция (шаг 2 основного списка: версия без поля могла записать сообщения с пустой `currency`) и шаг 5 — проверка базы `assistant` после неё (шаг 4 уже выполнен); для `Message.currency` главная проверка — база, историю читают редко. Если откатывали `analytics` — сообщений у него нет, нужна только метрика. Повторные 14 дней (шаг 3) не нужны: достаточно проверки нуля (ниже) с окном `[24h]`, которое начинается после последнего из событий — обновления последнего экземпляра сервиса и (для `assistant`) окончания повторной миграции. Проверяются все поля `currency`: рост по полю другого сервиса тоже останавливает возврат, его разбирает сервис, отдавший поле, а тишина не расширяется на его `field`. На время возврата владелец продлевает тишину отметками в задаче; предел из шага 1 действует и здесь — через 72 часа с начала отката нужно явное решение владельца. Нет новой отметки — тишина истекает, и алерт включается с той серьёзностью, которая у правила на этот момент: это осознанное следствие, дежурный видит причину по отметке об откате. Порядок: проверка нуля, затем снятие тишины, затем (если по отметке `bank-bff` откатывали) сразу выкладка `bank-bff` без подстановки — перед ней проверку нуля повторяют с окном `[24h]` и концом в момент выкладки, как при правке серьёзности алерта.

  Выкладка `bank-bff` без подстановки — только после шагов 1–5; её дату владелец FIN-98 отмечает в задаче. Откатывать `bank-bff` можно только на версию с подстановкой — не старше первой версии с подстановкой и метрикой `finassist_empty_required_field_total`; более старая пропустила бы пустую `currency` к клиенту. Эту версию владелец FIN-98 записывает в задаче и как минимальную в конфигурацию выкладки `bank-bff`, как у сервисов.

  Правила алерта хранятся в конфигурации мониторинга, отдельно от релиза `bank-bff`, и откат `bank-bff` их не трогает. Серьёзность правила по `currency` владелец FIN-98 меняет на срочную отдельной правкой этой конфигурации до выкладки `bank-bff` без подстановки и только когда проверка нуля с окном `[24h]` выполнена в момент правки; выкладка — только после этой правки. Если счётчик растёт, правку и выкладку откладывают, причину разбирает сервис, который отдал поле, и шаг 3 условия снятия (14 дней) начинается заново. После правки правило срочное всегда, кроме тишины на время аварийного отката (выше).
- пользовательские тексты ошибок помощника: после FIN-224 каталог находится в BFF (5.4), поэтому пустые прежние gRPC `AnswerError.text` / `Message.error_text` не являются дефектом для нового BFF, не управляют `retryable` и не считаются пустыми обязательными полями. До обновления BFF прежний сервис продолжает заполнять их по правилам совместимого внедрения (5.4).
- текст блокировки верхнего уровня (`Block.lock.text`, устаревший `MetricLock.text`) — общий запасной текст «Пока недоступно» для любого `reason` (он же описан у `lock.text` в `api.md` 6.1 и в OpenAPI). Подстановка постоянная — защита экрана, а не допустимое состояние: пустой текст всегда дефект сервиса, и чинят его в сервисе. Внутрь `data` (`google.protobuf.Struct`) `bank-bff` не заглядывает — он переводит блоки один к одному, и новый примитив не требует его релиза. Поэтому пустой текст вложенной блокировки (плитка `tile_group`, `tiles[].lock.text`) не подставляется и в метрику не попадает: этот же текст «Пока недоступно» показывает клиент (`api.md` «Блоки»).

Метрика `bank-bff` — `finassist_empty_required_field_total{field}`. Значения `field`: `Block.lock.text` (только верхний уровень блока), `MetricLock.text`, `GetAnalyticsResponse.currency`, `Message.currency`, `AnswerSnapshot.currency`; «поля `currency`» здесь — последние три, их выбирает селектор `field=~".*\\.currency"`. Новое поле с валютой добавляют в этот перечень, и его значение `field` обязано оканчиваться на `.currency`, иначе селектор его не увидит. При старте `bank-bff` создаёт ряд со значением 0 для каждого значения `field`, чтобы `increase()` по нему всегда вычислялся и первое срабатывание не терялось. Счётчик растёт на 1 за каждое пустое значение поля в каждом ответе (три пустые блокировки в одном ответе — +3; повторное чтение той же записи — снова +1): он считает срабатывания, а не уникальные записи. Растёт и пока действует подстановка, и после её снятия — до того, как `bank-bff` отдаёт ошибку клиенту. `currency` при `has_data = false` не считается. Каждое срабатывание — дефект, разбирается сервис, который отдал поле. Прежние `AnswerError.text` / `Message.error_text` в список нового BFF не входят (5.4).

Проверка нуля — `sum(increase(finassist_empty_required_field_total{field=~".*\\.currency"}[окно])) == 0`, по всем полям `currency` сразу. Сумма по всем рядам (`field` × экземпляр `bank-bff`) даёт одно значение, а `== 0` работает как фильтр: результат непустой — выполнено; пустой (ненулевая сумма или нет данных) — не выполнено. Окно:
- шаг 3 условия снятия — `[14d]`, целиком после отметки шага 2 в FIN-98;
- возврат вперёд — `[24h]`, после последнего из событий (обновление последнего экземпляра сервиса, для `assistant` — окончание повторной миграции);
- правка серьёзности алерта и выкладка `bank-bff` без подстановки (в том числе повторная после аварийного отката) — `[24h]` с концом в момент правки или выкладки.

Момент вычисления: для шага 3 и возврата — не раньше, чем событие (отметка шага 2; последнее из событий возврата) плюс длина окна, иначе окно захватит время до события; для правки серьёзности и выкладки — в момент действия, после шагов 1–5.

Пропуски в сборе. За окно сбор метрики `bank-bff` (метка `job="bank-bff"` — задание сбора `bank-bff` в конфигурации мониторинга) не должен прерываться. Признак — правило записи `bank_bff:scrape_gap = max_over_time(up{job="bank-bff"}[3m]) == bool 0` (`[3m]` — три интервала сбора при сборе раз в минуту; при другом интервале — три его длины): 1 у экземпляра с тремя и больше неудачными сборами подряд, иначе 0, ряд есть всегда. Проверка — `max(max_over_time(bank_bff:scrape_gap[окно])) == 0`, результат непустой — пропусков не было. Одиночные нули завершающегося при выкладке пода, пока его не убрали из обнаружения, пропуском не считаются и шаг 3 не сдвигают. Правило владелец FIN-98 заводит до отметки шага 2: у правила нет истории до создания, и окно должно быть им покрыто целиком. Сбросы счётчика при перезапуске `increase()` учитывает. Не покрыты два интервала, каждый не больше одного интервала сбора: до первого сбора нового экземпляра и после последнего сбора упавшего; срабатывание в них теряется. Для `Message.currency` это закрывает проверка базы (шаг 5). Для `GetAnalyticsResponse.currency` и `AnswerSnapshot.currency` это допустимо, только если дефект повторяется в окне многократно; редкий путь мог попасть лишь в непокрытый интервал, поэтому правка серьёзности и выкладка без подстановки опираются ещё и на шаг 1. Срок хранения: `finassist_empty_required_field_total` и `bank_bff:scrape_gap` хранятся в мониторинге не меньше 15 дней — с запасом для окна `[14d]`; владелец FIN-98 проверяет это до начала шага 3.

Проверка шага 1. Версию отдают сами сервисы метрикой `build_info{job, version}` (`job` — `assistant`, `analytics`). Условие — значение `0` у `count(build_info{job=~"assistant|analytics", version!~"<допустимые>"}) or vector(0)` (без `or vector(0)` при отсутствии недопустимых версий запрос вернул бы пустой результат, а не `0`), где `<допустимые>` — явный список версий, заполняющих поле, из задачи FIN-98 (PromQL не сравнивает версии по старшинству). И по каждому сервису отдельно `count(build_info{job="assistant"})` и `count(build_info{job="analytics"})` равны числу его экземпляров из конфигурации выкладки (проверяют после завершения выкладки, когда старых подов уже нет): исчезнувший экземпляр ряда не даёт, а по сумме недостаток одного сервиса скрылся бы излишком другого.

У нового BFF правил алерта два. Условие каждого — рост счётчика за окно, а не его накопленное значение: иначе срабатывания, ожидаемые при выкладке (старые версии), держали бы срочный алерт и после смены серьёзности — до перезапуска экземпляров `bank-bff`. Точные выражения — под таблицей.

| Правило | Серьёзность |
|---|---|
| `empty_lock_text` | срочное (как `finassist_untranslated_code_total`) |

### 5.4 Общий механизм ошибок (FIN-224)

Общая ошибка — `google.rpc.Status`: классификация `code`, диагностический `message` и типизированные `details`. При отказе unary RPC это транспортный статус; внутри результата, события или истории — вложенное значение, **не** новый отказ успешно выполненного RPC чтения. Общие типы не содержат квот, списаний, названий прикладных операций и выбора восстановления. Причины и параметры — данные, а решение разрешить действие принимает соответствующий usecase. Разрешение новой попытки — отдельное свойство результата; это не разрешение повторить исходный запрос.

| Деталь | Универсальный смысл |
|---|---|
| `google.rpc.ErrorInfo` | Ровно одна причина: `domain: finassist`, открытый `reason` и структурированные `metadata`. `reason` — стандартный UPPER_SNAKE_CASE до63 символов, `[A-Z][A-Z0-9_]+[A-Z0-9]`; ключи metadata — до64 символов, `[a-z][a-zA-Z0-9_-]+`. Параметры дополнительно проверяет адаптер по схеме своего сценария |
| `google.rpc.BadRequest` | Не более одной детали с непустыми нарушениями; каждое имеет машинный `reason`. Описания нарушений — диагностика, не UI |
| `google.rpc.RetryInfo` | Не более одной детали с корректной положительной задержкой, представимой Go duration; **ожидание не является разрешением**. У unary-кодов с обязательной деталью сохраняется прежний `error_spec` |
| `common.v1.RequestRetryInfo` | Не более одной optional typed detail: `bool retryable = 1`. Отсутствие всей детали — разрешение неизвестно; присутствующий `false` — прямой повтор исходного запроса запрещён; `true` — usecase разрешает его в рамках условий метода. Только исходный RPC, никогда новая попытка прикладной операции |

Неизвестные типы `Any` игнорируются как расширение. Некорректная или дублированная **распознанная** деталь делает payload непригодным: положительное разрешение из него не извлекается; unary получает прежний безопасный fallback, вложенный результат — профиль ниже. `Status.message`, `BadRequest.description`, сырой вывод исключений/SQL/провайдеров/моделей не становятся UI-текстом. Каталог безопасного текста и критичности принадлежит BFF, проверяет параметры и оформляет причину; он не принимает бизнес-решений о повторе по имени кода.

**Unary → REST.** `finerr.WithRequestRetryInfo(err, permission)` добавляет или заменяет только эту деталь, сохраняя остальные; permission задаёт сервис/usecase, helper не вычисляет его по коду. Обёртки ошибки не сериализуются в `status.message`: берётся исходный `GRPCStatus`, а не строка `Error()` обёртки. `finerr.ToREST` сохраняет прежние сигнатуру, HTTP-реестр и обязательные параметры `error_spec`, дополнительно выдаёт `REST.RequestRetryable *bool` (nil/false/true). Устаревший сервер без детали не даёт нового разрешения. Пустой/неизвестный reason unary и неполная ошибка по-прежнему дают500 `INTERNAL_ERROR`/`finassist_unmapped_error_total`; дополнительная деталь не превращает неизвестную ошибку в известную.

BFF механически соединяет применимое service-owned разрешение для исходного RPC с доказанной безопасностью **всего** REST-запроса по его контракту: `error.retryable` true только при обеих гарантиях. Разрешение одного дочернего RPC не доказывает безопасность уже выполненных действий других RPC. Отсутствие детали, непроверенный контекст или недоказанное окно ключа — false у нового BFF; сам UUID, HTTP/gRPC-статус, RetryInfo, severity и пользовательский текст ничего не разрешают. Бизнес-переключателей по причинам в BFF нет. Собственные транспортные отказы BFF получают разрешение из соответствующего транспортного обработчика, а не из каталога UI-текстов.

REST `false` останавливает прямой повтор в неизменённом контексте; завершение прежних корректирующих flow (обновление авторизации, один guarded resume экрана `MAINTENANCE`) подчиняется отдельным правилам `api.md`, «Ошибки»: тот же ключ и тело, новый RequestId, фактические проверки безопасности/TTL; повторный отказ не создаёт цикл.

Сервис хранит gRPC-результат, не REST-представление. Разрешение и относительное ожидание повторно оцениваются при выдаче результата, не становятся бессрочным сохранённым обещанием. Время исходного запроса/ключа и TTL относятся к механике операции. BFF/клиент не угадывают их по UUID и часам устройства. `RetryInfo`/`Retry-After` пересчитываются от действительного текущего deadline; после потери временной базы положительное решение не выдаётся. Общие часы/Date/монотонные таймеры — `api.md`, «Время ожидания и часы».

**Вложенная ошибка результата — начальный профиль.** `finerr.NewResultStatus(code, reason, metadata)` создаёт общий payload, `finerr.DecodeResultStatus` выдаёт `ResultError{Code, Reason, Metadata, Violations}` без диагностического message, request-permission и request-delay. Нужны non-OK code и корректный ErrorInfo. Reason открыт и **не обязан** входить в unary ErrorReason/error_spec: новая причина результата не превращается в unary500. В этом профиле RequestRetryInfo и RetryInfo запрещены: RPC чтения/открытия потока успешен, а повтор исходного чтения не равен новой попытке результата. Будущее ожидание новой попытки относится к внешней операции и её реальной временной базе; застывшая относительная задержка не запускается заново при чтении истории. Профиль может расширяться отдельно, без встраивания бизнес-политики в общий Status. Совпадение reason с unary-кодом допустимо и не включает REST-действия: их выбирает контекст REST Error или явно описанного ErrorEvent, а вложенный результат — собственный адаптер сценария (api.md, «Единое отображение ошибок»). Namespace blacklist и lookup unary-реестра в общем декодере не вводятся.

Для нового Go API нужен новый неизменяемый `gen/go` тег владельца **после мержа**, до зависимых PR. Поля/номера/типы прежнего wire и constructor/error_spec существующих кодов не меняются. Новый `google/rpc/status.proto` берётся из закреплённого googleapis BSR-модуля (`buf.yaml`/`buf.lock`), не из локальной копии.

### 5.5 Адаптеры сценариев и совместимое внедрение (FIN-224)

Общий декодер из5.4 не знает следующих причин и не выбирает новую попытку. Эти таблицы описывают только прикладные адаптеры существующих сценариев:

`WatchAnswerResponse.error` остаётся прежним полем7 прежнего типа, `WatchUploadResponse.error` — полем3; новые альтернативы oneof вместо старых не вводятся. Поэтому старый потребитель продолжает распознавать терминальное событие, а не считает его обрывом. Внешний stream RPC после доменного terminal error завершается OK; не-OK транспортный обрыв по-прежнему не становится таким событием.

**Приоритет и dual-write.** Поля Status нет — новый BFF использует прежний адаптер кода/параметров и совместимость FIN-159. Поле есть и корректно — его открытая причина каноническая; старый enum не переопределяет её и не восстанавливает старое действие. Для новой причины без старого enum допустим консервативный `UNSPECIFIED`: нельзя выдавать MODEL_ERROR только ради кнопки повтора. При известной представимой причине legacy-алиас соответствует канонической, расхождение диагностируется, каноническая причина имеет приоритет. Присутствующий некорректный Status даёт безопасный общий текст сценария/метрику, сохраняет внешний failed/terminal исход и не превращается в транспортный обрыв. Фиксированные внешние коды: AnswerErrorEvent.code — INTERNAL_ERROR, Message.error_code failed-истории — INTERNAL_ERROR (не null), StreamError.code импорта — PROCESSING_FAILED. Legacy-код при present-invalid не читается, включая CANCELLED; при absent Status прежняя отмена импорта сохраняется. Корректное явное разрешение новой попытки остаётся отдельным внешним свойством результата; его нельзя вывести из общего Status или несовпадающего старого кода.

В SSE и истории нового BFF открытая каноническая причина переносится как внешний `code`/`error_code`; совпадение с REST-кодом (например, MAINTENANCE/CONSENT_REQUIRED/LIMIT_EXCEEDED) не открывает REST-экран, не запускает auth/квоту/восстановление исходного Ask и не меняет outer result.retryable; при неизвестной каталогу причине — безопасный общий текст сценария и метрика, без raw status.message/параметров. Старые enum/text/error_text заполняются параллельно до обновления всех потребителей. Новый BFF сам формирует внешние user_message/severity и прежние text/error_text из своего контролируемого каталога, не копируя сервисные UI-строки.

Permission новой генерации остаётся в `AnswerError.retryable` / `Message.retryable` и проверяется `RetryAnswer`: это новое действие с новым ключом. В общий Status эта permission не помещается. Модель/квоты/остатки/charged/сбросы не становятся полями общего механизма. Вложенный Status сохраняют без request-retry advice и request-relative delay; при чтении истории не запускают прежний интервал ожидания заново.

Порядок внедрения:

1. После мержа владелец публикует новый gen/go тег; сначала обновляются декодеры BFF/потребителей с поддержкой optional полей, потом producers с dual-write. До введения новых канонических причин фиксируется нижняя граница отката старых потребителей: они должны безопасно переживать legacy UNSPECIFIED и сохранять внешнее domain retryable.
2. Все экземпляры assistant для нового BFF поддерживают FIN-159 `retryable`; список версий/граница отката фиксируются в FIN-225 и конфигурации выкладки. Proto3 bool `AnswerError.retryable` не позволяет отличить отсутствующий старый флаг от false. UI-строка не является маркером возможностей.
3. Unary producers начинают добавлять RequestRetryInfo по решению usecase. Старый BFF новую деталь игнорирует; новый без неё выдаёт false, не подменяет неизвестное разрешение бизнес-переключателем. Включение прежних auto-retry сценариев требует готовности соответствующего producer; старые/неполные cached ошибки не дают положительного разрешения.
4. Реальная оговорка replay: текущий go-idempotency при сохранённом телефонном RATE_LIMITED с абсолютным RetryAt пересоздаёт finerr.RateLimited и теряет дополнительные детали. Это не исправлено данным PR. Путь должен сохранить/пересчитать advice в отдельной библиотечной/сервисной реализации до положительного разрешения; отсутствие детали — консервативный false. Обычный go-grpc normalize и protobuf-сериализация Status сохраняют Any, но сами не закрывают этот специальный путь.
5. После обновления всех BFF и фиксации нижней границы отката сервисы могут прекратить формировать прежние UI-строки; protobuf-поля остаются. Прежний empty_answer_error_text относится только к старому BFF, его правило снимается при миграции, до прекращения заполнения строк. Проверки currency/lock из5.3 сохраняются. Runtime, deploy и мониторинг этим контрактным PR не заявляются выполненными.

Реализация адаптеров/каталога — FIN-225 после отдельно согласованной основы FIN-268; Android/fake — FIN-223. Переименование семейства прикладных Answer-ресурсов/RPC не входит в эту миграцию.

## 6. Идемпотентность

Правило `architecture.md` переносится без изменений: ключ хранит сервис-владелец эффекта, в одной транзакции с эффектом. В gRPC:

| REST | RPC | Хеш запроса | Срок |
| --- | --- | --- | --- |
| 1.1 | `AuthService/StartPhoneVerification` | сериализация запроса (deterministic marshal) | 24 ч; `RATE_LIMITED` на дубль — до его `retry_at` |
| 1.3 | `AuthService/Register` | то же | 24 ч |
| 1.4 | `AuthService/RefreshTokens` | то же | 60 с, ответ зашифрован |
| 3.2 | `StatementsService/UploadStatement` | `SHA-256(SHA-256(содержимое) ‖ file_name)` — формула ниже | 24 ч |
| 7.1 | `AssistantService/AskQuestion` | сериализация запроса | 24 ч |
| 7.4 | `AssistantService/RetryAnswer` | `answer_id` | 24 ч |

- Сохраняется пара (gRPC-код + `ErrorInfo`, либо сериализованный ответ), а не REST-ответ: `bank-bff` при повторе получает то же, что в первый раз, и переводит так же. Сохраняются только исходы, соответствующие REST `2xx/400/413/422` (кроме `FILE_TOO_LARGE` в `UploadStatement` — ниже); исключение — `RATE_LIMITED` на дубль в `StartPhoneVerification` (номер занят у провайдера), он хранится под ключом до своего `retry_at` (api.md, «Идемпотентность»; 7.1). Кроме того, у ответа `StartPhoneVerification` поле `expires_in` не берётся из сохранённого ответа: `user` пересчитывает его из `expires_at` в момент отправки (после `expires_at` — 0). Для `RATE_LIMITED` на дубль хранится абсолютный `retry_at`, а не готовый статус: при повторе сервис собирает ошибку заново через `finerr.RateLimited(retry_at)`, так что `RetryInfo` (и `Retry-After` в REST) пересчитывается от текущего момента и не расходится с телом; остальные детали те же. Без `RetryInfo` `bank-bff` отдал бы 500 (раздел 5.1).
- В `StartPhoneVerification` поиск ключа включает долговечную попытку без кэша ответа после 5xx. Она продолжается по долговечному состоянию на шаге ключа, до лимитов и занятости: первый вызов без отметки либо сверка после отметки (7.1), без повторного списания попытки и повторного confirm/Start; другое тело — конфликт, активный исполнитель — REQUEST_IN_PROGRESS. Неизвестный ключ при известной занятой внешней заявке получает обычный дубль; при неизвестном исходе другой попытки — тот же RATE_LIMITED-дубль с retry_at = сохранённый unknown deadline (default 5 минут), округлённый вверх до минуты. На этом сроке unknown attempt закрывается/номер освобождается с принятым риском, старые ключи сохраняют терминальное состояние (7.1). Определённый отказ без созданной заявки закрывает попытку и требует нового ключа для нового действия; это состояние попытки, а не сохранённый 5xx-ответ (7.1).
- Хеш `UploadStatement` (FIN-297) — не по сериализации потока, а по формуле `request_hash = SHA-256(SHA-256(содержимое) ‖ file_name)`: первая часть — 32 байта SHA-256 всех байтов файла (конкатенация `chunk` в порядке потока), вторая — байты `UploadHeader.file_name` в UTF-8, `‖` — конкатенация без разделителя. Первая часть всегда ровно 32 байта, поэтому граница однозначна: разные пары «содержимое, имя» не дают одной строки на входе внешнего SHA-256. `file_name` берётся как передан в запросе, без нормализации (регистр, Unicode-нормализация, пробелы, расширение не меняются) — то самое значение, которое сохраняется и показывается в «Истории загрузок»; пустое имя — пустая вторая часть. Тот же ключ, то же содержимое, другое имя — `IDEMPOTENCY_CONFLICT`: иначе повтор вернул бы загрузку со старым именем. Хеш не зависит от схемы protobuf, поэтому ложного конфликта после деплоя у загрузки нет. Хеш известен только после последнего `chunk`, поэтому сохранённый исход ищется и хеш сверяется в конце потока: повтор с тем же ключом дочитывается, и сохранённый ответ (или `IDEMPOTENCY_CONFLICT`, `REQUEST_IN_PROGRESS`) отдаётся после последнего `chunk`. `FILE_TOO_LARGE` у `UploadStatement` — исключение из сохраняемых `413`: сервис отвечает им до конца потока (по `header.size_bytes` — до первого `chunk`), когда хеша ещё нет, и под ключом его не сохраняет; ключ при этом не проверяется. Повтор выполняется заново и так же дёшево получает тот же `413` — исход зависит только от размера.
- Хеш — `proto.MarshalOptions{Deterministic: true}` + SHA-256. Детерминизм гарантирован только для одного бинаря; после деплоя с изменённой схемой сообщения хеш повтора может не совпасть → ложный `IDEMPOTENCY_CONFLICT`. Окно — 24 ч после релиза, затрагивает только повторы, пересёкшие деплой; принимаем (решено 14.10.2026: хеш считает сервис по protobuf; вариант с канонизированным телом REST в `bank-bff` отклонён как лишняя сложность).
- Внутренние вызовы с эффектом идемпотентны по конструкции и ключа не требуют: `UpsertUserMetrics` (версии), `SetUserTimezone` (версия настроек), `PurgeUserData` (повтор — OK), `DismissRegularPayment` / `ChangeCategory` (присваивание).

### 6.1 Outbox

Решено 14.10.2026. Все фоновые вызовы между сервисами (`SetUserTimezone`, `PurgeUserData`, `UpsertUserMetrics`) идут через transactional outbox на PG, без брокера. Механизм один — общая Go-библиотека (рядом с библиотекой идемпотентности, FIN-78).

- **Запись.** Изменение и событие фиксируются в одной транзакции БД производителя: например, `UPDATE profile SET timezone = …, settings_version = settings_version + 1` и `INSERT INTO outbox`. Либо оба, либо ничего; падение пода после `COMMIT` событие не теряет.
- **Событие, а не вызов.** Строка outbox — тема (`user.timezone_changed`), ключ (`user_id`) и payload (protobuf). Список получателей темы и метод, которым доставлять, — в конфигурации доставщика, а не в коде производителя: новый получатель добавляется без правки производителя. Доставщик раскладывает событие на задания по получателям и доставляет их независимо.
- **Таблица** (примерно): `outbox(id int8 GENERATED ALWAYS AS IDENTITY, topic text, key text, payload bytea, target text, attempts int4 DEFAULT 0, next_attempt_at timestamptz, last_error text, created_at timestamptz DEFAULT now())`, индекс по `next_attempt_at`.
- **Доставщик** — горутина в каждом поде производителя. В транзакции берёт пачку: `SELECT … WHERE next_attempt_at <= now() ORDER BY id LIMIT 50 FOR UPDATE SKIP LOCKED` (поды разбирают разные строки); по каждой — системный gRPC-вызов получателя с токеном ServiceAccount, дедлайн 30 с. Успех — `DELETE`; ошибка — `attempts + 1`, `next_attempt_at` по экспоненте (1 с, 2, 4… до 5 мин, с джиттером), `last_error`. Будится через `LISTEN/NOTIFY` после записи, плюс опрос раз в несколько секунд для надёжности.
- **Получатель идемпотентен**: доставка at-least-once, порядок не гарантирован. Применяет только при большей версии (`settings_version`, `calc_version`), иначе отвечает OK без действий; для удалённого пользователя (tombstone) — OK без действий, чтобы строка не висела.
- **Наблюдаемость:** метрики возраста самой старой строки и числа строк по получателю; алерт, если строке больше часа; причина застревания — в `last_error`.
- **После MVP — брокер** (Redpanda или Kafka) на месте доставки: доставщик (или CDC по WAL) переносит события из outbox в топик, получатели читают топик тем же обработчиком. Outbox при этом остаётся — атомарности записи в PG и публикации в брокер иначе не получить. Производители и обработчики не меняются, потому что библиотека с первого дня работает с событиями и конфигурируемыми получателями. Когда переходить: получателей и тем станет много, понадобится журнал событий с повторным чтением или поток в ClickHouse.

### 7.1 `user`

REST 1.x и 2.x один к одному. Дополнительно:

#### Согласие и возраст до телефонного провайдера (FIN-363)

`StartPhoneVerificationRequest` добавляет `pd_consent_accepted` (bool, поле 2), `pd_consent_version`
(string, поле 3, 1–64 Unicode-символа) и `age_confirmed` (bool, поле 4). Требуются true, актуальная
версия PERSONAL_DATA и отдельное подтверждение 14+. `user` проверяет это сам, в том числе при прямом RPC:
отсутствующие scalar-поля декодируются как false/пустая строка и не дают обхода. Порядок после ключа —
лимиты и занятость номера (RATE_LIMITED), формат/возраст/границы версии (VALIDATION_ERROR; для возраста
field=age_confirmed, code=REQUIRED), согласие (CONSENT_REQUIRED), актуальность версии (CONSENT_OUTDATED).
Новые error_spec и коды не вводятся. REST дополнительно отклоняет отсутствие обязательных полей до ключа
по схеме. Существование аккаунта не влияет на проверки и не раскрывается до подтверждения номера.

После проверок, но до внешнего вызова `user` в одной транзакции резервирует попытку и сохраняет отдельное
долговечное доказательство: ID попытки, phone, ключ и хеш всего запроса, тип/версию и доступ к неизменяемому
тексту документа, принятые согласие и возраст, UTC-время первого приёма каждого подтверждения и доверенный
`x-client-ip` из BFF. Вызов провайдера — после commit, вне `db.Run`; ошибка БД/commit запрещает передачу.
До verified это подтверждения неустановленного заявителя, не доказанное владение телефоном: нельзя
приписывать их найденному по phone аккаунту. После verified существующий аккаунт получает ссылку на это
доказательство до выдачи токенов; новый — атомарно с созданием и расходованием registration_token в Register.
Прежние события согласий не перезаписываются; повторная доставка результата не создаёт новое согласие.
Каждый отдельный принятый Start сохраняет собственные время и доверенный IP даже при той же версии и
повторном входе: п. 3.3 Политики задаёт фиксацию получения каждого согласия, а FIN-363 — доказательство до
каждой отдельной передачи телефона. У связанного подтверждённого аккаунта эти записи сохраняются весь
установленный срок; дедупликация до одного согласия на версию/короткое хранение повторных входов не согласованы.
Состав ограничен phone, типом/версией, полученными подтверждениями/временем согласия и возраста, IP и связью
с запросом; IP и события Watch/RefreshTokens или иных последующих обращений в доказательство не добавляются.

Попытка без окончательного ответа находится на шаге ключа до лимитов/занятости, в том числе после 5xx:
другое тело — IDEMPOTENCY_CONFLICT, активный исполнитель — REQUEST_IN_PROGRESS с RetryInfo. Иначе она
продолжается по долговечному состоянию без повторного списания и 429 против собственной резервации.
Локальный timeout неизвестного исхода — PHONE_VERIFICATION_UNKNOWN_TIMEOUT, default 5m, startup validation
Go duration в диапазоне 1s..5m; некорректное значение запрещает запуск. Hot reload/новых REST-полей нет.
При первом успешном приёме абсолютный deadline = приём + тогдашняя настройка сохраняется один раз;
смена env/перезапуск, исполнитель/повтор/сверка его не пересчитывают и не продлевают. Фиксированный
provider TTL 5 минут, expires_at известной заявки и 15 минут verified-результата не параметризуются этим env.
До первого внешнего вызова единственный исполнитель атомарно сохраняет отметку «вызов мог начаться» и
конечный dispatch_not_after, не позже этого срока. Только впервые записавший её вправе сделать один
первый вызов строго до границы, с дедлайном не позже неё; позже отправлять не вправе и он. При существующей
отметке — только читающая сверка, даже после crash между commit и отправкой. Retry-middleware и повторный
confirm/Start старой попытки запрещены навсегда, истечение аренды исполнителя этого не меняет.

До локального срока неизвестный исход удерживает номер в карантине. Новый ключ получает существующий
RATE_LIMITED-дубль (429), retry_at = сохранённый unknown deadline, округлённый вверх до минуты, без confirm.
Кэш до retry_at, пересчёт RetryInfo/Retry-After и phone/x-client-ip accounting — общие правила дубля:
исполнение списывает попытку один раз на окно до retry_at; replay до него не списывает, после него ключ
выполняется заново. Лимиты проверяются до состояния: лимитный RATE_LIMITED не проверяет карантин,
не списывает попытку и не кэшируется. Это не меняет recovery/терминальный учёт исходного unknown-ключа.

При внутренней ошибке продолжения до локального срока true допустим только при доступном проверенном
читающем пути сверки: явный RequestRetryInfo{retryable: true}, иначе false. BFF соединяет permission
с доказанной safety всего запроса. Разрешён тот же запрос/ключ: без отметки один первый вызов до границы,
после неё только сверка, без повторного confirm/списания/продления TTL. «Не найдено» не означает
определённого отказа: запрос мог ещё не дойти/не появиться в чтении. Проверенный окончательный ответ
первого вызова, гарантирующий отсутствие созданной заявки (кроме provider duplicate), закрывает попытку
раньше срока; тот же ключ получает INTERNAL_ERROR с явным false.

На локальном сроке при всё ещё неизвестном исходе рабочая попытка атомарно закрывается как неудачная,
карантин/phone-fence освобождаются и новая независимая попытка разрешена. Владелец выбрал сохранённый
unknown deadline с default 5 минут от первоначального приёма, приняв риск поздней внешней заявки, ещё действующей прежней заявки и дубля
(28.10.2026). HTTP timeout/локальное закрытие не доказывают отсутствие удалённого принятия и не отменяют
внешнюю заявку. Глобального provider-off/требования гарантии верхней границы Zvonok для обычного создания нет.
Уже авторитетно установленный и сохранённый результат следует обычным срокам известной заявки/15 минутам
verified. Поздние webhook/исполнитель/сверка не открывают закрытую попытку, не выдают старые токены/результат
и не переносят прежнее подтверждение новой заявке; рабочие recovery jobs прекращаются при закрытии.

По unknown deadline закрывается рабочее состояние, а не удаляется весь архив. Терминальное состояние,
request_hash и связь старого ключа с доказательством сохраняются отдельно не меньше обычного 24-часового
окна ключа, в пределах retention доказательства. Тот же ключ/тело получает INTERNAL_ERROR с явным false,
другое тело — IDEMPOTENCY_CONFLICT; без confirm, восстановления pending, смены времён и списания. Это
терминальное правило исходного unknown-ключа; 429 новых ключей следует отдельному кэшу до retry_at. Физическое удаление рабочей строки допустимо
лишь с сохранением этих отдельных записей; активный fence после срока не удерживается. В обычном
окне старого ключа новое действие использует новый ключ и проходит все gates с новым доказательством.
Replay/конфликт/учёт действуют 24 часа с первого приёма ключа, не unknown deadline + 24 часа; физическое
хранение архива до proof retention не продлевает lookup/replay. После окна тот же UUID трактуется как
fresh-запрос по общему правилу, с новой попыткой и всеми проверками; архивная заявка не восстанавливается. Завершение/очистка сериализуются
с записью результата/привязкой к аккаунту, другие live account/attempt данные не удаляются, квота не возвращается.

Zvonok confirm может вернуть прежний ID незавершённой заявки. Доверенные поля — provider created,
call_id/phone, call_status (legacy status), completed и пул. Ключ (provider, настроенная campaign, call_id)
атомарно уникален между live attempts и сохраняемыми архивами. Campaign устанавливается из доверенного
запроса к настроенной кампании/проверенного binding, не из клиента и не отсутствующего поля ответа.
Чужой binding ID — существующий RATE_LIMITED 429 по правилу provider duplicate, без перепривязки.

Для unbound ID C нужны одновременно: same phone/campaign; provider created в интервале
[C.first_dispatch_at.Truncate(1ms), получение первого authenticated confirm-ответа], не future;
first_dispatch_at — сохранённое серверное начало первого confirm, не часы клиента/нового retry. При
read-only recovery после потери ответа верхняя граница — получение этого authenticated чтения, только
пока C открыта и её unknown deadline не наступил. Точность — 1 ms; произвольное расширение/локальная
подстановка времени запрещены. Первое связывание требует pending new/wait/in_process, completed null/zero,
не pincode_ok/terminal, валидный пул 1–1000 distinct E.164 и usable remaining lifetime.
expires_at = provider.created + фиксированные 5 минут; expires_in от него, не от C/sent/recovery. Created
раньше нижней границы — старый вызов/429-дубль; неизвестные/противоречивые поля или непроверяемое время —
безопасная внутренняя ошибка без binding/proof. Сам closed unknown archive телефона не создаёт 500/новый lock.

Уникальный ID/binding и все условия проверяются атомарно с сохранением результата, включая C open и
now < сохранённого unknown deadline, независимо от cleanup job. Late A, неразличимый внутри того же
интервала, остаётся принятым поздним риском, без выдуманного TTL/наследования подтверждённого результата.
Первое связывание не принимает terminal/pincode_ok; дальнейший proof — только authenticated проверка
текущего binding. Повтор ID C не меняет created/TTL. Нынешний Recover снова confirm не допускается,
FIN-364 заменяет его действительно читающим путём.

Late executor A с причинным контекстом может дописать только ID/created/фактический expiry в ещё живой
архив A без reopen/auth/продления retention. Уникальность атомарна: уже связанный C ID не отнимается.
Webhook не несёт AttemptID; ct_phone/наличие архива не позволяют угадать A. После authenticated call_by_id
он обновляет архив лишь по уже существующему однозначному binding; иначе unknown-call/ignore, без нового
binding. Наблюдение не является условием входа, не вводит карантин и не воссоздаёт удалённый архив.

Доказательство переживает provider error и закрытие/истечение рабочей заявки. Для брошенной регистрации
без созданного аккаунта/связи с подтверждённым существующим аккаунтом оно хранится отдельно 24 часа после
окончания срока заявки (28.10.2026). При неустановленном внешнем сроке опора — первоначально сохранённый unknown deadline
(приём + тогдашний PHONE_VERIFICATION_UNKNOWN_TIMEOUT), затем ещё 24 часа; закрытие/освобождение/сверка срок не продлевают. В этом архивном сроке допустимы
терминальные key records без active phone-fence и восстановления эффекта. Связанные с подтверждённым
аккаунтом доказательства хранятся отдельно с отдельными правами доступа 3 года после удаления/отзыва,
как в п.3.3 Политики; первоначальные времена не меняются.

На конце retention брошенного доказательства удаляются относящиеся к нему PII/производные: evidence,
phone/IP, request_hash/key/resource bindings, token hashes/result ciphertext, персональные recovery jobs
и старые связи 429 других ключей с этой попыткой. Кэш этих отказов живёт до retry_at и не продлевает
retention; если позже тот же ключ создал независимую заявку, её новые ресурсы не удаляются этим cleanup. Нет бессрочной записи с телефоном/производным ради fencing;
каскад working request по unknown deadline не удаляет архив, архив не продлевает активный lock. Очистка
сериализуется с привязкой доказательства к аккаунту и не затрагивает другие live account/attempt записи.
Удаление архивов не позволяет оживить старые токены, результаты или внешнюю отправку. Это требования
к FIN-364, а не подтверждение текущей реализации.

При повторе уже принятой попытки используется её версия, даже если текущий документ изменился. Срок
заявки и 15 минут результата verified не меняются. Register сохраняет поля 2/3: false — CONSENT_REQUIRED,
версия не равна доказательству — CONSENT_OUTDATED; current_version заново не сравнивается, время согласия
не меняется. Новая попытка с новым ключом требует текущего документа. При отсутствии доказательства
Watch/Register возвращают INVALID_TOKEN на шаге токена; поля Register не заменяют его.

**Внедрение:** PR FIN-363 → merge владельцем → неизменяемый gen/go-тег владельца → FIN-364 (`user` и BFF)
и FIN-365 (Android/mock). Публикация контракта не включает runtime-проверки. До включения серверного запрета
новых обязательных полей подготовить поддерживающий Android/mock, BFF-преобразование и user с новой схемой;
на точке переключения инвалидировать старые pending/results без доказательств, включая секреты из
сохранённых ответов StartPhoneVerification. После серверного момента переключения Watch/Register старых
заявок не выдают/не доставляют пару или registration_token. Установленная сессия для этой миграции —
пара access/refresh, выпущенная и надёжно сохранённая сервером до переключения, независимо от первого
RefreshTokens/закрытия заявки. Её refresh только из-за отсутствия нового доказательства не отзывается,
а первый RefreshTokens работает по прежним правилам. Доставленная до переключения пара остаётся рабочей;
сохранённую, но недоставленную пару старый Watch после переключения уже не возвращает. Register,
успешно завершённый до переключения, также создаёт установленную сессию; старый registration_token
без доказательства после переключения аккаунта не создаёт. Минимальная версия
клиента может направлять старые приложения на обновление, но не заменяет серверных проверок полей.
После переключения откат на user/BFF, допускающие внешнюю передачу без доказательства, запрещён; отказ
нового кода требует исправления либо остановки телефонного входа. Новые обязательные REST-поля —
несовместимый инкремент альфы, принимаемый владельцем меткой breaking-accepted; protobuf расширен добавлением.

#### Остальные правила user

- **Вебхук провайдера обратного звонка** — HTTP-эндпоинт `user` на ingress (отдельный маршрут, белый список адресов провайдера, подпись), мимо `bank-bff`. В gRPC-контракт не входит. Номер подтверждения общий для многих заявок, поэтому вебхук сопоставляется с заявкой по номеру звонившего: засчитывается только звонок с номера действующей заявки.
- **`StartPhoneVerification`** — срок заявки (`expires_at`) задаёт `user`: сейчас 5 минут с создания, это срок заявки у провайдера (не меняется). Порядок: сначала ключ идемпотентности — повтор с тем же ключом получает сохранённый ответ (раздел 6), и после `expires_at` тоже, тот же ключ с другим телом — `IDEMPOTENCY_CONFLICT`, без проверок ниже; для неизвестного ключа — сначала лимиты верификаций на номер и `x-client-ip` (при превышении — `RATE_LIMITED` с `retry_at` по лимиту, занятость номера не проверяется), затем занятость номера. Два понятия: **действующая заявка** — не закрыта: `pending` до `expires_at` или `verified` с неиспользованным результатом до 15 минут с подтверждения звонком (срок результата и `registration_token` отсчитывается от `verified`; закрывают первый `RefreshTokens` с выданным refresh или `Register`), от неё зависит повторная доставка результата; **номер занят у провайдера** — до `expires_at` последней заявки на номер, закрыта она или нет: провайдер не принимает повторную заявку на тот же номер до конца срока предыдущей. `user` определяет занятость по своей БД и для занятого номера отвечает `RATE_LIMITED` без вызова провайдера, без `verification_token` чужой заявки, с `retry_at` = `expires_at` последней заявки, округлённым вверх до целой минуты (22:16:20 → 22:17:00; точный срок чужой заявки не раскрывается). Отказ провайдера по дублю при свободном по БД номере — рассогласование: лог и метрика `finassist_phone_verification_provider_duplicate_total`, клиенту — `RATE_LIMITED` с `retry_at` = время запроса + 5 минут, округлённое вверх до минуты. Оба отказа по дублю сохраняются под ключом до своего `retry_at` (хранится `retry_at`; повтор с тем же ключом до `retry_at` получает `finerr.RateLimited(retry_at)` с задержкой от текущего момента, занятость не перепроверяется; после `retry_at` выполняется заново) и засчитываются в лимитах на номер и `x-client-ip`: попытку списывает выполнение, а не воспроизведение, поэтому один `idempotency-key` учитывается не больше одного раза на каждое окно до `retry_at`. `RATE_LIMITED` по лимиту не сохраняется и попытку не списывает.
- **`WatchPhoneVerification`** — первый ответ из БД, дальше `LISTEN/NOTIFY` по ID заявки (только primary). Дедлайн потока — `expires_at` + 10 с. Серверный лимит запросов (попыток подключения) за окно на `x-client-ip`, как у `Register` и `RefreshTokens` (значение задаёт `user`, в контракте не фиксируется; считаются и попытки, отклонённые по токену; отдельный потолок одновременных потоков с адреса — на усмотрение сервера, к защите токена не относится): сверх лимита — `RATE_LIMITED` с `retry_at` до первого сообщения потока и до проверки `verification_token`, чтобы подбор токена упирался в лимит.
- **Лимиты до проверки токенов**: у `WatchPhoneVerification` (попытки подключения), `Register` и `RefreshTokens` — серверный лимит запросов за окно на `x-client-ip` (значения задаёт `user`, в контракте не фиксируются); он проверяется после ключа идемпотентности и до проверки токена из запроса (`verification_token`, `registration_token`, `refresh_token`) — сверх лимита `RATE_LIMITED` с `retry_at`, подбор токена упирается в лимит.
- **`UpdateProfile` с `timezone`**: в той же транзакции — строки outbox `SetUserTimezone{user_id, timezone, settings_version}` (`settings_version` — `int32`) для `bank-statement-data` и `assistant` (по строке на получателя, доставляются независимо). При регистрации — так же, с поясом из 1.3. `bank-statement-data` пересчитывает агрегаты и первым делом отправляет в `analytics` `recalculating = true` — до этого `GET /v1/analytics` может несколько секунд отдавать старые цифры без признака пересчёта. Принимаем.
- **`DeleteAccount`**: синхронно — tombstone пользователя, отзыв всех refresh, строки outbox `PurgeUserData` для трёх сервисов; ответ OK. Повтор для уже удалённого — OK (tombstone найден). Outbox ретраит до успеха с экспоненциальной паузой; алерт, если строка старше часа.
- **Tombstone в каждом сервисе данных**: после `PurgeUserData` сервис помнит `user_id` и отвечает `TOKEN_REVOKED` на любой вызов от его имени. Иначе живой 15 минут access-токен успел бы загрузить выписку или задать вопрос уже после удаления, и данные появились бы снова. До прихода `PurgeUserData` (секунды) окно остаётся — закроется мгновенным отзывом access-токенов после MVP (`session_version`).
- **`GetSigningKeys`** — JWKS для локальной проверки JWT. Кэш в каждом сервисе: обновление раз в 10 минут и при неизвестном `kid` (не чаще раза в минуту). Отдельный HTTP `/.well-known/jwks.json` не нужен — все потребители внутри.

- **Лента и поиск — два RPC**, а не один с режимами, как в REST. Режим выбирает `bank-bff` по наличию фильтров; `before` вместе с фильтрами — 400 на `bank-bff`. Типы ответов разные, сервису не нужно ветвиться.
- **Исключение платежа из регулярных («не подписка») живёт в `bank-statement-data`**, хотя путь REST под `/v1/analytics`: отметка меняет распознавание регулярных платежей и вызывает пересчёт. `bank-bff` маршрутизирует путь в `RegularPaymentsService`. `analytics` про отметки не знает — получает пересчитанную метрику `insights.regular_payments`.
- **Запись по `occurred_at` и `id`** (решение владельца 20.10.2026, FIN-202): `GetOperation` и `ChangeCategory` получают вместе с `id` время совершения записи `occurred_at` — то, что клиент видел в ленте или поиске (api.md 4.2, 4.3). Поле обязательное (`buf.validate.field.required`): нет — `VALIDATION_ERROR` с нарушением у `occurred_at` от интерцептора. Сервис ищет запись по `(user_id, occurred_at, id)` — точное равенство момента, одна секция года; не нашёл — по `(user_id, id)` во всех секциях, потому что время записи меняется (холд проведён, повторный импорт). Неверное время — не ошибка; записи нет и так — `NOT_FOUND`. Чтобы значение из ленты возвращалось без потерь, `bank-bff` форматирует `occurred_at` с точностью хранения: доли секунды выводятся, если они не нулевые (api.md 4.2). Поле обязательно с этой версии контракта для всех сторон сразу: продовых клиентов нет, порядок выкатки не нужен (решение владельца 20.10.2026).
- **Таймаут разбора — 3 минуты** с начала (решение владельца 17.10.2026, FIN-159): разбор, не завершившийся за это время, в том числе прерванный падением пода, `bank-statement-data` завершает `IMPORT_ERROR_CODE_PROCESSING_FAILED` — фоновой проверкой загрузок в `PROCESSING` старше 3 минут, независимо от того, какой под вёл разбор. Как при любой ошибке, ничего не сохраняется, файл удаляется, а итог остаётся у записи загрузки для `WatchUpload`.
- **Загрузка**: `bank-bff` не держит файл целиком — режет multipart-поток на куски по 256 КиБ и шлёт первым сообщением `UploadHeader`. Сервис считает SHA-256 на лету, пишет файл во временный объект Object Storage, на исходе потока проверяет формат и банк и только тогда создаёт загрузку и отвечает. При `FILE_TOO_LARGE` сервис отвечает ошибкой, не дочитывая поток; `bank-bff` закрывает приём от клиента. Дедлайн — 60 с.
- **Поиск до 10 000 операций** — до ~3–4 МиБ в protobuf. `bank-bff` поднимает `MaxCallRecvMsgSize` до 16 МиБ только для этого метода; сервис — `MaxSendMsgSize` так же.
- **Инструменты помощника** (`AssistantToolsService`) — только чтение, системная модель. Набор минимальный и расширяемый:
  - `GetDataOverview` — границы данных, покрытие по месяцам, список полей, которые поставляют источники («нет» ≠ «неизвестно»), версия данных. Идёт в системный промпт.
  - `AggregateOperations` — суммы и счётчики по месяцу / категории / продавцу по правилам аналитики (`transfer_mode` обязателен). У каждой группы — `filters` (готовый переход к операциям), у продавца — токен `selection` (`s_merchant_…`).
  - `FindOperations` — ограниченный список операций (до 100).
  - `GetDataVersion` — для `changed_since` в истории диалога.
  - Правило возврата попытки («функция вернула блокировку или пустой охват») сервер `assistant` проверяет по `bounds.coverage == NO_DATA` в ответах инструментов и по `status == LOCKED` в метриках `GetAnalytics`.
- **Закрытие непрочитанных строк** (FIN-79): в транзакции успешного импорта `bank-statement-data` закрывает строки прежних загрузок, которые новая загрузка дочитала или заменила своей записью (правила — api.md 3.6, «Закрытие строк»), и помечает затронутые месяцы для пересчёта — `unread_lines_count` снимков `analytics` считает только незакрытые строки. Затронутые месяцы — месяцы дат закрытых строк, а для строк без даты — все месяцы периода их загрузки по этому счёту. Шаг закрытия сериализуется по пользователю (блокировка пользователя до конца транзакции). При удалении загрузки строки, которые она закрыла, проверяются заново в той же транзакции; для пересчёта помечаются месяцы и снова открытых строк, и собственных незакрытых строк удаляемой загрузки (они пропадают из счёта; для строки без даты — все месяцы периода загрузки). Блокировку пользователя берут первым действием транзакции или выполняют шаг закрытия в `READ COMMITTED` (api.md 3.6).
- **Пороги полноты данных** («нужно 3 полных месяца») живут в реестре метрик `bank-statement-data` (FIN-6) и попадают наружу уже вычисленными: в `ImportCoverage.features` итога импорта и в `lock` метрик для `analytics`. Других мест с порогами нет.

### 7.3 `analytics`

`analytics` хранит готовые метрики и собирает из них ответ `GetAnalytics`. Сам он не считает ничего, кроме того, что зависит только от текущего времени и уже переданных данных:

- точный ключ периода по `period` + `period_key` (`quarter` + `2026-09` → `2026-Q3`) в поясе пользователя;
- `is_current` — `now` внутри `range`;
- `stale` — `now ≥ stale_after` (порог присылает `bank-statement-data` готовым моментом, `analytics` его не знает). `stale_after` — начало 15-го календарного дня после последнего покрытого выпиской дня (`DTEND` по всем загрузкам, в том числе без операций) в поясе пользователя, а не от последней операции (FIN-124); тот же момент `bank-statement-data` использует для `FeedState.stale` ленты и блокировки прогноза `stale_data`;
- `navigation`, `ListPeriods` — по списку периодов, для которых есть снимки. Поэтому `bank-statement-data` присылает снимок на **каждый** период, где есть хоть один покрытый выпиской день, в том числе без операций (метрики по своим правилам: обычно `none`, но метрики с базой вне периода считаются — например, `small_frequent` неполного месяца по последнему полному месяцу до него), и удаляет (`removed_periods`) период, в котором покрытых дней не осталось (api.md 6.2, FIN-127);
- сборка дерева ответа из плоских снимков метрик.

**Модель записи.** `bank-statement-data` присылает `UpsertUserMetrics`: состояние пользователя (`UserDataState`) и снимки периодов (`PeriodSnapshot` на ключ `(период, ключ, transfer_mode)`), каждый — полный набор метрик периода с ID из реестра (`tiles.expense`, `tiles.expense.comparison`, …, `insights.small_frequent`). Каждая метрика — общий `Metric` (`status`, `lock`, `basis`, `filters`, `value_minor`, `range`) плюс типизированные `details` для карточек со списками. Единица замены — период `(период, ключ)`: оба его снимка (`transfer_mode` с переводами и без) всегда приходят в одном вызове `UpsertUserMetrics`, а `analytics` применяет вызов одной транзакцией — период заменяется сразу в обоих режимах (FIN-196). `analytics` это правило не проверяет и вызов не отклоняет: единственный вызывающий — системный `bank-statement-data`, ответственность на нём; период с одним режимом в вызове применяется как пришёл, а `analytics` пишет предупреждение в лог и увеличивает метрику `finassist_incomplete_period_snapshots_total` (раздел 9, «Метрики»). **Новое поле в данных записи** (FIN-284): `analytics` хранит метрики нормализованно — колонками и `details` в виде JSON по известной ему схеме — и сохраняет только поля, которые знает его выпуск; неизвестные поля protobuf и неизвестный вариант `details` отбрасываются без ошибки. Поэтому новое поле в `UpsertUserMetricsRequest` или во вложенных в него сообщениях (`UserDataState`, `PeriodSnapshot`, `PeriodRef`, `MetricSnapshot`, `Metric`, `MetricLock`, `MetricBasis`, `OperationsFilter` и другие общие типы) или новый вариант (поле) `details` выкатывается так: сначала `analytics` (колонка и отображение), затем `bank-statement-data` начинает его присылать. В обратном порядке `analytics` молча теряет значение до первого пересчёта затронутых периодов после своей выкатки — без ошибки и алерта. Новое поле-инструкция верхнего уровня запроса (по образцу `removed_periods`) в обратном порядке теряется навсегда, а не до пересчёта: старый `analytics` отбрасывает его и подтверждает вызов, строка outbox удаляется, и повторно инструкция не придёт. Порядок тот же, что для нового значения перечисления (раздел 8: сначала потребитель, потом производитель). Новый `metric_id` выкатки `analytics` для сохранения не требует — строка метрики сохраняется, но отображается только после выкатки композиции `analytics` (комментарий к `MetricSnapshot` в `analytics.proto`).

**Версии.** `calc_version` (`int32`) — монотонная последовательность пользователя в `bank-statement-data`. `analytics` применяет снимок периода и состояние, только если версия не меньше сохранённой для этого ключа; иначе подтверждает и пропускает. Удаление периода (`removed_periods`) подчиняется тому же правилу версий для ключа `(период, ключ)` в обоих режимах переводов: `analytics` хранит версию удаления как надгробие ключа; снимок с `calc_version` меньше версии надгробия пропускается как устаревший, удаление с версией меньше версии сохранённого снимка или существующего надгробия тоже пропускается — версия надгробия только растёт; удаление сравнивается с бо́льшей из сохранённых версий двух режимов (период с одним режимом возможен, «Модель записи»). Одна `calc_version` для `(период, ключ)` — либо снимок, либо удаление, но не то и другое: это обеспечивает `bank-statement-data`; вызов, где один `(период, ключ)` есть и в `periods`, и в `removed_periods`, отклоняется целиком голым `INVALID_ARGUMENT` без `ErrorInfo` (раздел 5.1, правило 3), как метрика `UNAVAILABLE` от производителя. Надгробие хранится, пока его не заменит применённый снимок этого ключа с версией не меньше надгробия, или до `PurgeUserData`; сроком его не чистят, потому что срок жизни строки outbox не ограничен (раздел 6.1). Поэтому опоздавший старый снимок не возвращает удалённый период, а опоздавшее старое удаление не стирает период, записанный заново. Одна и та же `calc_version` для одного ключа (снимок периода `(период, ключ, transfer_mode)` или состояние) означает одинаковое содержимое (решение владельца 25.10.2026, FIN-283): `bank-statement-data` обязан повышать версию при любом изменении содержимого, а `analytics` применяет повтор с той же версией как безопасный повтор доставки — содержимое и его хеш не сравнивает. Поэтому outbox может отправлять параллельно и повторно, порядок доставки не важен. Большой пересчёт (по новой версии реестра, смена пояса) режется на несколько вызовов ≤ 4 МиБ только по границам периодов: снимки одного периода в разные вызовы не разносятся, каждый вызов атомарен. Пересчёт после смены пояса `bank-statement-data` обязан завершить вызовом с `removed_periods`, где перечислены все ключи периодов, которых в новом поясе нет (решение владельца 25.10.2026, FIN-283): сам `analytics` периоды не удаляет и ключи старого пояса с новым не сверяет, поэтому до такого вызова снимки старого пояса остаются в навигации и `ListPeriods` (пока идёт пересчёт — с признаком `recalculating`).

**Поля, которые заполняет `analytics`** (решение владельца 25.10.2026, FIN-283). `METRIC_STATUS_UNAVAILABLE` ставит только `analytics` («Отказ метрики»): метрика с этим статусом от `bank-statement-data` — нарушение правил записи, вызов `UpsertUserMetrics` отклоняется целиком голым `INVALID_ARGUMENT` без `ErrorInfo` (раздел 5.1, правило 3), как при других нарушениях, которые проверяет `analytics`; ничего не применяется, строка outbox остаётся и видна в алерте. Текст блокировки `lock.text` строит `analytics` при сборке ответа: непустой `lock.text` от `bank-statement-data` вызов не отклоняет и игнорируется.

**Метрики, зависящие от «сегодня»** (прогноз, его блокировка `too_early_in_month` и замена на «Расходы» при устаревшей выписке): `bank-statement-data` пересчитывает текущие периоды ежедневным заданием в 00:05 по поясу пользователя. `stale_after` выровнен на начало дня, чтобы признак `stale` и блокировка прогноза менялись одновременно.

**Чтение после своей записи** (решено 14.10.2026). Правило механическое, клиенту не нужно думать, какие данные он читает: после любого своего успешного пишущего запроса (`POST`, `PUT`, `PATCH`, `DELETE`) клиент 30 секунд ставит на все запросы заголовок `X-Read-Primary: 1`, потом перестаёт; по умолчанию заголовка нет. На Android это один интерцептор OkHttp, на iOS и вебе — так же. `bank-bff` без состояния, поэтому окно держит клиент; `bank-bff` переносит заголовок в metadata `x-read-primary`, сервис читает с primary. 30 с с большим запасом перекрывают отставание асинхронных реплик (обычно доли секунды; алерт на отставание есть). Не покрывает изменения, сделанные не этим клиентом: фоновый пересчёт (на него есть признак `recalculating`), outbox, запись с другого устройства — их пользователь увидит с задержкой на отставание реплики. Злоупотребление (заголовок на каждом запросе) только переводит чтения этого пользователя на primary и ограничено общими лимитами запросов.

**Отказ метрики** (решение владельца 20.10.2026, FIN-196). `METRIC_STATUS_UNAVAILABLE` — только когда прежнего значения нет: снимка периода ещё нет или в сохранённом снимке нет нужной метрики (например, метрика новая в реестре, а период ещё не пересчитан). Смена версии определения в реестре (FIN-6) метрику не закрывает: релиз, меняющий реестр, ставит затронутые периоды на пересчёт, и до пересчёта `analytics` отдаёт прежний снимок периода как есть — `definition_version` сохранённых метрик с текущей версией реестра не сравнивается. Новые снимки периода (оба режима переводов) заменяют прежние целиком и атомарно, в одном вызове («Модель записи», «Версии»), поэтому старые и новые показатели в одном периоде не смешиваются — в том числе при переключении режима переводов. Межмесячные метрики («обычно», сравнение с прошлым периодом, `monthly_chart`) `bank-statement-data` считает по операциям, а не по сохранённым снимкам, так что новый снимок периода целиком по новым правилам; пока пересчёт идёт, расходиться могут только разные периоды — это допустимо. В REST `UNAVAILABLE` — открытое значение `unavailable`, текущий клиент покажет его как `locked` без подробностей — совместимо уже сейчас, до FIN-4.

### 7.4 `assistant`

REST 7.x один к одному. У `AskQuestion` и `RetryAnswer` сначала проверяется ключ идемпотентности: закреплённый ключ возвращает сохранённый ответ, даже при блокировке OFF_TOPIC или исчерпанном суточном лимите, без новой генерации и списания. Тот же ключ с другим телом — `IDEMPOTENCY_CONFLICT`. Новый ключ резервируется на 15 с (дедлайн unary-вызова `AskQuestion` 5 с из раздела 9 плюс 10 с запаса); повтор до истечения резерва — `REQUEST_IN_PROGRESS` с `RetryInfo` / `Retry-After`, равным остатку срока. Истёкший незакреплённый резерв можно занять заново.

После резервирования `assistant` проверяет блокировку OFF_TOPIC на primary до `GetAssistantConsentStatus` (primary в `user`). Далее одна транзакция на primary `assistant`: повторная проверка OFF_TOPIC под сериализацией пользователя → проверка и атомарное списание суточной попытки → сохранение вопроса и ответа (`RetryAnswer` — нового ответа и замены старого) → закрепление ключа. Повторная проверка нужна, чтобы параллельный пятый исход не пропустил новую генерацию по устаревшему чтению; при блокировке она предшествует другим бизнес-проверкам, как шаг `429` в разделе 5.2. Если согласие отсутствует, перед возвратом `CONSENT_REQUIRED` сервер также соблюдает этот порядок `429` → `403`. После коммита запускается генерация. Закрепление проверяет, что резерв ещё свой: тот же `reservation_id`, срок не истёк и запись не перезанята (`UPDATE … WHERE reservation_id = … AND expires_at > now()`). Иначе транзакция откатывается и возвращается `REQUEST_IN_PROGRESS` либо сохранённый ответ закрепившей попытки.

При любой ошибке до коммита (`RATE_LIMITED`, `CONSENT_REQUIRED`, `LIMIT_EXCEEDED`, сбой `user` → `UNAVAILABLE` или сбой БД) транзакция откатывается, попытка не списана и резерв снимается: эти исходы под ключом не сохраняются (раздел 6). Если процесс упал до коммита, инкремент не закоммичен, резерв истекает по сроку жизни.

**Учёт OFF_TOPIC** (FIN-222; точные границы и примеры — api.md, раздел 7): `assistant` по пользователю хранит терминальные исходы после последнего сброса; начальные конфигурационные значения — 5 за 7×24 часа. Проверка допуска новых `AskQuestion`/`RetryAnswer`, сохранение каждого терминального исхода и полный сброс счётчика сериализуются по одному пользователю. Сохранение `OFF_TOPIC`, возврат суточной попытки и учёт одного случая атомарны; повторная обработка завершения того же ответа не добавляет случай. Сброс атомарен с сохранением финансового `complete` с `charged: true`; все прочие исходы не сбрасывают счётчик. При одновременных завершениях порядок сериализации определяет, какие исходы предшествуют сбросу, а какие учитываются после него. Принятые ранее генерации продолжаются: случаев может оказаться больше порога, успешный финансовый ответ со списанной попыткой может разблокировать пользователя.

При числе учитываемых случаев не меньше порога новые запросы получают существующий `RATE_LIMITED` (`RESOURCE_EXHAUSTED`): `ErrorInfo.metadata.retry_at` — момент снижения числа уже сохранённых случаев ниже порога, `RetryInfo` — положительная задержка от текущего момента; `bank-bff` переводит в 429 с `error.retry_at` и `Retry-After`. В момент `completed_at + window` случай уже исключён. Для `n ≥ limit` случаев по возрастанию `completed_at` это `completed_at` случая с индексом `n − limit` (с нуля) плюс окно: при 5 случаях — первое истечение, при 7 — третье. Новые исходы от уже принятых генераций могут сдвинуть срок позже, конкурентный сброс — снять блокировку раньше. При отказе не создаются вопрос/ответ, не вызывается модель и не списывается попытка. `ListMessages`, `GetLimit`, `WatchAnswer` существующих ответов не проверяют этот лимит; `GetLimit` по-прежнему описывает только суточный остаток.

- **Поток ответа**: `WatchAnswer` — снимок из БД, дальше события генерации. Генерация в одном поде, поток может быть открыт в другом: события между подами — `LISTEN/NOTIFY` по `answer_id` (тот же приём, что в `user`), payload ≤ 8000 байт — для `block` с графиком передаётся только `index`, сам блок поток читает из БД.
- **Пояс для `time_zone`** (решено 14.10.2026): `assistant` — получатель `SetUserTimezone` от `user` через outbox, как `bank-statement-data` (общий контракт `usersettings.v1`). Хранит пояс пользователя у себя, применяет только при большей `settings_version`; в ответах (`WatchAnswer`, `ListMessages`) отдаёт текущий пояс. Пока строка outbox не доставлена (секунды) — пояс по умолчанию `Europe/Moscow`. Чужих вызовов ради пояса нет.
- **`changed_since`** в `ListMessages` — один вызов `GetDataVersion` с primary на запрос, сравнение ревизий с сохранёнными исходными ревизиями каждого ответа. В `WatchAnswer` сравнение выполняется перед начальным снимком с источником и при формировании последующих событий `source`. `calculated_at` не определяет наличие изменений (FIN-367).

### Ревизии исходных данных ответа помощника (FIN-367)

Решение владельца 27.10.2026. Общая запись `common.v1.DataRevision { code, value }` описывает ревизию одного вида исходных данных пользователя. `code` — открытая строка 1–64 символа `[a-z][a-z0-9_]*`, `value` — неотрицательный `int64` (PostgreSQL `bigint`). Списки содержат не более 32 записей, повтор `code` недопустим. MetricsIngestService проверяет весь формат ревизий и дубли в адаптере/domain до записи: любой неверный список или элемент — голый `INVALID_ARGUMENT` без частичной записи, как прочие нарушения ingest. Эти ограничения намеренно не заданы аннотациями protovalidate: иначе общий интерцептор вернул бы другой `VALIDATION_ERROR` до проверки пакета. Потребители ответов также проверяют формат и пределы. 0 — известное начальное состояние, отсутствие записи — неизвестная ревизия. Новый производитель передаёт все три кода, включая известные нули:

| code | Источник ревизии | Когда меняется |
| --- | --- | --- |
| `categories` | Счётчик bank-statement-data | Применённая ручная категория, split/join пары, dismiss/restore, применение изменившихся правил к исходным операциям |
| `uploads` | Счётчик bank-statement-data | Успешная фиксация импорта или удаление загрузки, включая последнюю; не staging/failed и не удаление файла уже сохранённой загрузки |
| `time_zone` | Применённый `settings_version` bank-statement-data, приведённый к int64 | Принятое обновление настроек часового пояса; повторы/старые версии не меняют значение |

Ревизии меняются атомарно с соответствующими фактами в транзакции записи. Счётчики категорий/загрузок строго возрастают, от часов не зависят и не обнуляются при удалении загрузки; переполнение отказывает всей транзакции. Первоначальная миграция устанавливает 1 для имеющегося вида изменений и 0 для исходного состояния, не пытаясь восстановить историю. Эта новая исходная точка не даёт baseline прежним ответам. После включения ответов с ревизиями нельзя откатывать writers на версии без продвижения счётчиков или сбрасывать счётчики down/up-миграцией: такой откат требует отдельно инвалидировать baseline ответов как `unverified` и согласовать новую исходную точку. Ревизии не подменяются `calc_version`, временем расчёта или порядком доставки outbox.

`statementdata.DataVersion.revisions` в Overview/Aggregate/Find берётся из того же согласованного read-snapshot, что и финансовые данные. Прежние `categories_changed_at`/`uploads_changed_at` сохраняются как информативные поля для старых потребителей. `GetDataVersion` всегда читает primary вне зависимости от `x-read-primary`: отставшая реплика не должна скрывать изменения в истории. Неизвестные коды промежуточное хранилище сохраняет; конечный потребитель не трактует их как известный вид изменений. Новый вид сначала поддерживают его потребители, затем включает производитель.

Конвейер передаёт `data_revisions` в `PeriodSnapshot` и `UserDataState` из того же snapshot исходных фактов, по которому рассчитаны метрики; оба режима одного периода имеют одинаковые ревизии. Это часть неизменяемого содержимого `calc_version`. analytics хранит ревизии с соответствующим снимком/состоянием. `GetAnalyticsResponse` использует и выбранный снимок, и `UserDataState` для состояния экрана, пояса и глобальных границ: один `code` в `data_revisions` известен только при одинаковом известном значении у **обоих** источников. Например, снимок `uploads=5` при состоянии `uploads=4` не подтверждает ревизию 5 всего ответа; этот code опускается. Когда выбранного снимка нет или `has_data=false`, возвращаются ревизии использованного состояния пользователя. Старый снимок или состояние без поля остаётся с неизвестной ревизией: подстановка из текущего обзора или другого источника запрещена. Внутренняя provenance допустима при `has_data=false`; остальные финансовые поля по-прежнему отсутствуют. bank-bff не переносит ревизии в REST.

assistant сохраняет baseline ревизий всех использованных источников в своём хранилище ответа. Для каждого известного вида любое несовпадение с текущей primary-ревизией даёт соответствующий `changed_since`: `categories`, `uploads`, `time_zone`. Если источников несколько и они расходятся, выбор только последнего/максимального baseline запрещён: актуальность подтверждается лишь при совпадении **каждого** использованного значения с текущим. Нет достаточного baseline или текущей ревизии — `unverified`; это не выдуманный факт изменения и не пустой список. Старые ответы обрабатываются так же без ложного бэкфилла. `calculated_at` служит для показа, в этом сравнении не участвует.

**Доступность проверки.** Только транспортный отказ `GetDataVersion` с голым статусом `UNAVAILABLE` или `DEADLINE_EXCEEDED` без details, пока родительский контекст чтения жив, допускает возврат сохранённых данных с `unverified`. Baseline при этом не меняется; следующее успешное чтение снова сравнит его с primary. Это не общее подавление ошибок: отказ аутентификации/авторизации, статус с details, неверный успешный ответ, отсутствие настройки клиента версии или отмена/истечение родительского контекста остаются ошибкой чтения истории/потока по прежним правилам.

**Поток.** `WatchAnswer` проверяет текущую версию перед начальным `snapshot`, если в нём есть источник, и перед выдачей `source` при последующих обновлениях сохранённого ответа. Даже неизменившийся сохранённый источник сравнивается заново; если результат проверки изменился, поток может выдать новое `source`. Это проверка на момент формирования сообщения, а не подписка на каждую будущую правку финансовых данных: без обновления ответа поток не обязан выдавать отдельное событие. У ответа без строки источника не создаются выдуманные `source`/`calculated_at` ради этой проверки; использованные no-data/списки периодов всё равно участвуют в приватном baseline, если у ответа есть другие источники.

Порядок совместимого включения: merge этого контракта → владелец выпускает новый неизменяемый `gen/go` тег → analytics сохраняет новое поле и bank-bff поддерживает `unverified`/`time_zone` и готовый текст → bank-statement-data публикует новые ревизии → assistant сохраняет baseline и сравнивает его. Старые сервисы игнорируют новые поля; пока источник не заполняет ревизии, новый assistant сообщает `unverified`. Старые мобильные клиенты используют `changed_since_text` для нового открытого кода. Зависимые сервисные PR используют опубликованный тег, не replace на несмёрженный контракт. Реализация: FIN-358 (источники), FIN-369 (конвейер/analytics), FIN-368 (assistant и BFF).

`ListPeriodsResponse.data_revisions` также относится к фактически возвращённому набору периодов и использованному `UserDataState` (в том числе поясу). Значение одного `code` известно только при одинаковом известном значении у каждого использованного заголовка снимка **и состояния**; при пустом списке используется только `UserDataState`. При частично доставленном наборе разные ревизии одного кода или прежний источник без него оставляют этот код неизвестным. Подстановка более свежего глобального состояния в непустой список запрещена. assistant учитывает этот источник, если его список участвовал в выборе ответа; отсутствие достаточной ревизии приводит к `unverified`. Совместимость Android и его mock-поставщика проверяется в FIN-370; новых обязательных полей REST нет.

**Полнота доставки.** Совпадения ревизий уже существующих заголовков недостаточно: новый период ещё может не поступить. Поэтому наличие `UserDataState.data_revisions` дополнительно удостоверяет, что весь набор периодов этой исходной ревизии доставлен. Перед передачей частей каждого пересчёта, включая ежедневный и обновление реестра, производитель отправляет состояние без `data_revisions` и дожидается его ACK. Только после этого разрешена передача любых частей; состояния в них тоже не содержат `data_revisions`. Финальное состояние с ревизиями отправляется лишь после ACK **всех** частей, включая удаления периодов. Очередь unordered: постановка clearing-состояния раньше частей без ACK-барьера не выполняет это правило. Версионные ограждения не дают позднему старому состоянию снова подтвердить набор. Это внутренний протокол полноты, независимый от пользовательского `recalculating`: ежедневный пересчёт и обновление реестра не включают этот флаг.

analytics не восстанавливает ревизии состояния из заголовков. До финального подтверждения отсутствие ревизий использованного состояния оставляет `data_revisions` всего составного ответа неизвестными: это относится и к `ListPeriods` (включая пустой список), и к `GetAnalytics` (включая отсутствие выбранного снимка, навигацию и no-data). Иначе недоставленный новый месяц мог бы навсегда сохраниться в ответе как доказанное отсутствие данных при уже совпадающей primary-ревизии. Начальное пустое состояние может иметь известные нули только после такой же доказанной полноты; legacy metadata не бэкфиллится.

Восстановление metadata прежней загрузки, которое делает `uploads` известным без продвижения счётчика, также запускает полную замену **всех** покрытых месяцев, кварталов и лет с этим протоколом полноты, а не только периодов восстановленной загрузки. Пока границы неизвестны, производитель консервативно опускает `uploads` во всех снимках пользователя. После восстановления каждый сохранившийся снимок должен получить установленную ревизию; иначе прежнее отсутствие кода оставляло бы новые ответы бессрочно `unverified` до следующей пользовательской правки.

Если у используемой прежней загрузки ещё неизвестны первичные границы покрытия (FIN-357), ревизия `uploads` не считается установленной до восстановления metadata из сохранённого OFX. Правило относится ко всем источникам: `DataVersion` инструментов **и** публикуемым `PeriodSnapshot.data_revisions`/`UserDataState.data_revisions`; производитель опускает этот code, а не отправляет текущий счётчик как доказательство прежних границ. Новые ответы с такими источниками остаются `unverified`; последующее восстановление не подменяет baseline прежнего ответа и само по себе не продвигает счётчик загрузок. У пустого пользователя, напротив, известны начальные нули. Это исключение из полной тройки известных ревизий, а не сброс счётчика.

Изменение `changed_since` относится к ответам с существующей строкой `source`. Этот инкремент не создаёт строку источника для чистого ответа без финансового источника/времени расчёта и не выдумывает `calculated_at`; внутренние ревизии всех чтений учитываются, когда ответ имеет строку источника.

**Полная замена после изменения глобальной ревизии.** Ревизии категорий/загрузок/пояса глобальны на пользователя, поэтому FIN-357/369 после их изменения вычисляет и пересылает снимки всех покрытых месяцев, кварталов и лет, включая периоды без изменённых операций. Упоминание «затронутых месяцев» задаёт триггер очереди, а не разрешение оставлять незатронутые снимки с прежней глобальной ревизией. Состав удалённых ключей также доставляется. Во время передачи разных частей ревизии периодов могут временно расходиться: это допустимая промежуточная неопределённость; признак завершения снимается только после подтверждения всех частей. После завершения все сохранившиеся снимки соответствуют одним исходным ревизиям, постоянный `unverified` из-за инкрементального обновления не допускается. Сам FIN-196 сохраняет атомарную замену одного периода в обоих режимах. Увеличение одной глобальной ревизии не даёт права просто переписать метку старого содержимого без пересчёта/проверки исходных фактов. Нагрузка измеряется на полном пути: подготовленный календарь/индекс переиспользуются, worker ограничен временем, очередью и количеством пользователей за итерацию.

**Служебная metadata и неверные данные.** `revisions`/`data_revisions` не включаются в системный промпт, результаты инструментов для модели, тексты блоков или REST. assistant извлекает и хранит их приватно до сериализации payload модели; предсуществующие информативные timestamp-поля не превращаются в доказательство актуальности. Неверный формат списка от финансового источника (nil-элемент, дубли, отрицательное значение, неверный code, превышение предела) делает чтение этого источника недействительным: assistant завершает всю генерацию как failed с `MODEL_ERROR`, `charged=false`, возвратом попытки и `retryable=true`. Неверный результат не отправляется модели как исправимая ошибка инструмента; частичный baseline, блоки и source этого неудавшегося ответа не публикуются как complete. Неверный успешный ответ текущего `GetDataVersion` даёт ошибку всего чтения истории/снимка; узкое исключение для транспортной недоступности описано выше. Неверная схема/значения уже сохранённого приватного baseline обрабатываются как неизвестный baseline с `unverified`; достоверный частичный baseline сохраняет известные отличия и добавляет `unverified`. Пустой старый список сам по себе не повреждён: он означает неизвестность. Для неизвестного, но корректного code одинаковое значение во всех использованных источниках и текущем ответе не мешает подтверждению; несовпадение или отсутствие пары в любом использованном/текущем источнике даёт `unverified`, а не выдуманный известный вид изменения и не пустой список.

## 8. Время, деньги, перечисления

- **Валидация полей** (решено 14.10.2026) — в два слоя. REST на входе — `kin-openapi` по `openapi.yaml` (400 в формате `api.md` до gRPC). gRPC в сервисе — `protovalidate`: аннотации в `.proto` (длины, диапазоны, формат телефона), проверка одним серверным интерцептором, нарушения — `google.rpc.BadRequest` → `VALIDATION_ERROR` с полями. Нужен потому, что системные вызовы идут мимо REST: прежде всего инструменты помощника, аргументы которых генерирует модель. Руками в обработчиках — только бизнес-правила (связи между полями, проверки по БД). Правила в `openapi.yaml` и `.proto` сверяет контрактный тест с граничными значениями; источник правды — `api.md`.
- **Моменты** — `google.protobuf.Timestamp` (UTC). REST требует моменты со смещением («`2026-09-01T00:00:00+03:00`»), а календарные границы считаются в поясе профиля. Поэтому каждый ответ с моментами для показа содержит `time_zone`, и `bank-bff` форматирует все `Timestamp` этого ответа в нём. Пояс приходит от сервиса, который считал календарь, — у `bank-bff` своего состояния нет.
- **Календарные ключи** — строки `YYYY-MM`, `YYYY-Qn`, `YYYY`, как в REST. **Календарный день** (REST `date`) — строка `YYYY-MM-DD` в поясе профиля, `bank-bff` передаёт её как есть, без пересчёта по `time_zone`; пара дней `*_from` / `*_to` — оба включительно (`Upload.period_from` / `period_to`, FIN-197).
- **Версии** (`calc_version`, `settings_version`) — `int32`, монотонные на пользователя. Производитель и получатели хранят их в PostgreSQL `integer`, не уже: значение больше 2^31−1 не возникает, а любое значение производителя помещается у получателя, иначе событие outbox застряло бы навсегда (решение владельца 20.10.2026, FIN-207).
- **Деньги** — `int64` в копейках, суффикс `_minor`; знак — как в REST. Валюта — отдельным полем только у операции.
- **Телефон** — `string` в E.164 (`+79001234567`), как в REST и в БД `user`; формат проверяет обработчик. `google.type.PhoneNumber` не используем: это зависимость от googleapis ради обёртки над той же строкой, а её варианты `short_code` и `extension` пришлось бы отвергать (решение 12.10.2026). Если понадобятся номера не из РФ или добавочные, заводится новое поле.
- **Необязательность** — `optional` (presence), отсутствующее поле → поле не выводится в JSON.
- **Перечисления** — proto-`enum`, ноль — `*_UNSPECIFIED`. `bank-bff` переводит в строковые коды REST механически по имени (`LOCK_REASON_NEED_FULL_MONTHS` → `need_full_months`) через `protoreflect`, без ручных таблиц. Новое значение: сначала выкатывается потребитель (`bank-bff`, затем остальные), потом производитель. Неизвестное `bank-bff` число (выкатили не в том порядке) → поле не выводится; для обязательных полей — по правилу поля из `api.md` (`status` → не выводить запись нельзя, поэтому ответ 500 и алерт). Закрытые наборы REST (`Theme`, `KindFilter`) и открытые реализуются одинаково — разница только в REST.
- **Реестр ошибок** — `ErrorReason`, имена значений без префикса (стиль Google AIP-193), это единственное исключение из lint.
- **Комментарии в `.proto`** — на русском и в терминах предметной области. Элементы интерфейса (экраны, карточки, плашки, кнопки, тексты макетов) не упоминаются: интерфейс меняется чаще контракта, и описание устаревает (решение 12.10.2026). Примеры строк допустимы только для полей, где сервер сам отдаёт готовый текст (`schedule_name`, `reason_name`).

## 9. Транспорт и эксплуатация

- **grpc-go**, HTTP/2 без TLS внутри кластера: трафик между узлами уже шифрует flannel `wireguard-native`, внутри узла — loopback/veth. mTLS не делаем (идентичность — токены ServiceAccount, см. 3.3).
- **Балансировка**: обычный ClusterIP при долгоживущих HTTP/2-соединениях даёт перекос (все запросы в один под). Сервисы — headless (`clusterIP: None`), клиенты — `dns:///<svc>.<ns>.svc.cluster.local:9090` с `round_robin`; на серверах `MaxConnectionAge = 5 мин` + `MaxConnectionAgeGrace = 4 мин` (больше 3-минутного потока ответа), чтобы новые поды получали соединения.
- **Дедлайны** — ставит `bank-bff` от своего бюджета, сервисы передают остаток дальше:

| Вызов | Дедлайн |
| --- | --- |
| Обычные unary | 5 с |
| `SearchOperations`, `GetAnalytics` | 10 с |
| `UploadStatement` | 60 с |
| `WatchUpload` | 4 мин (разбор — 3) |
| `WatchPhoneVerification` | до `expires_at` + 10 с (`pending`); результат `verified` отдаётся сразу, и поток закрывается |
| `WatchAnswer` | 4 мин (генерация — 3) |
| Инструменты помощника | 10 с на вызов; общий бюджет генерации — 3 мин |
| `UpsertUserMetrics`, `PurgeUserData`, `SetUserTimezone` | 30 с |

- **Ретраи** (service config клиента): только `UNAVAILABLE`, до 3 попыток с джиттером; для всех чтений и для методов, идемпотентных по конструкции (раздел 6). Методы с `idempotency-key` ретраит клиент (приложение), не `bank-bff` — иначе один пользовательский таймаут превращается в шквал. Хеджинг не используем.
- **Keepalive** для потоков: клиент `Time = 30 с`, сервер `EnforcementPolicy.MinTime = 20 с`. SSE-heartbeat `: ping` раз в 15 с генерирует `bank-bff`, в gRPC его нет.
- **Health** — `grpc.health.v1` на каждом сервисе, пробы Kubernetes нативные `grpc`. Reflection — только в dev.
- **Метрики** — RED по методу и `reason` (без `user_id` в метках), доля `UNAVAILABLE` метрик в `analytics` по `metric_id` (FIN-5); `finassist_incomplete_period_snapshots_total` в `analytics` — периоды, пришедшие в `UpsertUserMetrics` только с одним `transfer_mode` (7.3, «Модель записи»), метка — тип периода (`month` / `quarter` / `year`). В `bank-bff` — запросы по маршруту и версии клиента (FIN-20): метка — платформа и `MAJOR.MINOR`; заголовок подделывается, поэтому число значений метки ограничено (сверх лимита — `other`). По этим метрикам решается удаление устаревшего (`docs/api.md`, «Удаление устаревшего»).
- **Размер сообщения** по умолчанию 4 МиБ; исключение — `SearchOperations` (16 МиБ).

## 10. Кодогенерация и CI

- `.proto` — каталог `proto/` в `fin-assist/contracts`. Бэкенд — отдельный репозиторий на каждый сервис и отдельные репозитории библиотек (решение 16.10.2026, FIN-116), поэтому генерация одна — здесь, а не в каждом сервисе.
- Сгенерированный Go-код — в git этого репозитория, Go-модуль `github.com/fin-assist/contracts/gen/go` (каталог `gen/go`, свой `go.mod`; `go_package` — `github.com/fin-assist/contracts/gen/go/finassist/<сервис>/v1`), чтобы сборка сервиса не требовала `protoc` и `buf`. Сервис подключает его как обычную зависимость: `go get github.com/fin-assist/contracts/gen/go@vX.Y.Z`. Версии — теги `gen/go/vX.Y.Z`, выпуск и правило версий — `README.md` («Go-модуль `gen/go`»).
- Состав модуля: `finassist/<сервис>/v1` — сообщения (`protoc-gen-go`) и клиенты/серверы gRPC (`protoc-gen-go-grpc`); `finerr` — конструкторы ошибок реестра (по одному на код `ErrorReason`, обязательные ключи `metadata` — параметры, `BadRequest` и `RetryInfo` — параметры там, где их требует `error_spec`; если код требует и `RetryInfo`, и ключ `retry_at` (`RATE_LIMITED`), задержка вычисляется из `retry_at`, чтобы `Retry-After` и тело ответа не расходились), `Lookup` (спецификация кода по `reason`) и `ToREST` — перевод статуса в REST для `bank-bff` (`ok = false` — неполная или не из реестра ошибка по правилам раздела 5: 500 и метрика `finassist_unmapped_error_total`).
- Генерация — `scripts/generate.sh`: собирает закреплённые в `tools/go.mod` `buf`, `protoc-gen-go`, `protoc-gen-go-grpc` и `tools/protoc-gen-finerr`, запускает `buf generate` (`proto/buf.gen.yaml`). CI перегенерирует и требует, чтобы `gen/go` не изменился, затем `go build`, `go vet`, `go test` модуля.
- Проверки в CI (аналог `oasdiff` для REST): lint (STANDARD), несовместимые изменения против `main` (`FILE`), запрет повторного использования номеров полей (`reserved`), реестр ошибок — `scripts/check_error_registry.py <дескрипторы> <api.md>` (5.2).
- Из опций `error_spec` генерируются пакет `finerr` (конструкторы ошибок) и таблица перевода ошибок для `bank-bff` (5.2).
- **Инструмент — `buf`** (решено 14.10.2026): `buf build`, `buf lint` (STANDARD), `buf breaking` против `main`, `buf generate` с локальными плагинами `protoc-gen-go`, `protoc-gen-go-grpc` и `protoc-gen-finerr`, `buf format`. Версии `buf` и плагинов закреплены в инструментальных зависимостях модуля `tools/go.mod`; `BUF_VERSION` в CI сверяется с ним. Внешние `.proto` берутся из BSR как зависимости `proto/buf.yaml` с закреплённым коммитом в `proto/buf.lock`, а не кладутся в репозиторий; коммит совпадает с версией сгенерированного Go-модуля этой зависимости у сервисов, и тот же модуль указан в `gen/go/go.mod`. Первая такая зависимость — `buf.build/bufbuild/protovalidate` (FIN-202). Публикации в BSR нет.

Проверено 12.10: все файлы проходят `buf build` и `buf lint` STANDARD (единственное исключение — префикс значений `ErrorReason`); `check_error_registry.py` — 20 из 30 кодов, совпадает с `api.md`.
