# Расчёт метрик и правила учёта

**Как** считаются поля, которые описывает `docs/api.md`. По этому документу пишется Go-бэкенд (`bank-statement-data`, `analytics`, `assistant`) и проверяется фейковый бэкенд Android (`:mock:backend`); обе реализации сверяются с эталонными данными `fixtures/calc` (FIN-107, FIN-108), которые считает референсный расчёт `tools/refcalc` по этому документу.

Спецификация FIN-106; до 16.10.2026 жила в Confluence («Расчёт метрик и правила учёта»), теперь там только выжимка и ссылка сюда (FIN-158). Изменения — через задачу YouTrack `FIN-<n>`: правка этого документа, `tools/refcalc` и перегенерация `fixtures/calc/expected` — в одном PR.

**Какой источник главный.** Последнее решение владельца → этот документ (как считать) → `docs/api.md` и `openapi/openapi.yaml` (что и в какой форме отдавать) → эталонные данные (исполняемая копия первых двух). Расхождение между ними — дефект: правится тот, что ниже по цепочке, или, если ниже прав, — решением владельца тот, что выше.

Где фейковый бэкенд сейчас считает иначе, нормой считается этот документ — расхождения перечислены в разделе 11 с задачами.

## 1. Общие соглашения

- **Суммы** — целые копейки (int64). У операции сумма без знака, направление — списание / зачисление. Агрегаты расходов и доходов — со знаком (расходы за период могут быть отрицательными из-за возвратов). Валюта — `RUB`; другие валюты в MVP не пересчитываются.
- **Округление.** Деление суммы на число дней или операций — целочисленное с отбрасыванием дробной части к нулю (как `/` в Go и Kotlin). **Любое среднее по периодам** («обычно» под графиком, «обычно» заметных трат) и экстраполяция квартала/года — округление к ближайшему, .5 — вверх: `floor(x + 0.5)` при любом знаке (как `Math.round`; `math.Round` в Go для отрицательных округляет иначе). Доли — `float64` без округления; проценты в текстах — доля × 100 тем же правилом.
- **Время.** Дни, месяцы, кварталы, годы и «сегодня» считаются в поясе профиля (`profile.timezone`, FIN-91/92; неизвестный пояс — `Europe/Moscow`) на момент расчёта. День операции — дата `occurred_at` в этом поясе. Период — полуинтервал `[начало первого дня; начало дня после последнего)`, границы — с собственным смещением (летнее время). Смена пояса — пересчёт (`recalculating`).
- **Лимит помощника** — исключение: сутки по Москве независимо от пояса профиля.
- **Нет данных ≠ 0.** Значение за период без покрытых дней — отсутствие значения (`null`), а не ноль. Ноль — только когда дни покрыты, а подходящих операций нет.
- **Пороги** — только из реестра (раздел 7); клиент их не знает.

## 2. Входные данные

**Выписка OFX Т-Банка** (формат — Confluence, «Формат выписки Т-Банка (OFX)»). Из каждого блока `STMTTRNRS`: счёт (`ACCTID`, `ACCTTYPE`), период `DTSTART..DTEND`, строки `STMTTRN`. Блок без `ACCTID` пропускается целиком: его строки не попадают ни в операции, ни в непрочитанные. Счёт другого банка — `ACCTID` с префиксом `OB$` (`is_other_bank`, маски нет); у остальных `mask` — «··» и последние 4 символа `ACCTID`.

| Поле операции | Источник |
| --- | --- |
| ключ | (счёт, `FITID`) — по нему дедупликация между загрузками |
| `occurred_at` | `DTPOSTED`; пояс из `[+3:MSK]`, нет пояса — +03:00 |
| направление | списание, если `TRNAMT` < 0 или `TRNTYPE=DEBIT`; иначе зачисление |
| сумма | \|`TRNAMT`\| × 100, округление half-up |
| описание (`title`) | `NAME`: пробельные символы по краям обрезаются (до раскрытия XML-сущностей), затем раскрываются пять предопределённых сущностей XML (`&amp;` `&lt;` `&gt;` `&quot;` `&apos;`), одним проходом (`&amp;lt;` → `&lt;`, а не `<`); числовые ссылки (`&#171;`) остаются как есть; внутренние пробелы, в том числе неразрывные, — как есть. Может быть пустым (FIN-67) |
| категория банка | `MEMO`, обрезка краёв и сущности — как у `NAME`; пустой — «Без категории» (раздел 3.1) |
| валюта | `CURSYM`, по умолчанию `RUB` |

**Непрочитанная строка** — только когда операцию нельзя учесть, в порядке проверки: нет `DTPOSTED` → `no_date`; дата не разбирается → `bad_date`; сумма не разбирается → `bad_amount`; нет `FITID` → `truncated`. У строки хранятся номер строки файла (строка тега `<STMTTRN>`), дата (если прочиталась), причина, счёт блока и `FITID` (если есть). Закрытие строк более поздней загрузкой — по api.md 3.6 (FIN-79), дни — в поясе профиля. Счётчики непрочитанных строк за период — незакрытые строки завершённых загрузок с датой в `[from; to)`; строки без даты в периоды не попадают.

**Импорт атомарный.** После добавления новых операций правила раздела 3 заново применяются ко всем операциям пользователя (пара и возврат могут найтись через загрузки). Операция живёт, пока есть хотя бы одна загрузка с её ключом; удаление загрузки убирает остальные и снова применяет правила.

## 3. Правила учёта

### 3.1 Категории банка и направления

Категории — категории Т-Банка как есть (список открытый, новая категория добавляется при первой встрече; `id` — стабильный слаг `cat_<транслит>`). Иконка новой категории — `tag`. Число новых категорий не ограничено; название берётся из `MEMO` (после обрезки краёв, раздел 2) и обрезается до 64 символов (решение 16.10.2026); внутренние пробелы не нормализуются (неразрывный пробел остаётся). Направление (`kinds` в 5.1) задаёт выбор категории и правило возврата:

| Направление | Категории |
| --- | --- |
| только доход | Зарплата, Пополнения, Вклады, Проценты, Бонусы, Дивиденды и купоны, Другое |
| оба | Переводы, Финансы, Наличные, «Без категории» (системная, `MEMO` пустой, буквально «Без категории» или «Возврат» — решение 16.10.2026, зачисление с ним — возврат, 3.3), любая категория банка, которой нет в списке |
| расходная | остальные известные (Супермаркеты, Фастфуд, Услуги банка …) |

Системные: «Между своими счетами» (`cat_own_transfer`, оба), «Возврат» (`cat_refund`, только доход), «Без категории» (`cat_uncategorized`, оба). Список известных категорий банка с их `id`, иконками и направлениями — `fixtures/calc/categories.json`: 51 категория, собранная из выписки владельца (FIN-107; полного списка категорий Т-Банка нет — решение 20.10.2026, FIN-200). Категория банка не из списка — оба направления. Добавить категорию в список — правка этого файла и выпуск сервиса; после выпуска правила применяются заново ко всем операциям (api.md, 5.1).

### 3.2 Пара перевода между своими счетами

Перевод себе — операция с описанием «Между своими счетами», «Себе в другой банк», «Себе из другого банка» (точное совпадение с учётом регистра, после обрезки краёв) (или с категорией не от пользователя «Между своими счетами»), либо операция, которой пользователь вручную поставил эту категорию. Операция с ручной категорией, отличной от «Между своими счетами», переводом себе не считается и в пару не входит (3.4: автоматические правила ручную категорию не меняют). Операция из разделённой пользователем пары переводом себе по описанию больше не считается (флаг «разделена», снимается ручной категорией «Между своими счетами»).

Поиск пар (после каждого импорта, удаления и смены категории):

1. Существующие пары сохраняются, если обе стороны на месте: следующая загрузка не пересобирает пару, даже если добавит зачисление ближе по времени.
2. Списания-переводы себе без пары — по возрастанию времени. Для каждого — зачисление без пары на ту же сумму **в той же валюте** (решение 16.10.2026; обмен валюты остаётся двумя одиночными операциями), **на другом счёте**, |разница времени| ≤ 3 суток (72 ч), которое само перевод себе **или** имеет категорию банка «Переводы» без ручной правки. Из кандидатов — ближайшее по времени; при равной разнице — более раннее, при равном времени — с меньшим ключом (`ACCTID`, `FITID`).
3. Операция входит не больше чем в одну пару. Обе стороны пары получают «Между своими счетами»; в API пара — одна запись `own_transfer` (время и сумма — списания) с `is_category_manual: false` — в том числе после ручной смены на ту же «Между своими счетами» (ничего не меняется и не запоминается) и для пары, собравшейся после ручной категории «Между своими счетами».
4. Перевод себе по описанию без пары — обычная операция с категорией «Между своими счетами». Операция, потерявшая пару и не являющаяся переводом себе по описанию, возвращает категорию банка.

### 3.3 Возврат

Признак (для зачисления без ручной категории и вне пары) — хотя бы одно:

- категория банка — расходная (3.1), или `MEMO` в выписке — буквально «Возврат» (решение 16.10.2026; категория банка у такой операции — «Без категории», поэтому цель — по шагам 1, 2 или 4);
- раньше было списание с тем же непустым описанием (без учёта регистра), чья категория банка — не «Переводы»;
- в описании есть «возврат» (без учёта регистра).

Операция с пустым описанием по описанию не сопоставляется ни с одной стороны (FIN-67). Возврат получает категорию «Возврат» и **цель** — первая найденная по цепочке:

1. итоговая категория последнего более раннего списания с тем же описанием (кроме категории банка «Переводы»), если она не «Между своими счетами» и не «Возврат»;
2. итоговая категория последнего списания той же суммы на том же счёте не раньше чем за 60 суток до возврата (с теми же исключениями);
3. категория банка самого возврата, если она расходная;
4. иначе — «Без категории».

Возврат уменьшает расходы цели в **месяце возврата**, доходом не считается. Ручная смена категории на «Возврат» — цель по той же цепочке. Выбрать цель вручную нельзя (решение 16.10.2026): возврат без цели можно только оставить в «Без категории» или перевести в доходную категорию — тогда он обычный доход. Зачисление, переставшее быть возвратом (например, удалили загрузку со списанием), возвращает категорию банка. Подписи: `note` — «возврат · <цель>» (без цели — «возврат»), `note_details` — «Уменьшает расходы «<цель>» в <месяце>» / «Уменьшает общие расходы в <месяце>».

### 3.4 Ручная смена категории

По api.md 4.3. Ручная категория запоминается по ключу (счёт, `FITID`) и применяется при повторном импорте до всех правил; автоматические правила её не меняют (кроме цели ручного «Возврата»). Разделение пары: выбранная категория — списанию, если в её `kinds` есть `expense`, иначе зачислению; другая сторона — категория банка (ручная правка у неё снимается), обе получают флаг «разделена».

### 3.5 Итоговая категория — порядок

Ручная → сторона пары («Между своими счетами») → перевод себе по описанию («Между своими счетами») → возврат («Возврат») → категория банка. Пары ищутся до возвратов.

### 3.6 Что идёт в аналитику

- **Видимые операции режима:** `with` — все, кроме сторон пар; `without` — ещё и без операций с **итоговой** категорией «Переводы» (оба направления).
- **Расход** из видимых: списание не в «Между своими счетами» → +сумма в своей категории; возврат → −сумма в категории-цели.
- **Доход:** зачисление не возврат и не в «Между своими счетами» → +сумма.
- Операция относится к периоду по дню операции.

## 4. Календарь и полнота данных

- **Покрытые дни** — объединение периодов всех завершённых загрузок. Период загрузки — от дня минимального `DTSTART` до дня максимального `DTEND` по счетам файла, **оба дня включительно** (дни — в поясе профиля); в расчёт идут блоки, у которых есть **оба** тега; если таких блоков в файле нет — от первой до последней операции файла. Этот период отдаёт «История загрузок» (`api.md` 3.4, `uploads[].period_from` / `period_to`, FIN-197). Смежные или пересекающиеся интервалы сливаются.
- **Пропуски (`gaps`)** — непокрытые дни между первым и последним покрытым днём, интервалами `[начало первого дня; начало дня после последнего)`. В период (6.1 `period.gaps`, неполные месяцы итога импорта) попадает пропуск, пересекающий его, **целиком**, без обрезки границами периода (решение 16.10.2026): пользователь видит настоящие границы пропуска и понимает, какую выписку догрузить.
- **Полный месяц** — последний день месяца раньше сегодня и каждый день покрыт. **Месяц с данными** — хотя бы один покрытый день. Полный период (квартал, год) — все его месяцы полные.
- **`coverage` периода:** `no_data` — нет покрытых дней; `complete` — период закончился и покрыт весь; иначе `partial`. `data_from` — начало первого покрытого дня в периоде; `data_to` (6.1 `period`, точки графиков, сводка ленты) — время последней операции периода (любой: независимо от режима переводов и пар), если она в последний покрытый день периода, иначе конец этого дня (23:59:59). `state.data_from` / `state.data_to` (6.1) — начало первого и начало дня после последнего покрытого дня по всем загрузкам.
- **Устаревание (`stale`):** нет покрытых дней или `сегодня − последний покрытый день > 14` дней. Одно правило для ленты (4.1) и аналитики (6.1).
- **Периоды с данными (6.2)** — месяцы / кварталы / годы, в которых есть покрытый день, новые первыми. Период 6.1 без `date` — последний из них; `navigation` — соседние в этом списке; у периода вне списка (явный `date` без данных) `previous` и `next` — `null`. `is_current` — сегодня внутри периода. `has_data` — есть хотя бы одна операция и один покрытый день.
- **Раннее состояние** — всего один месяц с данными и он неполный: блока `monthly_chart` нет, период подписывается днями («1–25 сентября 2026»).

## 5. Метрики «Аналитики» (6.1)

Обозначения: P — выбранный период, V — видимые операции режима (3.6), E(X) и I(X) — расходы и доходы множества, D — последний покрытый день в P, «прошлые периоды» — периоды того же типа до P, начинающиеся не раньше месяца первого покрытого дня, новые первыми.

| Метрика | Формула и база | Статус, блокировки, крайние случаи |
| --- | --- | --- |
| Расходы, доходы | E(V∩P), I(V∩P) | всегда; расходы могут быть < 0 |
| Доходы минус расходы (`balance`) | I − E; доля = (I − E) / I | доля только при I > 0, иначе «Доходов за период нет»; доля < 0 — «−12% · потратили больше, чем получили» |
| Расходы в день (`daily_expense`) | E / N, N — число покрытых дней P не позже сегодня (не меньше 1) | всегда, не блокируется. Подпись для месяца: прошлый период полный → «в августе — E(прошлый)/дней в нём»; для квартала и года — «в среднем за <месяцы данных>» |
| Прогноз (`forecast`) | месяц: E × L / T, L — дней в месяце, T — дней от 1-го до min(D, сегодня) включительно. Квартал/год: E + round(E_base / days_base × R), база — последние 3/12 полных месяцев всей истории, R — дней от D+1 (или начала P) до конца P | дополнительная плитка только текущего P; фактическая `expense` всегда отдельна (FIN-408). Порядок: `is_current` → `stale_data` (прогноз отсутствует) → месяц: сегодня < 10-го → `too_early_in_month` (`available_from` = 10-е); квартал/год: полных месяцев < 3/12 → `need_full_months` |
| Сравнение «к тому же дню» | k = D − начало P (в днях); prev = E(V за первые k+1 дней прошлого периода, не дальше его конца); разница = round((E − prev) × 100 / \|prev\|) | только если непосредственно предыдущий период полный, иначе `need_full_months` (1). prev = 0 — «В прошлом периоде к этому дню расходов не было». Текст — только для месяца |
| «Обычно» (`typical`) | среднее E по до 6 последним полным прошлым периодам, округление; база — их диапазон | нужно 2 полных прошлых периода (`need_full_months`, required = 2 × месяцев в периоде) |
| Расходы по месяцам (`monthly_chart`) | месяц — 6 месяцев по P включительно (выделен P); квартал — 3 его месяца; год — 12, без выделения. Точка = E(V за месяц) или `null`, если в месяце нет покрытых дней | месяцев с данными во всей истории < 2 → `need_months_with_data`; раннее состояние (4) — блока нет. Примечания (`notes`) — раздел 10 |
| Доходы минус расходы по месяцам (`balance` chart) | те же месяцы; точка = (I − E) / I месяца | точка `null` при I ≤ 0 или без данных; нет для года; без графика — только итог |
| Расходы по категориям | группировка строк расхода (3.6) по категории, сумма со знаком, по убыванию; доля = сумма / E; `note` у «Переводов» — «N переводов» | доли нет при E ≤ 0 или сумме < 0; нет строк — `none` «Расходов за … нет» |
| Доходы по категориям | то же по доходам; доля = сумма / I | доли нет при I ≤ 0 |

### Наблюдения (только `period=month`)

B — полные месяцы по P включительно, новые первыми (пороги считаются по ним). **Единые исключения** (решение 16.10 по ревью): в регулярных платежах, заметных и мелких частых тратах не участвуют операции с итоговой категорией «Переводы» и «Между своими счетами» (для возврата — по цели); «Без категории» не становится группой по категории, но её операции могут войти в группу по продавцу.

| Наблюдение | Правило | Порог и статусы |
| --- | --- | --- |
| Регулярные платежи | окно W — первые min(3, \|B\|) месяцев B. Списания V в W с непустым описанием, кроме «Между своими счетами» и «Переводов», группируются по описанию (точное совпадение). Платёж — группа, в каждом месяце W ровно одно списание (две и больше в месяц — не регулярный платёж, решение 16.10.2026), все суммы в пределах ±15 % от медианы (медиана — элемент с индексом n/2 отсортированных сумм, то есть при чётном n — верхний из двух средних). Сумма и «в месяц» — медиана; день — медиана дней месяца («15-го числа»); `id` — UUID, стабилен по описанию (соответствие хранит сервис; описание в `id` не кодируется). Отмеченные «Не подписка» исключаются. Итог — сумма по платежам, строки по убыванию | \|B\| < 2 → `need_full_months` (2); 2 → `tentative`; ≥ 3 → `ready`; нет платежей — `none` |
| Заметные траты | база — 3 полных месяца **перед** P; «обычно» категории = сумма её строк расхода за базу / 3, округление half-up (раздел 1). Заметна категория (кроме «Без категории», «Переводов» и «Между своими счетами»), если обычно > 0, расход в P ≥ 1 000 ₽ и ≥ 1,5 × обычно. Порядок — по убыванию разницы «расход в P − обычно» в копейках (не кратности). Текст «В 2,3 раза больше обычного — обычно около X (июнь — август)», кратность — один знак после запятой | полных месяцев до P < 3 → `need_full_months` (3); нет категорий — `none` |
| Комиссии и проценты банку | строки расхода V∩P, где итоговая категория (для возврата — цель) «Услуги банка» **или** в описании есть **целое слово** «комиссия» или «процент» в любой падежной форме (комиссия, комиссии, комиссию, комиссией, комиссий, комиссиям, комиссиями, комиссиях; процент, процента, проценту, процентом, проценте, проценты, процентов, процентам, процентами, процентах). Слова — последовательности букв, регистр не важен, ё = е; «Комиссионный» не совпадает. Список словоформ — в реестре. Сумма со знаком; «из чего» — первые 3 разных непустых описания | всегда открыто; нет строк или сумма ≤ 0 — `none` |
| Мелкие частые траты | месяц расчёта M — сам P, если он полный; иначе последний полный месяц до P, и карточка называет его («по августу»), выборка в Поиске — за M. Списания V∩M с едиными исключениями. Сначала группы по продавцу (непустое описание): больше 8 операций и средний чек ≤ 500 ₽. Из оставшихся операций — группы по итоговой категории (кроме «Без категории») с тем же условием (операция входит в одну группу). Группа: count, средний чек = сумма / count, «в месяц» = сумма, «в год» = сумма × 12. Итог — сумма групп (`approx`) | \|B\| < 1 → `need_full_months` (1); нет групп — `none` |

**Выборки.** У каждой цифры с переходом `operations_filter` даёт в Поиске (4.1) ровно те строки, из которых она сложена: период P, `transfer_mode`, `kind` / `category_id` по правилам 4.1 или непрозрачный `selection` (комиссии, «Без категории», регулярный платёж, все регулярные, группа мелких трат, продавец из ответа помощника). Текстовый `q` для выборок не используется. Исключение — регулярные платежи (решение 16.10.2026): переходы карточки и строк платежей открывают Поиск за P, со свежими списаниями этих платежей, а не за окно W, по которому посчитаны суммы.

## 6. Лента, поиск и итог импорта

- **Сводка ленты (4.1):** порция — 3 календарных месяца, заканчивая месяцем самой новой записи (или месяцем перед `before`). `summary` — по месяцам порции с данными: E и I режима `with`, `data_to` — только у `partial`. `next_before` — начало порции, если есть записи раньше. `before` — только начало месяца в поясе профиля, то есть значение `next_before`; другой момент — 400 `VALIDATION_ERROR` (решение 16.10.2026).
- **Поиск:** период по умолчанию — `[сегодня − 12 месяцев; завтра)` по началам дней (29 февраля − 12 месяцев = 28 февраля). С `transfer_mode` — исключены все операции с итоговой категорией «Между своими счетами»: и пары, и одиночные переводы себе (решение 16.10.2026: выборка совпадает с цифрой «Аналитики», которая их не считает, 3.6); при `without` — ещё и «Переводы»; возврат — расход своей цели. `kind` не включает «Между своими счетами». `q`: подстрока описания, итоговой категории или категории банка; точная сумма, если `q` — число (пробелы убраны, запятая = точка, рубли); последние 4 цифры счёта, если `q` — 4 цифры; регистр и ё/е не важны.
- **Итог импорта (3.3):** `operation_count` — прочитанные операции файла; `new_count` / `duplicate_count` — по ключу (счёт, `FITID`); `totals` — E и I режима `with` по новым операциям вне пар (при первой загрузке `scope=all`, иначе `new`; нет новых — поля нет); `own_transfer_count` — новые операции в парах или в «Между своими счетами»; `uncategorized_count` — новые операции в «Без категории» и возвраты без цели; `categorized_count` = `new_count` − `uncategorized_count`; `coverage` — по разделу 4 до и после загрузки, `features` — по реестру (раздел 7) о данных за **всю историю**, а не о выбранном периоде («Заметные траты» открыты при 3 полных месяцах вообще, хотя карточка за месяц сразу после них ещё `locked`: её окно — 3 полных месяца перед P); `notices` — одно из двух: нет операций — `empty_statement`; операции есть, но нет ни одного списания — `no_expenses`.
- **Конфигурация импорта (3.1):** `suggested_period.from` — начало дня последней операции, а без операций — сегодня − 12 месяцев; `to` — начало завтра.

Пояснение базы заблокированного прогноза (FIN-408 / FIN-402): существующий `lock.text` перечисляет полные месяцы всей истории и объясняет неполные части, независимо от выбранного года (`api.md` 6.1). Источник — то же объединение периодов OFX из раздела 4, из которого посчитан счётчик. Месяцы с годами отсортированы; соседние полные и соседние целиком пустые месяцы обязательно объединены в диапазоны, несмежные участки разделены; неполные месяцы — с покрытыми границами и пропусками, текущий месяц с покрытыми днями — незавершённый, целые месяцы без данных внутри истории — отдельно. За пределами загруженного покрытия месяцы не перечисляются. Число полных месяцев совпадает с `available`. Формулы, пороги и stale-политика сохраняются. При недостаточных метаданных прежнего снимка — правило без вымышленных дат (`grpc-api.md`, FIN-408).

При выбранном периоде `no_data` блок `tiles` имеет `status: none` и `empty_text` «За этот период данных нет», с `data: {"tiles": []}`, без денежных значений (FIN-408 / FIN-401). Ноль в покрытом периоде без расходов остаётся фактическим нулём.

Параметры правил (тоже в реестре, с версией определения): окно пары 3 суток, одна валюта сторон; окно возврата по сумме 60 суток; допуск регулярного ±15 %, окно 3 месяца, 1 списание в месяц; заметные ×1,5 и 1 000 ₽; мелкие > 8 операций и ≤ 500 ₽ по полному месяцу; словоформы комиссий; исключённые из наблюдений категории; «обычно» — до 6 периодов; длина названия категории банка — 64 символа.

**Смена версии определения** (решение владельца 20.10.2026, FIN-196). Релиз, меняющий реестр, ставит затронутые месяцы пользователей на пересчёт. До пересчёта период показывается по прежним снимкам целиком; новые снимки периода (оба режима переводов) заменяют прежние целиком, атомарно и одновременно, показатели старой и новой версии в одном периоде не смешиваются — в том числе при переключении режима переводов. Межмесячные показатели («обычно», сравнение с прошлым периодом, расходы по месяцам) считаются по операциям, а не по сохранённым снимкам других периодов, поэтому новый снимок целиком по новым правилам; пока идёт пересчёт, расходиться могут только разные периоды. «Недоступно» (`unavailable`) — только у показателя, которого в прежнем снимке нет (новый в реестре), или если снимка периода ещё нет (`docs/grpc-api.md` 7.3, «Отказ метрики»). Признак `state.recalculating` этот пересчёт не ставит: он только для пересчёта после действия пользователя (импорт выписки, смена категории, удаление загрузки, смена часового пояса, «Не подписка»), а снимки после релиза реестра заменяются молча, по месяцам (решение владельца 20.10.2026).

## 8. Помощник

- Попытка списывается при создании вопроса (под той же блокировкой, что и проверка лимита) и возвращается при любой ошибке ответа (`failed`: сейчас `MODEL_ERROR`, `CANNOT_ANSWER`, `OFF_TOPIC`) и когда хотя бы одна нужная функция вернула `locked` или охват `no_data` за запрошенный период (`charged: false`). Пустой результат при покрытом периоде — ответ, попытка списана.
- Вопрос не по теме (решение 17.10.2026, FIN-159): модель вызвала инструмент `off_topic` — цикл останавливается (инструменты и поиск больше не вызываются, текст модели не используется), ответ — `failed` с `OFF_TOPIC`, `retryable: false`, попытка возвращается. Создание вопроса по-прежнему проверяет суточный лимит: без остатка — `LIMIT_EXCEEDED`. Отдельная защита от повторяющихся OFF_TOPIC — api.md, раздел 7 (FIN-222): начальные значения 5 исходов за скользящие 7 суток, сброс только после финансового `complete` с `charged: true`; заблокированный новый вопрос или повтор — `RATE_LIMITED` без вызова модели и списания.
- Повтор (7.4) — только для `failed` с `retryable: true` (сейчас — `MODEL_ERROR`), не заменённого; списывает новую попытку, режим переводов — как у исходного вопроса.
- `changed_since` (FIN-367): assistant сравнивает сохранённые ревизии всех использованных исходных данных с текущими primary-ревизиями, а не с `calculated_at`. Несовпадение даёт `categories` для категорий/учётных правил, `uploads` для завершённых/удалённых загрузок, `time_zone` для применённых настроек пояса. Отсутствующий или недоказуемый baseline даёт `unverified`, без выдуманного факта правки; пустой список подтверждает совпадение всех использованных ревизий. В истории проверка выполняется на момент запроса, в WatchAnswer — перед snapshot с источником и последующими source при обновлениях ответа. Политика неполной доставки analytics, недоступности проверки и неизвестных кодов — `docs/grpc-api.md`, «Ревизии исходных данных ответа помощника»; REST-тексты — `docs/api.md`, раздел 7. `calculated_at` остаётся временем расчёта для показа.
- Цифры в блоках ответа считаются по этому документу в режиме вопроса, а не из текста модели; пороги — те же.

## 10. Порядок и состав

Порядок элементов и состав блоков эталон сравнивает поэлементно. Для клиента порядок блоков 6.1 — не ограничение контракта (api.md, «Блоки экрана»: состав и порядок решает сервер), но обе реализации сервера отдают его одинаково. При равенстве основного ключа названия сравниваются по кодовым точкам Unicode, без учёта локали (латиница раньше кириллицы, заглавные раньше строчных, «ё» после «я»).

- **Блоки экрана 6.1** — `tiles` (плитки по порядку: `balance`, `expense`, `daily_expense`, `income`; дополнительная `forecast` — пятой только для свежего текущего периода, включая её блокировки (FIN-408 / FIN-401)); `monthly_chart` (кроме раннего состояния, раздел 4); `expense_categories`; `income_categories`; только для месяца — `heading` «Регулярные платежи и заметные траты», `regular_payments`, по карточке `notable_spending` на заметную категорию (одна карточка, если заметных нет или блок закрыт), `bank_fees`, `small_frequent`; для месяца и квартала — `balance` последним (для года его нет).
- **Операции (4.1)** — новые первыми; при равном `occurred_at` — по (`ACCTID`, `FITID`) записи по убыванию (у пары — по стороне списания).
- **Категории в `ranked_list`** — по убыванию суммы, при равной — по названию.
- **Категории 5.1** — в порядке списка известных (3.1: системные, затем категории банка из `fixtures/calc/categories.json` в порядке файла), затем новые категории банка в порядке первого появления: по загрузкам, внутри файла — в порядке строк (не по дате операции).
- **Регулярные платежи** — по убыванию суммы, при равной — по описанию. В `items` — первые три платежа, остальные — в `items_more`; у строки и `action` (операции платежа), и `button` («Не подписка»).
- **Заметные траты** — по убыванию разницы «расход в P − обычно» в копейках, при равной — по названию категории.
- **Мелкие частые траты** — группы по убыванию суммы, при равной — по названию. Крупнейшая группа — в `description` и `action` карточки, в `items` — остальные (одна группа — `items: []`).
- **Примечания под «Расходами по месяцам» (`notes`)** — состав строк по типу периода: месяц — `primary` сравнение «к тому же дню», если прошлый месяц полный, и `muted` «обычно», если есть 2 полных прошлых месяца; квартал — `primary` пиковый месяц, если хотя бы у одного месяца графика есть значение, и `muted` «обычно» при 2 полных прошлых кварталах; год — `primary` пиковый месяц и `muted` итог по месяцам, обе — только если хотя бы у одного месяца графика есть значение (у периода без данных `notes: []`). Текст строк — на сервере, эталон сравнивает число строк и `tone`.

## 11. Вся история, выбор месяца и группы итогов (FIN-409)

- `period=all_time`, точный ключ `all_time` — вся оболочка текущего объединения покрытых дней `[data_from,data_to)`, включая несколько лет и внутренние разрывы. При изменении импорта/удалении/категории/пояса пересчитывается вместе с календарными периодами; удалённые данные не остаются в суммах и диапазоне. `has_data` и правила dedup/refund/own-transfer/transfer_mode не меняются. В отличие от раздела4 для календарного периода, all_time имеет coverage=complete при отсутствии внутренних пропусков независимо от today/завершения текущего месяца; при пропусках partial. Месячные точки сохраняют прежнюю календарную полноту.
- Фактические E/I/разница/категории — по тем же правилам разделов1–5 за всю оболочку; средний день — E / число покрытых дней не позже сегодня, с прежним усечением к нулю. Разрывы не входят в знаменатель, округлённые средние месяцев не складываются. Прогноз, сравнения/«обычно», месячные наблюдения и отдельный balance-chart не предусмотрены. `is_current=false`, навигация отсутствует.
- `monthly_chart` для all_time: все календарные месяцы оболочки, старые первыми; покрытый ноль отличается от no_data/null. Даже 1 неполный месяц доступен: порог2 и early-state hide календарных режимов здесь не применяются. Выделения нет, подпись содержит год, заметка — пиковый месяц по прежнему правилу.
- FIN-398 добавляет select_analytics_period(MONTH,YYYY-MM) только покрытым точкам monthly_chart; денежные значения и формулы сохраняются. Ноль/отрицательный расход не выключает действие; no_data — без действия. Balance и assistant не получают действия выбора периода.
- При supports=tile_group@2 и выше — tile_group v2, groups: первая без заголовка [expense,income,balance], дополнительная с заголовком «Дополнительные показатели» [daily_expense,forecast?]. Expense/income названы «Расходы за период»/«Доходы за период», daily — «Средние расходы в день» и всегда содержит пояснение покрытых дней/исключения пропусков, сравнение — дополнение. Без supports/max1 полностью сохраняется прежняя v1 композиция FIN-408. Прогноз остаётся дополнительным по прежним условиям. no_data: groups=[] в v2, tiles=[] в v1, status=none и empty_text, без нулевых фактов.
- Согласование версии действует независимо для каждого типа: более высокая заявленная версия включает поддерживаемые более низкие; не заявленный тип не отдаётся. Все остальные примитивы пока v1.

Ежедневный пересчёт в 00:05 по поясу пользователя включает all_time обоих режимов независимо от is_current=false: ход календаря меняет полноту месячных точек и число покрытых дней не позже сегодня. Например, при OFX1–31октября точка октября partial31октября и complete1ноября без импорта. Суммы и исходные ревизии не меняются только из-за хода часов; доставка/clearing и удаление singleton следуют прежнему протоколу grpc-api7.3.

## 12. Скользящие фактические периоды (FIN-413, клиент FIN-411)

- `rolling_year` и `rolling_quarter` — отдельные типы с постоянными точными ключами того же имени, а не календарные год/квартал и не вся история. Обозначим последний покрытый день объединения всех действующих завершённых загрузок как D; он определяется по разделу4, включая пустые выписки с валидными границами, независимо от последней операции и сегодня. E — календарная дата D+1; S — E минус 12/3 календарных месяца с сохранением номера дня, а если его нет — последний день целевого месяца. Интервал P = [начало S; начало E) в текущем поясе профиля, каждую границу переводим в момент отдельно. Нельзя вычитать фиксированное число суток или нормализовать несуществующий день в следующий месяц (например, Go AddDate без clamp).
- Примеры: D=30.09.2026 → год [01.10.2025;01.10.2026), квартал [01.07.2026;01.10.2026). D=30.10.2026 → год [31.10.2025;31.10.2026). D=15.09.2026 → квартал [16.06.2026;16.09.2026); D=05.10.2026 → [06.07.2026;06.10.2026). D=30.05.2024 → квартал [29.02.2024;31.05.2024); D=30.05.2023 → [28.02.2023;31.05.2023). D=28.02.2024 → год [28.02.2023;29.02.2024).
- Range всегда полный запрошенный P, даже при короткой истории. `data_from`/`data_to` — фактическое покрытие внутри P по разделу4; короткое начало не сдвигает range. `complete` — все дни P покрыты, независимо от today, иначе `partial`. Внутренние `gaps` следуют прежнему правилу без обрезки; отсутствие покрытия в начале P видно по `data_from > range.from`, не выдумывается как ноль или внутренний gap. Список6.2 — один элемент либо пустой без покрытия. `is_current=false`, соседей нет. `has_data` остаётся общим правилом: только пустые выписки дают пустой экран; операции в другой части истории при покрытом P без операций дают настоящий ноль.
- E(V∩P), I(V∩P), разница, дневное среднее, категории и фильтры переходов вычисляются по исходным дедуплицированным операциям в P, с прежними возвратами и обоими режимами переводов; matching возвратов/пар использует всю историю до фильтрации P. Среднее = E/N с прежним усечением, N — покрытые дни P не позже сегодня, минимум 1, без внутренних пропусков. Пороги полных месяцев не закрывают факты или график. Прогноз, сравнения с прошлыми периодами, «обычно», месячные наблюдения и отдельный balance-chart отсутствуют; календарные прогнозы и их условия не меняются.
- `monthly_chart` — все календарные месяцы, пересекающие P, старые первыми: максимум13/4 точки. Сумма точки считается только на пересечении календарного месяца с P, а не за целый краевой месяц. REST `range` точки — именно это пересечение; подписи различают годы. В gRPC `MonthlyPoint.month`/`range` сохраняют календарный ключ/месяц, новый `calculation_range` передаёт точное пересечение для сумм и `bounds`. Краевой отрезок — `partial`, даже если он покрыт целиком; целый месяц — по календарному правилу4. Без покрытых дней в отрезке — `no_data` и `null`, без действия; покрытый ноль —0 с действием. `data_from`/`data_to` точки относятся только к пересечению. Нажатие через select_analytics_period(MONTH, YYYY-MM) открывает **полный календарный месяц**, поэтому его сумма может отличаться от краевой точки. Highlight отсутствует; из notes допустим только пиковый месяц по суммам отрезков, без «обычно»/сравнений.
- Импорт, удаление, категория и смена пояса полностью пересчитывают оба singleton обоих режимов вместе с календарными периодами и all_time. Пояс применяется заново к исходным временным границам загрузок и операциям, не к сохранённым дням. Ежедневный пересчёт обновляет дневной знаменатель и календарную полноту точек; без изменения покрытия сам P от today не сдвигается. Постоянный ключ не разрешает смешивать range и метрики разных исходных снимков.
