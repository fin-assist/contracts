# Эталонные данные расчёта (FIN-107)

Исполняемый контракт расчёта: на одних и тех же выписках и действиях фейковый бэкенд Android (`:mock:backend`, FIN-108) и Go-бэкенд должны отдавать одинаковые ответы API. Правила расчёта — спецификация [«Расчёт метрик и правила учёта»](https://finassist.atlassian.net/wiki/spaces/PF/pages/13991937) (FIN-106), смысл полей — `docs/api.md`.

Ожидаемые ответы не пишутся руками: их считает референсный расчёт `tools/refcalc` — небольшая реализация спецификации на Python (без зависимостей), проверенная примерами раздела 9 спецификации (`tools/refcalc/tests`). Расхождение реализации с эталоном — это либо ошибка реализации, либо ошибка референсного расчёта; второе правится в `tools/refcalc` вместе с перегенерацией ожидаемых ответов.

## Состав

| Путь | Что |
|---|---|
| `categories.json` | Реестр категорий для теста: системные (`cat_own_transfer`, `cat_refund`, `cat_uncategorized`) и известные категории банка с `id`, иконкой и направлением (`kinds`) по спецификации, 3.1. Обе реализации загружают его вместо своего реестра |
| `statements/*.ofx` | Выписки сценария |
| `scenario.json` | Сценарий: пояс профиля и шаги по порядку |
| `expected/*.json` | Ожидаемые ответы шагов сценария, уже подготовленные к сравнению (`<ignored>` там, где значение не сравнивается) |

### Выписки

`01`–`03` — фикстура фейкового бэкенда (`mock/backend/src/main/assets/statements/fixture.ofx`, release/0.2.8), дополнительно обезличенная: номера счетов заменены на фиктивные (`40817810000000001111` — текущий, `42301810000000002222` — накопительный, `OB$1$000000000000000000demo01` — счёт другого банка); `FITID` банка заменены стабильным хешем; работодатель — «Работодатель», имена ИП — «ИП 1», «ИП 2», …, похожие на имена описания — «Кафе 1», «Магазин 1», …; убраны регион налоговой и номера банкоматов. Телефоны в фикстуре уже замаскированы, контрагенты пронумерованы. Остались названия магазинов, сетей и мест — они не указывают на человека. В них добавлены синтетические платежи: «Облако Плюс» (раз в месяц — регулярный) и «Фитнес Плюс» (раз в неделю — не регулярный: в MVP регулярный платёж — ровно одно списание в месяц). `04`, `05` — синтетические крайние случаи.

## Сценарий

`scenario.json`: `time_zone` — пояс профиля; `steps` — шаги по порядку, выполняются для одного нового пользователя. Поля шага:

| Поле | Что |
|---|---|
| `name` | Имя шага: на него ссылаются другие шаги |
| `now` | «Текущий момент» с этого шага и до следующего `now` (часы реализации подменяются); он же `uploaded_at` загрузки |
| `do` | Действие (ниже) |
| `expect` | Файл ожидаемого ответа; нет — ответ не сравнивается |

| `do` | Параметры | Что делает реализация | Ответ для сравнения |
|---|---|---|---|
| `upload` | `file` | 3.2 загружает файл, ждёт конца разбора | событие `complete` (3.3) |
| `get` | `request` — метод и путь с query (`GET /v1/analytics?period=month&date=2026-09&transfer_mode=with`) **или** `filter_from: {step, path}` — `operations_filter` из ответа шага `step` по пути `path`, превращённый в запрос 4.1 (`selection_name` не передаётся). Элемент пути — ключ, индекс или `{"id": "…"}` (первый элемент массива с таким `id`, например блок 6.1) | выполняет запрос | ответ `200` |
| `change_category` | `operation: {account, fitid}`, `category_id` | 4.3 для записи операции с этим `ACCTID` и `FITID` (запись пары — по любой её стороне) | ответ 4.3 |
| `dismiss_regular_payment` | `request`, `title` | выполняет `request` (6.1), находит в блоке `regular_payments` строку с этим `title` (одну из видимых строк `items`) и вызывает 6.3 `PUT` с её `payment_id` | — |
| `delete_upload` | `file` | 3.5 удаляет загрузку этого файла | — |

Ошибка API на шаге с `expect` записывается как `{"status": <HTTP>, "error": {"code": "<код>"}}`. Ответы ниже — только `200`; ошибки в сценарий пока не входят.

## Правила сравнения

Реализация сравнивает свой ответ с файлом из `expected/` так (эталонная функция — `tools/refcalc/refcalc/compare.py`):

- **`<ignored>`** в ожидаемом — значение не сравнивается, поле может и отсутствовать. Так помечены:
  - непрозрачные значения: `id` операций и пар, `replaced_id`, `payment_id`, `selection`, `calculated_at`. `id` блоков, плиток, элементов `ranked_list` (это `category_id`) и категорий 5.1 — ключи, они сравниваются;
  - тексты, которые сервер пишет для показа: в блоках 6.1 — `title`, `alt_text`, `empty_text`, `text`, `caption`, `label`, `note`, `description`, `badge`, `sublabel`, `value_suffix`, `more_label`, `notes` целиком; вне блоков — `selection_name`, `type_name`, `feature_name`, `text` (функции, уведомления), `spoken`, `note_details`, `source_name`. Числа этих текстов приходят и в структурированных полях, их и сравнивают. Исключение — `title` строк в `items` блоков: это данные (категория, продавец, платёж), они сравниваются. Вне блоков `title` и `description` операции (описание из выписки) и `note` («не в тратах», «возврат · <цель>» — формат задан спецификацией, 3.3) — тоже данные.
- **Отсутствие = `null`** (нотация `T?`). Блок или плитка без `status` — `ready`.
- **Лишнее поле** в ответе реализации (его нет в эталоне) допустимо, только если это текст или непрозрачный `id` из списков выше; иначе — расхождение (например, `share` там, где доли быть не должно).
- **Моменты времени** (RFC 3339) сравниваются как моменты: `2026-09-25T21:40:00+03:00` = `2026-09-25T18:40:00Z`.
- **Дробные** (`share`, точки `percent`) — с допуском `1e-9`; суммы и счётчики — точно.
- **Массивы** — поэлементно, по порядку, одинаковой длины. Порядок задаёт спецификация, а при равенстве:
  - операции (4.1) — новые первыми; при равном `occurred_at` — по (`ACCTID`, `FITID`) записи по убыванию (у пары — по стороне списания);
  - категории (`ranked_list`) — по убыванию суммы, при равной — по `id`;
  - регулярные платежи — по убыванию суммы, при равной — по описанию; заметные траты — по превышению, затем по `id`; группы мелких частых трат — по сумме, затем по названию.
- Блоки 6.1 сравниваются по порядку: состав и порядок экрана — часть контракта. Ответы — при параметрах по умолчанию (`supports` и `exp` не передаются). Состав, который спецификация задаёт не дословно, эталон фиксирует так:
  - `small_frequent`: крупнейшая группа — в `description` и `action` карточки, в `items` — остальные группы (одна группа — `items: []`);
  - `regular_payments`: в `items` — первые три платежа, остальные — `items_more`; у строки и `action` (операции платежа), и `button` («Не подписка»);
  - медиана сумм регулярного платежа — элемент с индексом n/2 отсортированных сумм (спецификация, раздел 5), то есть при чётном n — верхний из двух средних;
  - плитка `daily_expense` не блокируется (спецификация, раздел 5: «всегда»).
- Выборки (`selection`) проверяются переходом в Поиск: «Без категории» (из итога импорта), все регулярные платежи, группа мелких частых трат и комиссии (из карточек 6.1).

## Как обновить

После правки спецификации, `docs/api.md` или `tools/refcalc` (из `tools/refcalc`):

```bash
python3 -m unittest discover -s tests -t .
python3 -m refcalc.scenario ../../fixtures/calc --write --openapi ../../openapi/openapi.yaml
```

`--openapi` проверяет ответы схемой `openapi.yaml` (до замены на `<ignored>`; нужны `pyyaml` и `openapi-schema-validator`). CI делает то же с `--check`: ожидаемые ответы должны совпадать с перегенерированными байт в байт и проходить схему.

Новый случай — шаг в `scenario.json` (и, если нужно, новая выписка) и перегенерация. Изменение ожидаемых ответов в PR — это изменение поведения обеих реализаций: в описании PR — какие ответы и почему поменялись, и клиентская задача на фейковый бэкенд.
