# Эталонные данные расчёта (FIN-107)

Исполняемый контракт расчёта: на одних и тех же выписках и действиях фейковый бэкенд Android (`:mock:backend`, FIN-108) и Go-бэкенд должны отдавать одинаковые ответы API. Правила расчёта — `docs/calc.md`, смысл полей — `docs/api.md`. Эталон — их исполняемая копия: при расхождении прав `docs/calc.md`, а эталон и `tools/refcalc` правятся вслед. Здесь — только состав данных и то, как сравниваются ответы; правило расчёта, записанное только здесь, — дефект.

Ожидаемые ответы не пишутся руками: их считает референсный расчёт `tools/refcalc` — небольшая реализация `docs/calc.md` на Python (без зависимостей), проверенная примерами его раздела 9 (`tools/refcalc/tests`). Расхождение реализации с эталоном — это либо ошибка реализации, либо ошибка референсного расчёта; второе правится в `tools/refcalc` вместе с перегенерацией ожидаемых ответов.

## Состав

| Путь | Что |
|---|---|
| `categories.json` | Реестр категорий для теста: системные (`cat_own_transfer`, `cat_refund`, `cat_uncategorized`) и известные категории банка с `id`, иконкой и направлением (`kinds`) по `docs/calc.md`, 3.1. Обе реализации загружают его вместо своего реестра |
| `statements/*.ofx` | Выписки сценария |
| `scenario.json` | Сценарий: пояс профиля и шаги по порядку |
| `coverage-exceptions.json` | Поля схем ответов, которых нет ни в одном ожидаемом ответе, — каждое с причиной (FIN-157) |
| `expected/*.json` | Ожидаемые ответы шагов сценария, уже подготовленные к сравнению (`<ignored>` там, где значение не сравнивается) |

## Сценарий

`scenario.json`: `time_zone` — пояс профиля; `steps` — шаги по порядку, выполняются для одного нового пользователя. Поля шага:

| Поле | Что |
|---|---|
| `name` | Имя шага: на него ссылаются другие шаги |
| `now` | «Текущий момент» с этого шага и до следующего `now` (часы реализации подменяются); он же `uploaded_at` загрузки |
| `do` | Действие (ниже) |
| `expect` | Файл ожидаемого ответа; нет — ответ не сравнивается |

| `do` | Параметры | Что делает реализация | Ответ для сравнения |
|---|---|---|---|
| `upload` | `file` | 3.2 загружает файл, ждёт конца разбора | событие `complete` (3.3) |
| `get` | `request` — метод и путь с query (`GET /v1/analytics?period=month&date=2026-09&transfer_mode=with`) **или** `filter_from: {step, path}` — `operations_filter` из ответа шага `step` по пути `path`, превращённый в запрос 4.1 (`selection_name` не передаётся). Элемент пути — ключ, индекс или `{"id": "…"}` (первый элемент массива с таким `id`, например блок 6.1) | выполняет запрос | ответ `200` |
| `change_category` | `operation: {account, fitid}`, `category_id` | 4.3 для записи операции с этим `ACCTID` и `FITID` (запись пары — по любой её стороне) | ответ 4.3 |
| `dismiss_regular_payment` | `request`, `title` | выполняет `request` (6.1), находит в блоке `regular_payments` строку с этим `title` (одну из видимых строк `items`) и вызывает 6.3 `PUT` с её `payment_id` | — |
| `delete_upload` | `file` | 3.5 удаляет загрузку этого файла | — |

Ошибка API на шаге с `expect` записывается как `{"status": <HTTP>, "error": {"code": "<код>", "message": "<ignored>"}}`: сравниваются статус и код, `message` — текст. Ответы ниже — только `200`; ошибки в сценарий пока не входят.

## Правила сравнения

Реализация сравнивает свой ответ с файлом из `expected/` так (эталонная функция — `tools/refcalc/refcalc/compare.py`):

- **`<ignored>`** в ожидаемом — значение не сравнивается, поле может и отсутствовать. Так помечены:
  - непрозрачные значения: `id` операций и пар, `replaced_id`, `payment_id`, `selection`, `calculated_at`. `id` блоков, плиток, элементов `ranked_list` (это `category_id`) и категорий 5.1 — ключи, они сравниваются; исключение — категория банка, которой нет в `categories.json` (пришла из выписки): её `id` и `category_id` непрозрачны (контракт не задаёт, как они образуются), такая категория сопоставляется по названию;
  - тексты, которые сервер пишет для показа: в блоках 6.1 — `title`, `alt_text`, `empty_text`, `text`, `caption`, `label`, `note`, `description`, `badge`, `sublabel`, `value_suffix`, `more_label`, `text` строк `notes` (состав строк сравнивается — см. ниже); вне блоков — `selection_name`, `type_name`, `feature_name`, `text` (функции, уведомления), `spoken`, `note_details`, `source_name`, `message` ошибки. Числа этих текстов приходят и в структурированных полях, их и сравнивают. Исключение — `title` строк в `items` блоков: это данные (категория, продавец, платёж), они сравниваются. Вне блоков `title` и `description` операции (описание из выписки) и `note` («не в тратах», «возврат · <цель>» — формат задан `docs/calc.md`, 3.3) — тоже данные.
- **Отсутствие = `null`** (нотация `T?`). Блок или плитка без `status` — `ready`.
- **Лишнее поле** в ответе реализации (его нет в эталоне) допустимо, только если это текст или непрозрачный `id` из списков выше; иначе — расхождение (например, `share` там, где доли быть не должно).
- **Моменты времени** (RFC 3339) сравниваются как моменты: `2026-09-25T21:40:00+03:00` = `2026-09-25T18:40:00Z`.
- **Дробные** (`share`, точки `percent`) — с допуском `1e-9`; суммы и счётчики — точно.
- **Массивы** — поэлементно, по порядку, одинаковой длины. Порядок, разбор равенств и состав блоков задаёт `docs/calc.md`, раздел 10.
- Блоки 6.1 сравниваются по порядку: состав и порядок экрана — часть контракта. Ответы — при параметрах по умолчанию (`supports` и `exp` не передаются).
- `notes` под графиком «Расходы по месяцам» сравниваются по составу — число строк и `tone` (`docs/calc.md`, раздел 10), `text` не сравнивается.
- Имя категории сравнивается как есть, без нормализации пробелов (`docs/calc.md`, 3.1): в реестре «Ремонт и мебель» — с неразрывным пробелом, как в выписке банка.
- Выборки (`selection`) проверяются переходом в Поиск: «Без категории» (из итога импорта), все регулярные платежи, группа мелких частых трат и комиссии (из карточек 6.1).

## Как обновить

После правки `docs/calc.md`, `docs/api.md` или `tools/refcalc` (из `tools/refcalc`):

```bash
python3 -m unittest discover -s tests -t .
python3 -m refcalc.scenario ../../fixtures/calc --write --openapi ../../openapi/openapi.yaml
```

`--openapi` проверяет ответы схемой `openapi.yaml` (и `data` каждого блока 6.1 — схемой своего примитива: `ChartData`, `TileGroupData`, …) и **покрытие схемы**: каждое поле схем ответов, которые проверяет эталон, хотя бы в одном ожидаемом ответе имеет значение, иначе оно должно быть в `coverage-exceptions.json` с причиной; запись об уже покрытом или несуществующем поле — тоже ошибка. Поэтому новое поле контракта без шага сценария, который его отдаёт, роняет CI. Проверка (до замены на `<ignored>`; нужны `pyyaml`, `openapi-schema-validator` и `rfc3339-validator` — проверка формата `date-time`). CI делает то же с `--check`: ожидаемые ответы должны совпадать с перегенерированными байт в байт и проходить схему.

Новый случай или новое поле контракта — шаг в `scenario.json` (и, если нужно, новая выписка), расчёт поля в `tools/refcalc` и перегенерация. В исключения покрытия — только поле, которого в ответах MVP не бывает, с причиной. Изменение ожидаемых ответов в PR — это изменение поведения обеих реализаций: в описании PR — какие ответы и почему поменялись, и клиентская задача на фейковый бэкенд.
